# 하네스 엔지니어링

AI가 프로젝트를 수행하는 환경을 개선한다.
[하네스 판단 기준](references/harness-engineering.md)을 읽고 현재 문제에 해당하는 부분을 적용한다.

1. 요청, 기대 행동, 실제 도구 입력·결과와 실행 환경을 확인한다. 필요한 증거가 없으면 실패 원인을 단정하지 않는다.
2. 정보 부족, 도구 실행 실패, 결과 판정 실패, 권한·상태 문제를 구분한다. 현재 지침, 도구 설명과 설정으로 해결할 수 있는지도 살핀다.
3. 원인에 맞춰 판단 안내(Guide), 결과 관찰(Sensor), 진행 차단(Gate), 규칙에 따른 수정(Transformer)을 고르고 개입할 위치를 정한다. 명칭보다 실제로 관찰·변경·차단할 동작을 설명한다.
   검사 결과의 다음 경로도 정한다. 허용된 범위에서 고칠 수 있는 실패는 에이전트의 수정·재검사로 잇고, 사용자 선택·권한·요구 변경은 필요한 결정을 구체적으로 제시해 사람에게 넘긴다. 반복 한도와 검사기 오류 때의 행동을 정한다.
4. 사용 중인 호스트와 버전을 확인한 뒤 지원되는 설정·API로 구현한다. 설치 범위와 프로젝트 데이터의 저장·공유 범위를 구분한다. 한 호스트의 훅 이름과 반환 형식을 다른 호스트에 그대로 적용하지 않는다.
5. 실패 사례와 정상 사례를 같은 초기 상태에서 변경 전후로 확인한다. 실행 결과, 오탐, 누락, 반복 수정, 시간·비용과 미검증 범위를 보고한다.

실행 후 검사가 이미 발생한 부작용을 막았다고 주장하지 않는다.
차단이 필요하면 우회 경로, 검사 오류, 반복 실행과 복구를 확인한다.
안내만 필요한 문제에 매번 승인이나 차단을 추가하지 않는다.
기존 사용자 권한과 작업 범위를 유지하고, 새 권한이나 외부 부작용이 필요한 경우 구체적인 변경과 영향을 제시한다.

필요한 자료를 실제로 읽을 수 있게 연결하되 모든 문서를 상시 문맥에 넣지 않는다.
다음 세션에 필요한 결정은 프로젝트의 기존 기록 방식을 따른다.
발동 문제와 내용 문제를 나눠 확인하며 명시 호출 성공만으로 자동 선택이 검증됐다고 보고하지 않는다.
결과에 맞춰 개입을 유지·수정·축소하고, 단일 사례를 보편 규칙으로 만들지 않는다.
