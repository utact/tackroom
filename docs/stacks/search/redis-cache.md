# Redis 캐시

확인: 2026-09-29 재검토. 최초 조사는 2026-09-27, redis/docs 저장소(Redis 8.x 문서) 기준. 캐시 일관성 기법은 Facebook의 memcache 논문(NSDI 2013)과 Vattani 외(VLDB 2015)를 근거로 한다.

## 요약

Redis 캐시는 계산하거나 조회하는 데 비싼 결과를 메모리에 두고, 같은 요청에 원본 대신 답한다.
캐시는 기준점이 아니라 **다시 만들 수 있는 파생물**이다.
어려운 부분은 속도가 아니라 "언제 틀린 값을 주게 되는가"를 통제하는 것이다. 키에 무엇을 넣고, 언제 지우고, 동시에 채울 때 어떻게 되는지가 핵심이다.

## 문제 신호

- 같은 조회가 반복되고, 원인을 고친 뒤에도 원본(DB, 외부 API)의 부하나 지연이 한계에 가깝다.
- 결과를 계산하는 비용이 크고(집계, 추천, 외부 API), 약간 오래된 값이 허용된다.
- 외부 API의 호출 한도나 요금 때문에 호출 수를 줄여야 한다.
- 인스턴스 여러 개가 같은 계산 결과를 공유해야 한다.

## 기준선의 한계

기준선은 인덱스와 실행 계획을 고친 SQL이다.

- 캐시 전에 느린 이유를 확인한다. [PostgreSQL](../state/postgresql.md#깊이-있는-활용)의 `pg_stat_statements`와 `EXPLAIN (ANALYZE, BUFFERS)`로 인덱스 부재, 잘못된 계획, N+1을 찾는다. 여기서 풀리면 캐시는 필요 없다.
- DB 자체의 버퍼 캐시는 이미 자주 읽는 페이지를 메모리에 둔다. 문제는 "읽기"가 아니라 "계산"이나 "왕복 횟수"일 때가 많다.
- 프로세스 안 캐시([Caffeine](caffeine.md))는 인스턴스끼리 공유하지 않는다. 인스턴스마다 따로 채우고, 무효화가 다른 인스턴스에 전파되지 않는다.

## 원리

- **메모리 키-값 저장소.** 단일 스레드 명령 처리로 명령 하나는 원자적이다. 문자열, 해시, 집합 등 자료구조가 있다.
- **만료(TTL).** 캐시에 쓴 뒤 키가 살아 있는 시간을 제한한다. 지연된 읽기가 옛 값을 다시 채우거나 원본 복제본이 뒤처져 있으면 TTL만으로 원본 변경 후의 신선도 상한을 보장하지 못한다. 값의 버전·원본 시각과 재적재 경쟁까지 고려한다.
- **퇴출 정책.** `maxmemory`에 닿으면 `maxmemory-policy`에 따라 키를 버린다.
  - `noeviction`은 쓰기에 오류를 준다.
  - `allkeys-lru`, `allkeys-lfu`, `allkeys-lrm`(8.6부터, 쓰기 시각 기준), `volatile-*`(만료가 있는 키만) 중 문서는 `allkeys-lru`를 무난한 기본으로 권한다.
  - LRU는 표본을 뽑는 근사다.
- **읽기 경로(look-aside).** 캐시를 먼저 보고, 없으면 원본을 읽어 넣는다. 채우기와 무효화는 모두 애플리케이션의 책임이다.
- **서버 보조 클라이언트 캐싱.** Redis 6부터 `CLIENT TRACKING`으로 클라이언트가 읽은 키가 바뀌면 서버가 무효화 메시지를 보낸다. 기본 모드는 서버가 클라이언트별로 읽은 키를 기억하고, broadcasting 모드는 키 접두어를 구독한다.

## 가치

Redis 캐시의 가치는 **여러 인스턴스가 공유하는, 원자적 연산이 있는 빠른 파생 상태 저장소**라는 점이다.

- 비싼 계산을 한 번 하고 모든 인스턴스가 재사용한다.
- 원자적 명령(`SET NX`, `INCR`)으로 채우기 경쟁, 속도 제한, 카운터를 함께 다룬다.
- TTL과 퇴출 정책으로 메모리를 스스로 관리한다.

값을 잃어도 원본에서 다시 만들 수 있을 때만 이 가치가 안전하다.
원본이 없는 상태(세션, 장바구니)를 두면 캐시가 아니라 저장소이므로 내구성 요구가 달라진다.

- **학습 실험.** 상품 조회에서 원본 읽기 직후 요청을 멈추고 다른 요청으로 값을 수정한다. 캐시 삭제 뒤 옛 값이 다시 채워지는지 관찰하고, TTL·버전 검사·채우기 합치기의 역할을 비교한다.

## 트레이드오프와 리스크

- **틀린 값을 줄 수 있다.** 원본이 바뀌고 무효화가 늦거나 빠지면 오래된 값이 나간다. 권한이나 가격처럼 틀리면 안 되는 값은 특히 위험하다.
- **무효화 경쟁(stale set).** "원본 읽기 → 캐시 쓰기" 사이에 다른 요청이 원본을 바꾸고 캐시를 지우면, 늦게 도착한 옛 값이 캐시에 남는다. Facebook memcache 논문은 이 문제를 stale set으로 부르고 lease로 해결했다.
- **캐시 쇄도(stampede, thundering herd).** 인기 키가 만료되는 순간 많은 요청이 동시에 원본으로 간다. 원본이 캐시를 전제로 용량을 잡았다면 이때 쓰러진다.
- **콜드 스타트.** 캐시가 비면(재시작, 퇴출, 장애) 원본이 전체 부하를 받는다. 원본이 그 부하를 견디지 못하면 캐시가 가용성의 일부가 된다.
- **키 설계 오류가 데이터 유출이 된다.** 사용자별로 달라야 할 결과를 사용자 ID 없이 캐시하면 다른 사용자에게 보인다.
- **새 장애 지점과 네트워크 왕복.** 캐시가 느려지거나 죽으면 모든 요청이 영향을 받으므로 타임아웃과 우회 경로가 필요하다.
- **메모리 비용과 핫 키.** 큰 값, 한 키에 몰리는 요청은 단일 노드를 포화시킨다.

## 대안과 경계

| 대안 | 고를 때 |
|---|---|
| 쿼리와 인덱스 개선 | 느린 원인이 쿼리다. 캐시보다 먼저 한다. |
| [Caffeine](caffeine.md) | 값이 작고 자주 읽히며, 인스턴스별로 따로 가져도 되고, 네트워크 왕복조차 아깝다. Redis 앞의 1차 캐시로도 쓴다. |
| 구체화 뷰, 요약 테이블 | 집계 결과를 DB 안에 두고 트랜잭션 일관성을 유지한다. 새로 고침 주기를 정한다. |
| HTTP 캐시, CDN | 응답 전체를 사용자 가까이에서 재사용한다. `Cache-Control`, `ETag`로 제어한다. |
| 읽기 복제본 | 읽기 부하 분산이 목적이고, 결과를 가공하지 않는다. 복제 지연이 신선도 한도가 된다. |

## 깊이 있는 활용

- **키에 결과를 바꾸는 모든 입력을 넣는다.** 사용자나 권한 범위, 로캘, 스키마 버전, 원본 버전을 키에 넣는다. 예: `product:v3:{id}:ko`. 형식이 바뀌면 버전만 올려 옛 키를 자연 퇴출시킨다.
- **쓰기 후에는 갱신하지 말고 지운다.** 원본을 바꾼 뒤 키를 지우고 다음 읽기가 채우게 한다. 두 쓰기의 순서가 뒤바뀌어 옛 값이 남는 경쟁이 준다(Facebook 논문의 방식).
- **stale set은 채우기 토큰으로 막는다.** memcache 논문의 lease를 흉내 낸다. 미스 때 토큰을 받고(`SET lock:key 토큰 NX PX`), 그 사이 무효화가 토큰을 지웠으면 채우지 않는다. 토큰 확인과 값 쓰기는 Lua 스크립트 하나로 묶는다. 따로 하면 확인과 쓰기 사이에 다시 무효화가 끼어든다.
- **쇄도는 한 명만 채우게 한다.** 미스 때 채우기 잠금을 얻은 요청 하나만 원본을 읽고, 나머지는 잠깐 기다렸다 다시 보거나 옛 값을 쓴다. memcache 논문은 키당 10초에 한 번만 토큰을 내줬다.
- **만료 전에 확률적으로 미리 갱신한다.** XFetch(Vattani 외)는 만료가 가까울수록 높은 확률로 요청 하나가 미리 계산하게 해 쇄도를 흩뜨린다. TTL에 지터를 더하는 것만으로도 동시 만료를 흩뜨린다.
- **"없음"도 캐시한다.** 존재하지 않는 키 조회가 매번 원본으로 가지 않게 짧은 TTL로 빈 결과를 저장한다. 공격성 조회를 막는다.
- **캐시 장애 시 원본을 보호한다.** 캐시 조회에 짧은 타임아웃을 두고, 캐시가 죽으면 원본 호출에 동시 호출 상한([Resilience4j](../api/resilience4j.md) Bulkhead)을 건다. 캐시 없이 원본이 버틸 수 있는지 미리 잰다.
- **서버 보조 무효화로 1차 캐시를 둔다.** 자주 읽는 작은 값은 프로세스 안에 두고, `CLIENT TRACKING`의 무효화 메시지로 지운다. Redis 왕복까지 없앤다.

## 임시방책의 신호

- 느린 API에 원인 분석 없이 `@Cacheable`을 붙인다.
- TTL만으로 요구된 신선도를 만족하는지 확인하지 않았다. 무효화가 없어도 허용되는 사례와, 재적재 경쟁 때문에 TTL 이후에도 옛 값이 남는 사례를 구분하지 않는다.
- 권한이 다른 사용자에게 같은 캐시 키를 쓴다.
- 캐시 쇄도로 DB가 넘어가자 TTL을 길게 늘린다.
- 캐시에만 있는 데이터가 생긴다(원본에 쓰지 않고 캐시에만 쓴다).
- 캐시가 죽으면 서비스가 같이 죽는데, 그 사실을 장애 때 안다.

## 실패 재현

- **stale set.**
  1. 요청 A가 원본을 읽은 뒤 캐시 쓰기 전에 멈춘다(주입한 지연).
  2. 요청 B가 원본을 바꾸고 캐시를 지운다.
  3. A가 재개해 옛 값을 쓰면 캐시에 옛 값이 남는다. 채우기 토큰을 넣고 반복한다.
- **쇄도.** 인기 키에 동시 요청 수백 개를 보내며 키를 만료시키고, 원본이 받은 요청 수를 센다. 채우기 잠금과 확률적 갱신을 넣어 비교한다.
- **콜드 스타트.** 캐시를 비우고(`FLUSHALL`) 정상 부하를 걸어, 원본의 지연과 오류율이 어떻게 되는지 본다.
- **캐시 장애.** [Toxiproxy](../verify/toxiproxy.md)로 Redis 연결에 지연과 끊김을 넣어, 요청 지연이 캐시 타임아웃에 묶이는지, 원본 보호가 동작하는지 본다.
- **키 누락.** 권한이 다른 두 사용자로 같은 자원을 조회해 결과가 섞이지 않는지 테스트로 고정한다.

## 측정과 검증

- **적중률만 보지 않는다.** 적중률, 원본 호출 수, 요청 지연(p50, p99)을 함께 본다. 적중률이 높아도 미스 지연이 크면 p99는 나쁘다.
- **신선도.** 원본 변경 시각과 캐시가 새 값을 주기 시작한 시각의 차이를 샘플링해 잰다. 틀린 값을 준 요청 비율을 추정한다.
- **정합성 검사.** 주기적으로 캐시 값과 원본을 표본 대조해 불일치율을 기록한다.
- **캐시 없는 용량.** 캐시를 끈 상태에서 원본이 버티는 최대 부하를 [k6](../verify/k6.md)로 잰다. 이 값이 캐시 장애 시의 가용성이다.
- **메모리와 퇴출.** `INFO`의 `used_memory`, `evicted_keys`, `keyspace_hits/misses`를 추세로 본다. 퇴출이 늘면 메모리가 부족하거나 키가 너무 많다.

## 재검토 조건

- 원인을 고쳐 원본이 캐시 없이도 충분히 빠르다. 캐시를 걷어낸다.
- 불일치로 인한 사고가 났다. 캐시 대상을 줄이거나 무효화를 강화한다.
- 캐시가 사실상 저장소가 됐다(원본이 없다). 내구성 요구에 맞는 저장소로 옮긴다.
