# HTTP 캐시와 CDN

확인: 2026-09-28, MDN(mdn/content, main)의 HTTP 캐시 안내와 `Cache-Control` 참조 기준. 명세는 RFC 9111이다.

## 요약

HTTP 캐시는 응답 헤더로 "이 응답을 누가, 얼마나 오래, 어떤 조건으로 다시 써도 되는가"를 선언하는 방식이다.
브라우저(개인 캐시)와 프록시·CDN(공유 캐시)이 이 선언을 따라 원본 서버에 가지 않고 응답한다.
애플리케이션 캐시와 달리 **코드 없이 헤더만으로** 클라이언트와 원본 사이의 모든 층에서 요청을 없앤다.

## 문제 신호

- 정적 파일, 이미지, 공개 목록 같은 같은 응답을 매번 서버가 만든다.
- 사용자와 서버가 멀어 지연이 크다.
- 트래픽 폭증 때 원본 서버가 먼저 무너진다.
- 반대로 배포 뒤에도 사용자에게 옛 파일이 보이거나, 다른 사용자의 개인 정보가 보였다는 신고가 있다.

## 기준선의 한계

기준선은 `Cache-Control` 없이 응답하는 것이다.

- 그래도 캐시는 된다. 헤더가 없으면 브라우저가 경험적으로 캐시하고, 명세는 마지막 수정 후 지난 시간의 약 10%를 권한다.
- 그래서 무엇이 얼마나 캐시될지 서버가 통제하지 못한다.
- 캐시를 끄려고 여러 지시어를 한꺼번에 넣는 "주방 싱크대" 헤더는 필요한 것보다 많은 것을 잃는다.

## 원리

- **신선도.** `max-age`(초) 동안은 원본에 묻지 않고 재사용한다. 공유 캐시에는 `s-maxage`로 따로 줄 수 있다.
- **재검증.** 신선도가 지나면 `ETag`나 `Last-Modified`로 조건부 요청을 보내고, 바뀌지 않았으면 `304`로 본문 없이 답한다.
- **지시어의 의미.**
  - `no-cache`: 저장은 하되 쓸 때마다 재검증한다.
  - `no-store`: 저장하지 않는다. 이미 저장된 옛 응답을 지우지는 않는다.
  - `private`: 개인 캐시에만 저장한다. 공유 캐시에 개인화 응답이 남아 다른 사용자에게 가는 것을 막는다.
- **`Vary`.** 요청 헤더(예: `Accept-Language`)에 따라 응답이 다르면 캐시 키에 넣는다. `User-Agent`처럼 값이 많은 헤더는 적중률을 무너뜨린다.
- **캐시 무효화(cache busting).** 바뀌지 않는 파일은 URL에 버전이나 해시를 넣고 긴 `max-age`와 `immutable`을 준다. 파일이 바뀌면 URL이 바뀐다.
- **`stale-while-revalidate`.** 만료된 응답을 먼저 주고 뒤에서 재검증한다. `stale-if-error`는 원본 오류 때 만료된 응답을 준다.

## 가치

HTTP 캐시의 가치는 **요청이 원본까지 오지 않게 하는 가장 바깥의 캐시를 표준만으로 얻는 것**이다.

- 브라우저 캐시는 네트워크 왕복 자체를 없앤다.
- CDN은 사용자 가까이에서 응답해 지연을 줄이고, 원본 부하를 흡수한다.
- 재검증은 본문 전송을 없애 대역폭을 줄인다.
- 애플리케이션 코드를 바꾸지 않고 헤더로 조정한다.

## 트레이드오프와 리스크

- **지울 수 없는 캐시.** 브라우저에 저장된 응답은 서버가 지우지 못한다. 긴 `max-age`를 준 뒤 내용이 틀렸다면 만료까지 기다려야 한다.
- **개인 정보 유출.** 개인화 응답에 `private`가 없으면 공유 캐시가 다른 사용자에게 준다. 쿠키가 있다고 자동으로 개인 응답이 되지 않는다.
- **캐시 키 실수.** `Vary`를 빠뜨리면 다른 언어나 형식의 응답이 섞이고, 과하게 넣으면 적중률이 떨어진다.
- **CDN 무효화의 지연과 비용.** 무효화 요청은 즉시가 아니고, 제품마다 요금과 한도가 있다.
- **`no-store`의 비용.** MDN은 `no-store`를 남용하면 뒤로 가기 캐시 같은 브라우저 기능을 잃는다고 경고한다.

## 대안과 경계

| 대안 | 고를 때 |
|---|---|
| [Redis 캐시](redis-cache.md) | 응답이 아니라 계산 결과를 서버 사이에서 공유한다. 무효화를 코드로 통제한다. |

| 사전 생성(정적 사이트) | 내용이 배포 때만 바뀐다. 파일로 만들어 CDN에 올린다. |

## 깊이 있는 활용

- **자산은 해시 URL과 긴 수명.** 빌드 도구가 파일 이름에 내용 해시를 넣게 하고, `Cache-Control: public, max-age=31536000, immutable`을 준다. HTML은 `no-cache`로 두어 새 자산 URL을 바로 받게 한다.
- **개인화 응답은 `private`와 재검증.** `Cache-Control: no-cache, private`로 두면 공유 캐시에는 남지 않고, 브라우저는 재검증으로 본문 전송을 아낀다.
- **API 목록은 짧은 수명과 재검증.** `max-age=0`이나 수 초와 `ETag`, `stale-while-revalidate`를 조합해, 폭주 때 원본에 가는 요청을 줄인다.
- **CDN에는 `s-maxage`.** 브라우저에는 짧게, CDN에는 길게 주고, 배포나 수정 때 CDN 무효화를 부른다.
- **사전 서명 URL과 함께 쓸 때.** 다운로드 URL이 요청마다 달라지면 캐시 키도 달라진다. 공개 자산은 서명 없는 경로와 CDN으로 분리한다([객체 저장소](../storage/object-storage.md)).

## 임시방책의 신호

- 모든 응답에 `no-store, no-cache, must-revalidate`를 붙인다.
- 배포 뒤 옛 JS가 보인다는 신고에 "강력 새로고침하세요"라고 답한다.
- 파일 URL 뒤에 `?t=현재시각`을 붙여 캐시를 매번 우회한다.
- 로그인 사용자의 대시보드 API가 CDN을 거치면서 `Cache-Control`이 없다.
- 캐시 적중률을 한 번도 본 적이 없다.

## 실패 재현

- **개인 정보 섞임.** 스테이징 CDN이나 프록시 캐시 뒤에서 두 사용자로 같은 개인화 URL을 요청해, 두 번째 사용자가 첫 사용자의 응답을 받는지 본다. `private`를 넣고 반복한다.
- **옛 자산.** 긴 `max-age`를 준 고정 이름 파일을 배포로 바꾸고, 브라우저가 옛 파일을 계속 쓰는 것을 확인한다. 해시 URL로 바꿔 반복한다.
- **폭주 흡수.** [k6](../verify/k6.md)로 같은 목록 API에 폭주를 걸어, 캐시 지시어 유무에 따라 원본 요청 수를 비교한다.

## 측정과 검증

- **적중률.** CDN과 프록시의 적중률, 재검증 비율(`304`), 원본 요청 수.
- **지연.** 사용자 쪽 로딩 시간과 첫 바이트 시간(TTFB)을 캐시 적중과 미스로 나눠 본다.
- **정확성.** 응답의 `Cache-Control`과 `Vary`를 엔드포인트별 기대값과 대조하는 자동 테스트를 둔다. 개인화 엔드포인트의 `private` 누락을 CI에서 잡는다.

## 재검토 조건

- 적중률이 낮다. 캐시 키(`Vary`, 쿼리 문자열)를 다시 본다.
- 무효화가 잦아 비용이 크다. 해시 URL과 짧은 수명으로 바꾼다.
