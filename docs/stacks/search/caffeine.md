# Caffeine

확인: 2026-09-27, Caffeine 3.3.0 기준 저장소 위키(ben-manes/caffeine.wiki) 기준.

## 요약

Caffeine은 JVM 프로세스 안의 메모리 캐시 라이브러리다.
네트워크 왕복 없이 나노초 단위로 답하고, W-TinyLFU 퇴출 정책으로 같은 메모리에서 LRU보다 높은 적중률을 노린다.
같은 키의 적재를 한 번으로 합치고, 만료 전에 비동기로 새로 고치는 기능이 있어 캐시 쇄도를 구조적으로 줄인다.

## 문제 신호

- 매우 자주 읽히는 작고 변하지 않는 값(설정, 코드표, 권한 규칙, 환율 같은 준정적 데이터)이 있다.
- [Redis 캐시](redis-cache.md)의 왕복 지연마저 요청 지연의 큰 부분이다.
- 인기 키 몇 개가 Redis 노드 하나에 몰린다(핫 키).
- 외부 API 결과를 인스턴스 안에서 잠깐 재사용하면 호출 수가 크게 준다.

## 기준선의 한계

- 매번 DB나 Redis를 부르면 요청마다 네트워크 왕복이 생긴다. 작은 값을 수천 번 읽는 경로에서는 이 왕복이 지배적이다.
- `ConcurrentHashMap`에 직접 담으면 크기 제한, 만료, 퇴출, 통계를 직접 만들어야 하고, 무한히 커지기 쉽다.
- 같은 키를 동시에 여러 스레드가 적재하면 원본 호출이 중복된다.

## 원리

- **W-TinyLFU 퇴출.** LRU는 전체 스캔 같은 부하에서 적중률이 나쁘다. Caffeine은 최근성(작은 창)과 빈도(압축된 스케치)를 함께 보고, 새 항목이 기존 항목보다 자주 쓰일 때만 들여보낸다.
- **원자적 적재.** `cache.get(key, k -> value)`는 없으면 계산해 넣고 있으면 돌려준다. 동기 캐시는 `ConcurrentHashMap`의 `computeIfAbsent`와 같게 동작해, 같은 키의 동시 적재는 하나만 실행되고 나머지는 기다린다.
- **refresh와 만료의 차이.**
  - `expireAfterWrite`가 지나면 항목이 사라져 다음 조회가 적재를 기다린다.
  - `refreshAfterWrite`가 지나면 다음 조회 때 비동기로 새로 고치고, 그동안 옛 값을 준다. 새로 고침이 실패하면 옛 값을 유지한다.
- **새로 고침 중복 제거.** `LoadingCache.refresh(K)`는 진행 중인 새로 고침을 중복 실행하지 않는다.
- **정리는 게으르다.** 만료된 항목을 즉시 지우지 않고, 쓰기 뒤나 가끔 읽기 뒤에 조금씩 정리한다. 제때 정리가 필요하면 `Scheduler`를 지정한다.
- **통계.** `recordStats()`로 적중률, 적재 시간, 퇴출 수를 모은다.

## 가치

Caffeine의 가치는 **가장 가까운 곳에서, 쇄도 없이, 높은 적중률로 답하는 것**이다.

- 네트워크 왕복이 없다. 작은 값을 자주 읽는 경로에서 Redis 왕복만큼 지연이 준다. 얼마나 주는지는 환경에서 잰다.
- 적재 합치기와 비동기 새로 고침으로, 인기 키가 만료되는 순간에도 원본에 요청이 몰리지 않고 사용자는 기다리지 않는다.
- W-TinyLFU가 한 번 읽고 마는 스캔성 접근에 캐시가 오염되지 않게 한다.

그래서 Caffeine이 맞는 상황은 값이 작고, 자주 읽히고, 인스턴스마다 잠깐 다른 값을 봐도 되는 경우다.

## 트레이드오프와 리스크

- **인스턴스마다 다른 값을 본다.** 인스턴스별 캐시라서, 원본이 바뀌면 인스턴스마다 다른 시점에 반영된다. 사용자가 요청마다 다른 인스턴스에 가면 값이 왔다 갔다 할 수 있다.
- **무효화가 전파되지 않는다.** 한 인스턴스에서 지워도 다른 인스턴스에는 남는다. 무효화 전파가 필요하면 메시지(Redis Pub/Sub, `CLIENT TRACKING`)를 따로 둬야 한다.
- **힙 메모리를 쓴다.** 큰 값이나 많은 항목은 GC 부담을 늘린다. 크기 상한을 항목 수(`maximumSize`)나 무게(`maximumWeight`)로 반드시 둔다.
- **재시작하면 비어 있다.** 배포 직후 모든 인스턴스가 동시에 원본을 부른다.
- **적재 함수 안에서 캐시에 쓰면 안 된다.** 위키 FAQ는 원자적 연산 안에서 같은 캐시에 쓰는 재귀 갱신이 `ConcurrentHashMap`에서 허용되지 않아 livelock이나 `IllegalStateException`이 난다고 적는다.
- **느린 적재가 같은 키의 조회를 모두 막는다.** 동기 캐시에서 적재가 오래 걸리면 그 키를 조회하는 모든 스레드가 기다린다.
- **새로 고침 실패가 조용하다.** 예외가 로그로만 남고 옛 값이 계속 나간다. 원본 장애가 길면 오래된 값을 모른 채 계속 준다.

## 대안과 경계

| 대안 | 고를 때 |
|---|---|
| [Redis 캐시](redis-cache.md) | 인스턴스들이 같은 값을 봐야 하고, 무효화가 즉시 모두에게 반영돼야 한다. 값이 커서 힙에 두기 어렵다. |
| 2단 캐시(Caffeine + Redis) | 핫 키를 인스턴스 안에서 흡수하고, 나머지는 Redis가 공유한다. 무효화 경로가 두 겹이 된다. |
| `ConcurrentHashMap` | 크기가 고정되고 절대 바뀌지 않는 참조 데이터(시작 시 적재). |
| Spring Cache 추상화 | 캐시 구현을 바꿔 끼우고 선언적으로 쓴다. Caffeine을 구현체로 쓸 수 있다. 단, 추상화가 refresh 같은 Caffeine 고유 기능을 가린다. |

## 깊이 있는 활용

- **refresh와 expire를 함께 둔다.** 위키 예시처럼 `refreshAfterWrite(1분)`과 `expireAfterWrite(5분)`을 같이 두면, 1분 뒤부터는 조회 때 백그라운드에서 갱신하고, 5분 동안 조회가 없던 항목은 사라진다. 인기 키는 절대 만료 대기를 겪지 않는다.
- **새로 고침을 원본 장애 대비로 쓴다.** 원본이 잠깐 죽어도 옛 값으로 계속 돈다. 마지막 성공 적재 시각을 기록해 너무 오래되면 경보를 건다.
- **비동기 캐시로 느린 적재를 격리한다.** `AsyncLoadingCache`는 `CompletableFuture`를 저장하므로, 조회 스레드가 적재 완료를 막혀서 기다리지 않는다. 적재용 실행기를 따로 둬 공용 `ForkJoinPool`을 보호한다.
- **대량 적재로 왕복을 줄인다.** `loadAll`/`asyncLoadAll`을 구현해 여러 키를 한 번의 원본 호출로 가져온다. 위키는 그룹 단위로 값이 나오는 경우 요청하지 않은 키까지 함께 적재할 수 있다고 설명한다.
- **무게로 크기를 잰다.** 값 크기가 제각각이면 `maximumWeight`와 `weigher`로 메모리 기준 상한을 둔다.
- **무효화 메시지를 붙인다.** 원본이 바뀌면 이벤트(Redis Pub/Sub, 메시지 브로커)로 각 인스턴스가 해당 키를 지우게 한다. 메시지가 유실돼도 `expireAfterWrite`가 상한이 된다.
- **적중률을 지표로 내보낸다.** `recordStats()`와 Micrometer 연동으로 적중률, 적재 시간, 퇴출 수를 본다.

## 임시방책의 신호

- `static Map`에 계속 넣기만 하는 "캐시"가 있다. 메모리가 늘다가 OOM이 난다.
- 인스턴스별 캐시 때문에 값이 어긋나자 TTL을 몇 초로 줄여 적중률을 없앤다.
- 적재 함수 안에서 다른 키를 같은 캐시에 넣는다.
- 캐시 만료 순간 DB에 요청이 몰리자 인스턴스 수를 늘린다.
- 사용자별 데이터를 인스턴스 캐시에 넣고 로그아웃이나 권한 변경 때 지우지 않는다.

## 실패 재현

- **쇄도 비교.** 같은 키에 동시 요청 수백 개를 보내면서 만료시킨다. `ConcurrentHashMap` + 수동 적재, `expireAfterWrite`만, `refreshAfterWrite` 추가 세 경우에 원본 호출 수와 요청 지연 p99를 비교한다.
- **인스턴스 간 불일치.** 인스턴스 둘을 띄우고 원본을 바꾼 뒤, 두 인스턴스가 서로 다른 값을 주는 시간 창을 잰다. 무효화 메시지를 넣고 반복한다.
- **원본 장애 중 새로 고침.** 원본을 멈추고 `refreshAfterWrite` 이후 조회가 옛 값을 계속 주는지, 로그와 지표에 드러나는지 본다.
- **재귀 적재.** 적재 함수 안에서 같은 캐시에 쓰게 해서 예외가 나는 것을 테스트로 고정한다.
- **스캔 오염.** 인기 키 집합을 반복 조회하는 중에 한 번씩만 읽히는 키를 대량으로 흘려, LRU 구현과 Caffeine의 적중률을 비교한다.

## 측정과 검증

- **적중률과 원본 호출 수.** `CacheStats`의 `hitRate`, `loadCount`, 평균 적재 시간을 본다. 인스턴스별로 보고 합친다.
- **지연.** 캐시 조회를 포함한 요청 지연 p50, p99를 Redis만 쓸 때와 비교한다.
- **메모리와 GC.** 캐시 크기에 따른 힙 사용량과 GC 정지 시간을 JFR이나 GC 로그로 본다.
- **신선도.** 원본 변경부터 모든 인스턴스가 새 값을 주기까지의 최대 시간을 잰다. 이 값이 허용 한도 안에 있어야 한다.
- 캐시 정책 비교는 Caffeine 저장소의 시뮬레이터로 실제 접근 기록(trace)을 재생해 정책별 적중률을 미리 볼 수 있다.

## 재검토 조건

- 인스턴스 간 값 불일치가 사용자에게 보이는 문제가 됐다. 공유 캐시나 무효화 전파를 강화한다.
- 캐시 크기가 힙과 GC에 부담을 준다.
- 값이 거의 재사용되지 않아 적중률이 낮다. 캐시를 걷어낸다.
