# pgvector

확인: 2026-09-27, pgvector v0.8.6 README 기준.

## 요약

pgvector는 PostgreSQL에 벡터 타입과 거리 연산, 근사 최근접 이웃(ANN) 인덱스(HNSW, IVFFlat)를 더하는 확장이다.
임베딩을 업무 데이터와 같은 테이블에 두므로, 권한·필터·트랜잭션·백업을 RDB 그대로 쓰면서 의미 검색을 한다.
기본은 정확 검색이고, 인덱스를 추가하면 속도를 얻는 대신 일부 결과를 놓칠 수 있다. 이 근사가 만드는 결과 차이를 이해하는 것이 핵심이다.

## 문제 신호

- 키워드가 일치하지 않아도 뜻이 비슷한 문서를 찾아야 한다(RAG의 근거 검색, 유사 상품, 중복 질문 찾기).
- 이미 PostgreSQL을 쓰고 있고, 벡터 수가 수백만 건 이하다.
- 검색 결과를 권한, 테넌트, 카테고리, 삭제 여부로 반드시 걸러야 한다.
- 별도 벡터 DB를 들이면 원본과의 동기화가 새 문제가 된다.

## 기준선의 한계

- 키워드 검색은 표현이 다르면 찾지 못한다("환불"과 "돈 돌려받기").
- 벡터를 애플리케이션 메모리에 두고 전수 비교하면 데이터가 늘면 느려지고, 인스턴스마다 복사본을 가진다.
- 별도 벡터 DB는 원본 DB와 이중 쓰기, 삭제·권한 동기화가 필요하다.

## 원리

- **정확 검색이 기본이다.** 인덱스 없이 `ORDER BY embedding <-> :q LIMIT k`는 전수 비교로 정확한 결과(재현율 100%)를 준다.
- **근사 인덱스는 결과를 바꾼다.** README는 일반 인덱스와 달리 근사 인덱스를 추가하면 질의 결과가 달라진다고 명시한다.
- **HNSW.** 다층 그래프 인덱스다. IVFFlat보다 속도-재현율 균형이 좋지만, 만들기 느리고 메모리를 더 쓴다. 기본값은 `m=16`, `ef_construction=64`, 질의 때 `hnsw.ef_search=40`이다.
- **IVFFlat.** 벡터를 목록(list)으로 군집화하고 가까운 목록 몇 개(`probes`)만 본다. 데이터가 적을 때 만들면 결과가 줄어든다.
- **필터는 인덱스 스캔 뒤에 적용된다.** README의 예시로, 조건이 행의 10%에 맞으면 기본 `ef_search` 40에서 평균 4행만 남는다. 0.8.0부터 반복 인덱스 스캔(`hnsw.iterative_scan`)이 결과가 찰 때까지 인덱스를 더 훑는다.
- **차원과 타입 상한.** 인덱스 가능한 차원은 `vector` 2,000, `halfvec` 4,000, `bit` 64,000이다. `sparsevec`는 0이 아닌 원소 1,000개까지다.
- **거리 함수마다 인덱스가 따로다.** L2, 내적, 코사인 등 연산자 클래스별로 인덱스를 만든다. 질의의 연산자와 인덱스가 맞아야 인덱스를 쓴다.

## 가치

pgvector의 가치는 **의미 검색을 업무 데이터의 규칙 안으로 들여오는 것**이다.

- 권한, 테넌트, 삭제 여부 필터가 같은 쿼리의 `WHERE`다. 원본과 색인이 어긋날 일이 없다.
- 임베딩 갱신이 업무 행 갱신과 같은 트랜잭션이다. [Outbox](../async/outbox-cdc.md) 같은 동기화 장치가 필요 없다.
- 전문 검색(`tsvector`)과 한 DB에서 합쳐 하이브리드 검색을 한다.
- 백업, 복제, 모니터링, 접근 제어가 이미 있다.

그래서 pgvector가 맞는 상황은 벡터 수가 단일 PostgreSQL이 감당하는 범위이고, 필터와 정합성이 속도보다 중요한 경우다.

## 트레이드오프와 리스크

- **필터가 결과를 줄인다.** 근사 인덱스는 후보를 먼저 고르고 필터를 나중에 건다. 선택적인 필터(특정 사용자의 문서만)와 함께 쓰면 결과가 비거나 줄어든다.
- **재현율이 설정과 데이터에 따라 조용히 변한다.** `ef_search`, 죽은 행, 필터 조건이 결과 수와 재현율을 바꾼다. 인덱스를 추가한 날부터 결과가 달라진다.
- **테넌트끼리 영향을 준다.** README는 테넌트가 근사 인덱스를 공유하면 한 테넌트의 벡터가 다른 테넌트의 재현율과 속도에 영향을 준다고 적는다.
- **인덱스 생성이 무겁다.** HNSW는 그래프가 `maintenance_work_mem`에 들어갈 때 훨씬 빨리 만들어진다. 대량 적재 뒤 인덱스를 만들고, 운영 중 생성은 [무중단 인덱스 생성](../state/schema-migration.md)으로 한다.
- **DB 자원을 검색이 쓴다.** 벡터 검색 CPU와 메모리가 업무 쿼리와 같은 서버를 쓴다. 규모가 커지면 읽기 복제본으로 나눠야 한다.
- **차원 상한.** 3,072차원 같은 큰 임베딩은 `vector`로 인덱싱할 수 없다. `halfvec`나 차원 축소, 부분 벡터 인덱스가 필요하다.
- **NULL과 영벡터는 색인되지 않는다.** 코사인 거리에서 영벡터도 빠진다. 임베딩 생성 실패로 비어 있는 행은 조용히 검색에서 사라진다.

## 대안과 경계

| 대안 | 고를 때 |
|---|---|
| 정확 검색(인덱스 없음) | 벡터가 수만 건 이하이거나, 필터가 강해서 후보가 적다. 재현율 100%다. |
| [Elasticsearch](elasticsearch.md) | 키워드 검색 품질(형태소 분석, 관련도 튜닝)이 중요하고 벡터 검색도 함께 한다. 원본과의 동기화 비용을 감수한다. |
| 전용 벡터 DB(Qdrant, Milvus 등) | 벡터 수가 수억 건 단위이거나, 필터 결합 ANN과 양자화가 더 성숙한 도구가 필요하다. (미검증: 이 조사에서는 비교하지 않았다.) |
| [하이브리드 검색과 리랭킹](hybrid-rerank.md) | 키워드와 의미 검색 결과를 합친다. pgvector와 전문 검색으로 한 DB 안에서 할 수 있다. |

## 깊이 있는 활용

- **필터가 강하면 먼저 B-tree로 좁힌다.** README는 적은 비율의 행에 맞는 조건이면 필터 컬럼 인덱스로 좁히고 정확 검색을 하는 편이 좋다고 권한다. 사용자별 문서 검색이 대표적이다.
- **테넌트는 파티션으로 나눈다.** 목록 파티셔닝으로 테넌트마다 작은 인덱스를 두면 필터 문제와 테넌트 간 간섭이 함께 사라진다. 값 종류가 적은 필터는 부분 인덱스(`WHERE category_id = 123`)를 쓴다.
- **필터가 약하면 반복 스캔을 켠다.** `hnsw.iterative_scan = relaxed_order`로 재현율을 높이고, 순서가 중요하면 `MATERIALIZED` CTE로 다시 정렬한다. `hnsw.max_scan_tuples`(기본 20,000)가 훑는 양의 상한이다.
- **`ef_search`는 질의마다 조정한다.** `SET LOCAL hnsw.ef_search`로 정확도가 중요한 질의만 크게 한다.
- **양자화로 인덱스를 줄이고 원본으로 다시 순위를 매긴다.** `halfvec` 인덱스나 이진 양자화로 인덱스 크기를 줄여 메모리에 넣고, 후보를 넉넉히 뽑은 뒤 원래 정밀도의 벡터로 다시 정렬한다.
- **거리 함수를 임베딩 모델에 맞춘다.** 정규화된 임베딩이면 내적과 코사인이 같은 순서를 주고 내적이 싸다. 모델 문서가 권하는 거리를 쓰고, 인덱스 연산자 클래스를 일치시킨다.
- **임베딩에 모델 버전을 붙인다.** 모델을 바꾸면 벡터 공간이 달라져 옛 벡터와 비교할 수 없다. `embedding_model` 컬럼을 두고, 새 모델 벡터를 새 컬럼에 채운 뒤 전환한다.
- **대량 적재 후 인덱스를 만든다.** `COPY`로 적재하고 나서 `maintenance_work_mem`을 넉넉히 주고 인덱스를 만든다.

## 임시방책의 신호

- 필터와 함께 쓴 근사 검색이 빈 결과를 내자 `LIMIT`을 크게 올린다.
- 권한 필터를 검색 뒤 애플리케이션에서 건다. 상위 k개가 모두 걸러져 결과가 빈다.
- 모델을 바꾸고 기존 벡터를 다시 계산하지 않는다.
- 재현율을 재지 않고 인덱스를 추가한 뒤 "빨라졌다"로 끝낸다.
- 임베딩 생성 실패를 NULL로 두고 모니터링하지 않는다.

## 실패 재현

- **필터 결과 부족.** 행의 1~10%에만 맞는 조건으로 HNSW 검색을 하고 반환 행 수를 센다. 반복 스캔, 부분 인덱스, 파티션, B-tree 선필터 각각과 비교한다.
- **재현율 저하.** 같은 질의 집합을 정확 검색과 근사 검색으로 돌려 겹치는 비율(recall@k)을 `ef_search` 값별로 잰다.
- **테넌트 간섭.** 큰 테넌트와 작은 테넌트를 한 인덱스에 두고, 작은 테넌트 질의의 재현율을 파티션 분리 전후로 비교한다.
- **죽은 행.** 대량 갱신 뒤 VACUUM 전후의 결과 수와 지연을 비교한다.
- **NULL 누락.** 임베딩이 NULL인 행을 섞고 검색에서 빠지는 것을 확인한다.

## 측정과 검증

- **재현율은 정확 검색을 정답으로 잰다.** 실제 질의에서 정확 검색과 근사 검색의 상위 k가 겹치는 비율을 필터 조건별, 테넌트 크기별로 본다. 평균보다 재현율이 낮은 질의의 비율을 본다.
- **검색 품질은 따로 잰다.** 재현율은 인덱스가 정확 검색을 얼마나 흉내 내는지다. 사용자가 원하는 문서를 찾는지는 [LLM 평가](../rag/llm-evaluation.md)와 [하이브리드 검색](hybrid-rerank.md)의 평가셋으로 잰다.
- **지연과 자원.** 질의 p50, p99를 `EXPLAIN (ANALYZE, BUFFERS)`와 함께 본다. 인덱스 크기(`pg_relation_size`)가 메모리에 들어가는지 확인한다.
- **적재 비용.** 인덱스 생성 시간과 갱신 처리량을 데이터 크기별로 잰다.

## 재검토 조건

- 벡터 수가 늘어 단일 PostgreSQL의 메모리나 CPU로 지연 목표를 못 맞춘다.
- 필터 결합 검색의 재현율 문제가 파티션이나 반복 스캔으로 해결되지 않는다.
- 키워드 검색 품질이 더 중요해져 검색 엔진으로 옮긴다.
