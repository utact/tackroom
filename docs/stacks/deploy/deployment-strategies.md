# 배포 전략

확인: 2026-09-28, Kubernetes 문서(kubernetes/website, main)와 Argo Rollouts 문서(master) 기준.

## 요약

배포 전략은 옛 버전을 새 버전으로 바꾸는 동안 트래픽과 위험을 어떻게 나눌지 정하는 방식이다.
롤링 업데이트는 인스턴스를 조금씩 바꾸고, 블루그린은 새 버전을 통째로 띄운 뒤 트래픽을 한 번에 넘기고, 카나리는 일부 트래픽만 새 버전에 보내 지표를 본다.
어느 전략이든 **옛 버전과 새 버전이 잠시 함께 돈다.** 이 공존을 견디도록 애플리케이션과 스키마를 설계하는 것이 전략 선택보다 먼저다.

## 문제 신호

- 배포할 때마다 몇 초~몇 분의 오류나 다운타임이 생긴다.
- 배포 직후 장애가 나면 되돌리는 데 오래 걸린다.
- 새 버전의 문제가 모든 사용자에게 한꺼번에 드러난다.
- 배포를 사람이 지켜보며 로그와 대시보드로 성공을 판단한다.

## 기준선의 한계

기준선은 멈추고 교체하는 배포(Recreate)다.

- 옛 버전을 모두 내린 뒤 새 버전을 띄우므로 두 버전이 공존하지 않는다. 대신 그 사이가 다운타임이다.
- 되돌리기도 같은 절차라 다시 다운타임이 생긴다.
- 서버가 하나이고 정해진 점검 시간이 있으면 충분할 수 있다. 무중단이 요구되면 여기서 막힌다.

## 원리

- **롤링 업데이트.** Kubernetes Deployment의 기본 전략으로, `maxUnavailable`과 `maxSurge`(기본 각 25%) 안에서 파드를 바꾼다. readiness를 통과한 파드만 트래픽을 받는다.
- **진행 기한.** `progressDeadlineSeconds`(기본 600초) 안에 진행이 없으면 `ProgressDeadlineExceeded`로 보고한다. 보고만 할 뿐, Deployment가 스스로 되돌리지는 않는다.
- **블루그린.** 새 버전을 옛 버전 옆에 모두 띄우고, 준비되면 서비스의 선택자를 바꿔 트래픽을 한 번에 넘긴다.
  - Argo Rollouts는 미리보기 서비스로 새 버전을 먼저 시험하게 한다.
  - 전환 뒤 `scaleDownDelaySeconds`(기본 30초)만큼 옛 버전을 남긴다. 노드의 iptables 갱신이 퍼지는 동안 옛 파드로 가는 요청을 받기 위해서다.
- **카나리.** 새 버전에 트래픽을 10%, 33%처럼 단계별로 늘리고, 단계마다 지표를 분석해 자동으로 승격하거나 중단한다. 세밀한 비율과 헤더 기반 분할은 인그레스나 서비스 메시 같은 트래픽 관리자가 있어야 한다.
- **공존 조건.** Argo Rollouts 문서는 두 버전이 동시에 돌 수 있는지 먼저 확인하라고 한다. 공유 파일에 쓰는 앱과 큐 소비자는 코드 수정 없이는 잘 맞지 않는다고 적는다.

## 가치

배포 전략의 가치는 **배포와 위험 노출을 분리하는 것**이다.

- 롤링은 추가 자원을 조금만 쓰고 다운타임을 없앤다.
- 블루그린은 되돌리기가 트래픽 전환 한 번이라 빠르다. 전환 전에 실제 환경에서 새 버전을 시험한다.
- 카나리는 문제가 일부 사용자에게만 드러나고, 지표로 자동 중단하면 사람이 지켜보지 않아도 된다.

## 트레이드오프와 리스크

- **두 버전의 공존.** 롤링과 카나리는 옛 버전과 새 버전이 같은 DB, 같은 큐, 같은 캐시를 동시에 쓴다. 스키마나 메시지 형식이 호환되지 않으면 배포 중에 깨진다.
- **블루그린의 비용과 폭발 반경.** 전환 동안 자원이 두 배 든다. 전환은 전부 아니면 전무라, 전환 뒤 드러난 문제는 모든 사용자에게 간다.
- **긴 연결.** WebSocket, SSE, gRPC 스트림은 트래픽을 넘겨도 옛 인스턴스에 붙어 있다. 옛 버전을 내리면 한꺼번에 끊기고 재연결이 몰린다.
- **되돌리기의 한계.** 데이터를 바꾼 배포(스키마 삭제, 형식 변환)는 트래픽을 되돌려도 원상태가 되지 않는다.
- **카나리의 판단 근거.** 트래픽이 적으면 단계마다 모이는 표본이 작아 지표로 판단하기 어렵다. 판단 지표가 없으면 카나리는 느린 롤링일 뿐이다.

## 대안과 경계

| 대안 | 고를 때 |
|---|---|
| Recreate | 두 버전이 절대 공존하면 안 되고, 점검 시간을 허용한다. |
| [기능 플래그](feature-flags.md) | 배포와 기능 공개를 분리하고 싶다. 사용자 단위로 켜고 끈다. |
| 섀도 트래픽 | 실제 요청을 복제해 새 버전에 보내되 응답은 버린다. 부작용이 없는 읽기 경로에 맞다. |
| 서버리스 버전 분할 | 플랫폼이 버전별 트래픽 비율을 제공한다. |

## 깊이 있는 활용

- **스키마는 확장 → 이행 → 축소로 바꾼다.** 새 컬럼을 먼저 추가하고(두 버전이 모두 동작), 코드를 배포하고, 옛 컬럼을 다음 배포에서 지운다([Flyway와 무중단 스키마 변경](../state/schema-migration.md)). 한 배포에 추가와 삭제를 함께 넣지 않는다.
- **메시지와 API도 같은 규칙.** 새 필드는 선택으로 추가하고, 소비자가 모두 새 버전이 된 뒤에 필수로 바꾼다.
- **종료를 우아하게.** readiness를 먼저 내리고, 진행 중 요청을 끝낸 뒤 종료한다([Kubernetes](../ops/kubernetes.md)). 긴 연결은 서버가 먼저 재연결을 안내하고, 클라이언트는 무작위 지연으로 재연결한다([WebSocket](../comm/websocket.md)).
- **카나리 판단은 자동으로.** 새 버전과 옛 버전의 오류율과 지연을 같은 기간에 비교하는 분석을 둔다. 문서는 5~15분 안에 성공 여부를 말해 주는 지표를 먼저 갖추라고 권한다.
- **큐 소비자는 따로 다룬다.** 트래픽 분할이 적용되지 않으므로, 소비자를 멱등하게 만들고 메시지 형식 호환을 지킨다. 새 소비 로직은 [기능 플래그](feature-flags.md)로 켠다.

## 임시방책의 신호

- 배포 스크립트가 서버를 멈추고, 파일을 바꾸고, 다시 띄운다. 그 사이의 오류는 "배포 중이라 어쩔 수 없다".
- 블루그린이라며 트래픽만 넘기고, 한 배포에서 컬럼 이름을 바꾼다.
- readiness 없이 배포해, 시작 중인 인스턴스가 요청을 받아 오류를 낸다.
- 배포 후 한 시간 동안 사람이 대시보드를 지켜본다.
- 되돌리기 절차를 문서로만 두고 한 번도 해 보지 않았다.

## 실패 재현

- **공존 깨짐.** 스테이징에서 옛 버전과 새 버전을 동시에 띄우고, 같은 DB에 번갈아 요청을 보낸다. 스키마나 형식 차이로 한쪽이 실패하는지 본다.
- **배포 중 오류.** [k6](../verify/k6.md)로 일정 부하를 걸어 둔 채 배포하고, 배포 구간의 오류 수와 지연을 센다. readiness와 종료 처리를 넣고 반복한다.
- **긴 연결 폭주.** WebSocket 연결 수천 개를 붙인 채 배포해, 재연결 폭주와 서버 부하를 본다.
- **되돌리기.** 일부러 오류를 내는 버전을 배포하고, 감지부터 복구까지 걸린 시간을 잰다.

## 측정과 검증

- **배포 구간의 가용성.** 배포 시작부터 끝까지의 오류율과 p99 지연을 평소 구간과 비교한다. 목표는 차이 없음이다.
- **복구 시간.** 나쁜 배포의 감지 시간과 되돌리기 시간.
- **카나리 비교.** 새 버전과 옛 버전의 오류율 차이. 표본이 작으면 비율 차이의 신뢰구간을 함께 본다([측정 통계](../verify/statistics.md)).
- **배포 빈도와 실패율.** 배포 횟수 대비 되돌린 비율을 추적한다.

## 재검토 조건

- 트래픽이 적어 카나리 판단이 안 된다. 블루그린과 기능 플래그로 바꾼다.
- 두 버전 공존이 계속 문제를 만든다. 호환 규칙을 먼저 정비하고, 그동안 Recreate나 블루그린을 쓴다.
