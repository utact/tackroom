# 기능 플래그

확인: 2026-09-28, OpenFeature 명세(open-feature/spec, main) 기준. 플래그 분류는 Pete Hodgson의 "Feature Toggles"(martinfowler.com)를 검색 요약으로 확인했다.

## 요약

기능 플래그는 코드 경로를 배포가 아니라 실행 중 설정으로 켜고 끄는 장치다.
배포(코드를 서버에 올림)와 공개(사용자가 기능을 봄)를 분리해, 미완성 코드를 꺼 둔 채 배포하거나 일부 사용자에게만 켤 수 있다.
대가는 조건 분기와 설정 상태가 늘어나는 것이다. 플래그마다 수명과 주인을 정하지 않으면 코드에 죽은 분기가 쌓인다.

## 문제 신호

- 긴 기능 브랜치가 병합 충돌과 큰 배포를 만든다.
- 새 기능을 내부 사용자나 일부 고객에게 먼저 켜고 싶다.
- 장애 때 무거운 기능(추천, 외부 연동)을 배포 없이 끄고 싶다.
- 배포를 되돌리는 것 말고는 문제를 멈출 방법이 없다.

## 기준선의 한계

기준선은 배포로 기능을 켜고 끄는 것이다.

- 켜고 끄려면 빌드와 배포가 필요해 몇 분~몇십 분이 걸린다.
- 일부 사용자에게만 켤 수 없다.
- 환경 변수로 분기하는 방법도 재시작이 필요하고, 사용자 단위 분기가 안 된다.

## 원리

- **평가.** 코드는 플래그 키, 기본값, 평가 문맥(사용자 ID, 조직, 지역)을 넘겨 값을 받는다. 규칙(비율, 대상 목록)은 코드 밖 설정에 있다.
- **기본값이 안전장치다.** OpenFeature 명세는 평가 함수가 예외를 던지지 말고, 비정상 상황에서는 항상 기본값을 돌려주라고 요구한다. 플래그 서비스가 죽어도 애플리케이션은 기본값으로 돈다.
- **공급자 분리.** OpenFeature는 평가 API와 공급자(벤더, 자체 구현)를 분리해, 코드를 바꾸지 않고 플래그 저장소를 바꾼다.
- **평가 상세.** 값과 함께 이유(대상 일치, 비율, 기본값, 오류)와 오류 코드를 돌려줄 수 있다. 어떤 사용자가 왜 그 값을 받았는지 추적하는 근거다.
- **플래그 분류.** Hodgson은 수명과 동적 정도로 네 가지를 나눈다.
  - 공개 플래그: 미완성 기능을 숨긴다. 며칠~몇 주 산다.
  - 실험 플래그: A/B 시험용이다. 사용자마다 다르게 평가된다.
  - 운영 플래그: 장애 때 기능을 끄는 스위치다. 오래 살 수 있다.
  - 권한 플래그: 요금제나 사용자 집단별로 기능을 연다. 사실상 영구적이다.

## 가치

기능 플래그의 가치는 **공개 결정을 배포에서 떼어 내 몇 초 안에 되돌릴 수 있게 하는 것**이다.

- 코드는 작게 자주 병합하고, 미완성 기능은 꺼 둔다.
- 비율을 조금씩 늘려 카나리와 비슷한 효과를 사용자 단위로 얻는다. 트래픽 관리자가 없어도 된다.
- 큐 소비자처럼 트래픽 분할이 안 되는 곳에서도 새 로직을 점진적으로 켠다.

- **학습 실험.** 한 기능을 사용자 일부에 공개하고 같은 사용자의 배정이 유지되는지 본다. 플래그 서비스 장애와 즉시 끄기를 시험하고, 코드 배포·기능 공개·데이터 복구가 별개임을 확인한다.

## 트레이드오프와 리스크

- **플래그 부채.** 켜진 채 방치된 공개 플래그는 죽은 분기다. 조합이 늘어 시험할 경우의 수가 지수적으로 는다.
- **분류 혼동.** 권한 플래그와 공개 플래그를 같은 방식으로 관리하면, 지워야 할 것과 남겨야 할 것이 섞인다.
- **새 의존성.** 원격 플래그 서비스가 느려지면 모든 요청이 느려진다. 캐시와 기본값 설계가 필요하다.
- **일관성.** 한 요청 안에서 같은 플래그를 두 번 평가해 값이 바뀌거나, 여러 서비스가 다른 값을 보면 반쯤 켜진 상태가 된다.
- **데이터 호환.** 플래그를 켜고 끄는 것은 쉽지만, 켜진 동안 새 형식으로 쓴 데이터는 끈 뒤에도 남는다.

## 대안과 경계

| 대안 | 고를 때 |
|---|---|
| [배포 전략](deployment-strategies.md)의 카나리 | 인스턴스 단위로 새 버전 전체를 시험한다. 코드에 분기를 넣지 않는다. |
| 환경 변수 설정 | 재시작으로 바꿔도 되고, 사용자 단위 분기가 필요 없다. |
| 권한 시스템 | 요금제와 역할에 따른 영구적 접근 제어다. 플래그 도구보다 권한 모델이 맞다. |
| A/B 시험 플랫폼 | 통계 분석과 실험 설계까지 필요하다. |

## 깊이 있는 활용

- **플래그마다 주인과 만료일을 둔다.** 공개 플래그는 만든 날 제거 작업도 함께 만든다. 만료가 지난 플래그를 CI에서 경고한다.
- **평가는 경계에서 한 번.** 요청 진입점에서 평가해 결과를 요청 문맥에 싣고, 안쪽 코드는 그 값을 쓴다. 한 요청 안의 값이 바뀌지 않는다.
- **비율은 안정적인 키로 나눈다.** 사용자 ID의 해시로 나누면 같은 사용자는 늘 같은 값을 받는다. 비율을 늘려도 이미 켜진 사용자는 켜진 채로 남는다.
- **운영 플래그는 끄는 방향이 안전하게.** 끄면 기능이 줄어들 뿐 오류가 나지 않게 설계한다. 장애 대응 문서에 플래그 이름을 적어 둔다.
- **평가 결과를 관측한다.** 플래그 값과 이유를 트레이스 속성이나 로그에 남겨, 오류율을 플래그 값별로 나눠 본다([OpenTelemetry](../ops/opentelemetry.md)).

## 임시방책의 신호

- `if (user.email.endsWith("@우리회사.com"))` 같은 하드코딩 분기가 코드 곳곳에 있다.
- 플래그 서비스 호출이 실패하면 예외가 요청을 실패시킨다.
- 1년 전 공개 플래그가 켜진 채 남아 있고, 끄면 무엇이 깨질지 아무도 모른다.
- 플래그를 켜는 것만 시험하고, 끈 상태와 전환 중 상태는 시험하지 않는다.

## 실패 재현

- **플래그 서비스 장애.** [Toxiproxy](../verify/toxiproxy.md)로 플래그 서비스를 끊거나 늦춘다. 요청이 기본값으로 계속 처리되는지, 지연이 늘지 않는지 본다.
- **요청 중 전환.** 긴 요청이 도는 동안 플래그를 바꿔, 한 요청 안에서 값이 섞이는지 본다.
- **양방향 호환.** 플래그를 켜서 새 형식 데이터를 쓴 뒤 끄고, 옛 경로가 그 데이터를 읽는지 본다.

## 측정과 검증

- **플래그 수와 나이.** 종류별 활성 플래그 수와 만료가 지난 수를 추적한다.
- **평가 지연과 실패율.** 플래그 평가 시간, 기본값으로 떨어진 비율.
- **플래그별 결과.** 켠 집단과 끈 집단의 오류율과 지연을 비교한다. 실험 플래그라면 표본 크기와 신뢰구간을 함께 본다([측정 통계](../verify/statistics.md)).

## 재검토 조건

- 플래그가 너무 많아 조합 시험이 불가능하다. 제거를 우선하고, 새 플래그 추가에 승인 절차를 둔다.
- 대부분이 권한 플래그다. 권한 모델로 옮긴다.
