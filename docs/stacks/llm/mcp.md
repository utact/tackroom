# MCP

확인: 2026-09-29 재검토. 최초 조사는 2026-09-28, Model Context Protocol 명세 2026-07-28 판(modelcontextprotocol/modelcontextprotocol, main) 기준.

## 요약

MCP(Model Context Protocol)는 LLM 애플리케이션(클라이언트)이 외부 도구, 자료, 프롬프트를 제공하는 서버에 붙는 표준 프로토콜이다.
도구를 한 번 MCP 서버로 만들면 MCP를 지원하는 어느 에이전트에서도 쓸 수 있다. 에이전트마다 통합 코드를 다시 짜지 않아도 된다.
대가는 **신뢰할 수 없는 코드와 문서가 에이전트의 판단 안으로 들어오는 새 경계**다. 권한, 인증, 사람 승인을 설계해야 한다.

## 문제 신호

- 사내 시스템(티켓, 문서, DB 조회)을 여러 AI 도구(IDE, 채팅, 사내 에이전트)에서 쓰게 해야 한다.
- 에이전트마다 같은 도구의 통합 코드를 따로 유지한다.
- 외부 서비스가 제공하는 도구를 우리 에이전트에 붙이고 싶다.

## 기준선의 한계

기준선은 애플리케이션 안에서 LLM API의 도구 호출(function calling)로 도구를 직접 정의하는 것이다.

- 에이전트 하나라면 이것이 가장 단순하고 충분하다.
- 에이전트나 AI 도구가 여럿이면 같은 통합을 여러 번 만든다.
- 다른 조직이 만든 도구를 가져다 쓸 표준 방법이 없다.

## 원리

- **서버가 제공하는 것.** 도구(모델이 호출하는 함수), 자원(읽을 자료), 프롬프트(사용자가 고르는 템플릿)다.
- **전송.** 두 가지다.
  - stdio: 클라이언트가 서버를 하위 프로세스로 띄우고 표준 입출력으로 JSON-RPC를 주고받는다. 서버는 `stdout`에 MCP 메시지 외의 것을 쓰면 안 된다.
  - Streamable HTTP: 원격 서버에 HTTP로 붙는다.
- **2026-07-28 판의 주요 변화.** 프로토콜이 상태 없이 바뀌었다.
  - 세션과 `Mcp-Session-Id`, 초기화 핸드셰이크가 없어지고, 요청마다 버전과 능력을 싣는다. 대신 `server/discover`로 능력을 알린다.
  - 스트림 재개와 재전달이 없어져, 끊기면 요청을 새 ID로 다시 보내야 한다.
  - 목록 결과에 캐시 수명(`ttlMs`)과 공유 캐시 허용 범위(`cacheScope`)가 붙고, 도구 목록은 결정적 순서로 반환하라고 권한다. 클라이언트 캐시와 LLM 프롬프트 캐시 적중을 위해서다.
  - 서버가 먼저 보내던 요청(`sampling/createMessage`, `elicitation/create`, `roots/list`)은 다중 왕복 요청(MRTR)으로 바뀌었다. 서버가 `input_required` 결과로 필요한 정보를 알리면, 클라이언트가 답을 실어 원래 요청을 다시 보낸다. 사람 확인도 이 흐름을 탄다.
  - 오래 걸리는 작업(tasks)은 핵심 명세에서 공식 확장으로 빠졌고, Roots·Sampling·Logging은 폐기 예정이다. 새 구현은 이 기능에 기대지 않는다.
- **사람 승인.** 명세는 안전을 위해 도구 호출을 거부할 수 있는 사람이 항상 개입해야 한다고 권한다. 도구 설명(annotations)은 신뢰하는 서버가 아니면 믿지 말라고 한다.
- **인가.** 원격 서버는 OAuth 기반 인가를 쓴다.
  - 서버는 토큰이 자기를 대상(audience)으로 발급됐는지 검증해야 한다.
  - 받은 토큰을 하위 API에 그대로 넘기는 것(token passthrough)은 금지다.
  - 혼동된 대리인(confused deputy) 공격을 경고한다.

## 가치

MCP의 가치는 **도구 통합을 한 번 만들어 여러 에이전트에서 쓰게 하는 것**이다.

- 도구 제공자와 에이전트 개발자가 독립적으로 움직인다.
- 에이전트는 도구 목록을 실행 중에 발견해, 코드 변경 없이 능력을 넓힌다.
- 인증과 권한 모델이 표준화되어, 원격 도구에 사용자 권한으로 접근한다.

- **학습 실험.** 프로젝트의 읽기 도구 하나를 MCP로 노출한다. 입력 스키마 오류, 도구 실패와 취소를 시험하고, 연결·도구 발견·권한 검사·업무 실행 중 어느 층이 실패를 책임지는지 설명한다.

## 트레이드오프와 리스크

- **프롬프트 주입.** 도구 결과와 자원 내용은 모델 입력이 된다. 문서 속 "이전 지시를 무시하라" 같은 문장이 모델을 조종할 수 있다.
- **과한 권한.** 쓰기와 삭제가 가능한 도구를 사람 승인 없이 열면, 모델의 오판 하나가 실제 피해가 된다.
- **공급망.** 로컬 stdio 서버는 사용자의 권한으로 도는 임의 코드다. 출처를 확인하지 않은 서버는 설치하지 않는다.
- **컨텍스트 비용.** 도구가 많으면 도구 정의만으로 입력 토큰이 커지고, 모델의 도구 선택이 흐려진다.
- **명세 변화.** 판마다 전송과 상태 모델이 바뀐다(2026-07-28 판은 세션을 없앴다). 클라이언트와 서버의 판 호환을 확인해야 한다.

## 대안과 경계

| 대안 | 고를 때 |
|---|---|
| 애플리케이션 내 도구 호출 | 에이전트가 하나이고, 도구를 공유할 필요가 없다. |
| 일반 REST API | 호출하는 쪽이 사람이 짠 코드다. 모델이 도구를 고를 필요가 없다. |
| [A2A](a2a.md) | 도구가 아니라 다른 에이전트에게 일을 맡긴다. 상대의 내부는 알 필요가 없다. |
| 에이전트 스킬 | 도구보다 절차와 지식을 필요할 때 읽게 한다. |

## 깊이 있는 활용

- **도구는 업무 단위로 작게.** API 엔드포인트를 그대로 옮기지 말고, 모델이 한 번에 목적을 이루는 단위로 만든다. 설명에 언제 쓰고 언제 쓰지 않는지를 쓴다.
- **읽기와 쓰기를 나눈다.** 읽기 도구는 자동 허용, 쓰기 도구는 사람 승인으로 둔다. 되돌릴 수 없는 동작은 확인 단계를 둔다.
- **사용자 권한으로 호출한다.** 원격 서버는 사용자별 토큰으로 하위 API를 부르고, 서버 자신의 관리자 권한을 쓰지 않는다. 토큰은 서버용으로 따로 받는다.
- **결과는 데이터로 다룬다.** 도구 결과 속 지시문을 따르지 않도록 에이전트 쪽에서 구분해 표시하고, 민감한 동작 앞에서 사람 확인을 둔다.
- **관측.** `_meta`의 `traceparent`로 트레이스 문맥을 넘겨 에이전트 호출과 도구 실행을 한 트레이스로 본다([OpenTelemetry](../ops/opentelemetry.md)).

## 임시방책의 신호

- 사내 DB 전체에 쓰기 권한이 있는 "SQL 실행" 도구 하나를 연다.
- 서버가 받은 사용자 토큰을 하위 API에 그대로 넘긴다.
- 인터넷에서 찾은 MCP 서버를 검토 없이 설치한다.
- 도구 수십 개를 한 에이전트에 모두 붙여 어떤 도구를 쓸지 모델이 헤맨다.
- stdio 서버가 디버그 출력을 `stdout`에 찍어 프로토콜이 깨진다.

## 실패 재현

- **프롬프트 주입.** 도구가 돌려주는 문서에 지시문을 심어, 에이전트가 쓰기 도구를 부르려 하는지 본다. 승인 단계가 막는지 확인한다.
- **권한 경계.** 사용자 A의 토큰으로 사용자 B의 자원을 요청해 거부되는지 본다.
- **끊김.** 원격 호출 중 연결을 끊어, 클라이언트가 새 요청으로 다시 보내는지, 부작용 있는 도구가 두 번 실행되지 않는지 본다.

## 측정과 검증

- **도구 선택 정확도.** 평가 과제에서 맞는 도구를 고른 비율과 불필요한 호출 수.
- **승인.** 쓰기 도구 호출 수, 사람 거부율.
- **비용.** 도구 정의가 차지하는 입력 토큰, 도구 호출당 지연.
- **보안.** 주입 시험 세트의 통과율.

## 재검토 조건

- 도구가 한 앱 내부에서만 쓰이고 표준 클라이언트 연결·독립 배포·권한 경계도 필요 없다. 프로토콜 변환과 연결 관리만 남았다면 앱 내 도구 호출로 단순화한다.
- 도구 수가 너무 많다. 도구 검색이나 스킬로 필요할 때만 불러오게 바꾼다.
