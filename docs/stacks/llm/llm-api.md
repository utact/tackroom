# LLM API와 SDK

확인: 2026-10-01 캐시 조건·수치를 각 벤더의 공식 본문에서 재확인했다. SDK와 나머지 API 항목은 2026-09-28 최초 조사 및 2026-09-29 재검토 기준이며, 항목별 확인 범위는 출처에 적었다.

## 요약

OpenAI, Anthropic, Google은 각자 공식 SDK로 LLM API를 제공한다.
세 SDK는 모양이 비슷하지만, **프롬프트 캐시, 구조화 출력, 도구 호출, 일괄 처리, 재시도의 의미가 조금씩 다르다.** 이 차이가 비용과 신뢰성을 가른다.
기술 선택의 핵심은 어느 벤더냐보다, 벤더 기능을 알고 쓰면서도 한 벤더에 묶이지 않게 경계를 두는 것이다.

## 문제 신호

- 요약, 분류, 추출, 대화 기능에 LLM을 붙여야 한다.
- LLM 호출 비용이 예상보다 크고, 대부분이 같은 시스템 프롬프트와 문서의 반복이다.
- 응답 형식이 가끔 깨져 JSON 파싱 오류가 난다.
- 호출이 가끔 오래 걸리거나 429, 5xx로 실패한다.
- 모델을 바꾸거나 벤더를 비교해야 한다.

## 기준선의 한계

기준선은 HTTP 클라이언트로 API를 직접 부르고, 응답 텍스트를 정규식으로 파싱하는 것이다.

- 재시도, 타임아웃, 스트리밍 처리, 오류 분류를 직접 만들어야 한다.
- 자유 텍스트를 파싱하면 형식이 가끔 깨진다.
- 캐시와 일괄 처리 같은 비용 기능을 모르고 지나친다.

## 원리

- **재시도와 타임아웃 기본값.** OpenAI와 Anthropic SDK는 연결 오류, 408, 409, 429, 5xx를 기본 2회 재시도하고, 기본 타임아웃은 10분이다.
  - 타임아웃도 재시도될 수 있지만 `타임아웃 × 3`은 전체 대기의 상한이 아니다. 백오프가 추가되고, HTTPX 같은 전송 계층의 읽기 타임아웃은 청크 사이의 대기 한도다. 사용 중인 SDK·전송 계층 버전을 확인하고, 전체 업무 기한과 취소를 별도로 둔다.
  - OpenAI SDK는 스트림을 읽는 중의 끊김은 재시도하지 않는다.
- **프롬프트 캐시.** 재사용 가능한 입력의 계산을 저장한다. 접두 내용뿐 아니라 모델·도구·요청 설정과 수명이 적중에 영향을 준다. 의미가 비슷한 요청의 결과를 재사용하는 응답 캐시와 구분한다.
  - OpenAI(2026-10-01): GPT-5.6 이후는 최소 1,024토큰이며 암묵적·명시적 캐시를 지원한다. 기본 입력 가격 대비 쓰기 1.25배, 읽기 대부분 0.1배이며 GPT-6.1 Sol은 0.05배다. 이전 세대는 최소 길이·지원 방식이 다르다.
  - Anthropic(2026-10-01, Claude API): `cache_control`로 지점이나 자동 캐시를 설정한다. 쓰기는 5분 수명 1.25배, 1시간 수명 2배다. 읽기는 기본 0.1배, Opus 5.5는 0.05배, Fable 5.1·Mythos 5.1은 0.025배다. 적중 시 수명이 갱신된다.
  - Anthropic의 최소 길이는 예를 들어 Sonnet 5.5·Opus 5.5가 512토큰, Sonnet 4.6이 1,024토큰, Haiku 4.5가 4,096토큰이다. 최소 길이 미만은 오류 없이 미적중하므로 usage 필드로 확인한다.
  - Google(2026-10-01): Gemini 2.5 이후는 암묵적 캐시가 기본 활성화된다. 최소 길이는 2.5 Flash·Pro가 2,048토큰, 3.8 Flash가 4,096토큰이다. 명시적 캐시는 `generateContent`에서 사용하며 Interactions API는 암묵적 캐시만 지원한다.
- **구조화 출력.** 응답을 JSON 스키마로 제약해, 자유 텍스트를 파싱하지 않는다. Anthropic은 `output_config.format`과 도구의 `strict: true`, Google SDK는 `response_json_schema`, OpenAI는 Structured Outputs를 쓴다.
- **도구 호출.** 모델이 함수 이름과 인자를 JSON으로 내고, 애플리케이션이 실행해 결과를 돌려준다. 실행 루프와 승인은 애플리케이션 몫이다.
- **일괄 처리.** 세 벤더 모두 비동기 일괄 API를 약 50% 가격으로 제공한다. Anthropic은 일괄 하나에 최대 10만 요청이고, 대부분 1시간, 최대 24시간 안에 끝난다. 결과 순서가 보장되지 않아 요청 ID로 맞춘다.
- **API 형태.** OpenAI는 Responses API를 주 API로, Chat Completions를 이전 표준으로 둔다. Google GenAI SDK는 Gemini API와 기업용 플랫폼(구 Vertex AI)에 하나의 SDK로 붙는다.
- **모델 ID.** 모델은 ID로 고정한다. 새 모델은 파라미터와 동작이 바뀌기도 한다(예: 일부 모델에서 사전 채움과 강제 도구 선택이 400 오류가 된다). 모델 교체는 코드 변경처럼 평가를 거친다.

## 가치

공식 SDK의 가치는 **각 벤더의 비용·신뢰성 기능을 검증된 방식으로 바로 쓰는 것**이다.

- 재시도, 타임아웃, 스트리밍, 타입 있는 오류를 직접 만들지 않는다.
- 캐시와 일괄 처리로 같은 품질을 더 싸게 얻는다. 반복 접두어가 큰 작업은 비용이 크게 준다.
- 지원되는 스키마를 사용한 구조화 출력으로 형식 오류를 줄인다. 거절·중단·API 오류와 내용의 사실성은 별도로 처리한다.

- **학습 실험.** 동일한 작은 과제를 스트리밍·구조화 출력·도구 호출로 실행한다. 가짜 서버의 429와 느린 청크로 재시도·전체 기한을 관찰하고, 출력 형식 준수와 내용 정확성을 따로 판정한다.

## 트레이드오프와 리스크

- **벤더 종속.** 캐시 지정, 도구 형식, 구조화 출력 문법이 벤더마다 달라 코드가 벤더에 묶인다.
- **추상화 계층의 손실.** 여러 벤더를 감싸는 라이브러리(LiteLLM, Spring AI 등)는 공통분모만 제공해, 벤더 고유 기능(세밀한 캐시 지정, 사고 설정)을 잃거나 늦게 받는다.
- **숨은 캐시 무효화.** 시스템 프롬프트에 현재 시각이나 요청 ID를 넣거나, 도구 목록 순서가 바뀌면 캐시가 매번 깨진다. 오류가 아니라 비용으로만 드러난다.
- **재시도와 비용.** 긴 생성이 타임아웃 뒤 재시도되면 비용을 두 번 낸다. 부작용 있는 도구 호출은 재시도하면 두 번 실행된다.
- **모델 변화.** 같은 ID라도 벤더 정책(가격, 사용 중단)이 바뀐다. 사용 중단 일정을 추적해야 한다.
- **데이터 처리 조건.** 보관 기간, 학습 사용 여부, 처리 지역이 벤더와 계약마다 다르다.

## 대안과 경계

| 대안 | 고를 때 |
|---|---|
| 다중 벤더 추상화 라이브러리 | 여러 벤더를 자주 바꾸고, 벤더 고유 기능이 중요하지 않다. |
| LLM 게이트웨이 | 키 관리, 사용량 한도, 로깅, 대체 벤더를 여러 팀이 공유한다. |
| [vLLM](../rag/vllm.md) 자체 서빙 | 데이터를 밖으로 보낼 수 없거나, 사용률이 높아 자체 GPU가 싸다. |
| 클라우드 제공 경로(Bedrock, Vertex 등) | 기존 클라우드 계약, IAM, 네트워크 안에서 쓴다. 기능 제공 시점이 다를 수 있다. |

## 깊이 있는 활용

- **얇은 경계를 직접 둔다.** 애플리케이션 코드는 "요약해 줘", "이 스키마로 추출해 줘" 같은 업무 인터페이스만 보고, 그 뒤에서 공식 SDK를 쓴다. 벤더를 바꿀 때 경계 안만 고친다.
- **캐시를 위한 프롬프트 배치.** 도구 정의, 시스템 프롬프트, 공통 문서처럼 변하지 않는 것을 앞에, 질문과 시각을 뒤에 둔다. 응답의 캐시 읽기 토큰(Anthropic은 `usage.cache_read_input_tokens`)을 지표로 올려 적중을 확인한다.
- **급하지 않은 일은 일괄 처리로.** 야간 분류, 평가 실행, 대량 요약은 일괄 API로 보내 비용을 줄인다.
- **재시도는 멱등성과 함께.** 도구 실행은 호출 ID로 중복을 막는다. 요청 단위 타임아웃을 업무 기한에 맞게 줄인다([타임아웃·재시도·멱등 키](../api/timeout-retry-idempotency.md)).
- **사용량을 기록한다.** 요청마다 모델, 입력·출력·캐시 토큰, 지연, 결과를 로그와 트레이스에 남긴다. 기능별 비용을 볼 수 있어야 최적화할 수 있다.
- **모델 교체는 평가로.** 새 모델을 들이기 전에 같은 평가셋으로 품질, 비용, 지연을 비교한다([LLM 평가](../rag/llm-evaluation.md)).

## 임시방책의 신호

- 응답 텍스트에서 `{`부터 `}`까지 잘라 JSON으로 파싱한다.
- 시스템 프롬프트 맨 앞에 현재 시각을 넣는다.
- 429를 받으면 `sleep(1)` 후 무한히 다시 부른다.
- API 키를 코드에 두거나 프런트엔드에서 직접 부른다.
- 모델 ID 대신 "최신" 별칭을 써서, 어느 날 동작이 바뀐다.
- 모든 기능이 같은 비싼 모델과 같은 설정을 쓴다.

## 실패 재현

- **형식 오류.** 같은 추출 요청을 수백 번 보내 자유 텍스트 파싱 실패율을 재고, 구조화 출력으로 반복한다.
- **캐시 무효화.** 시스템 프롬프트에 시각을 넣었을 때와 뺐을 때의 캐시 읽기 토큰을 비교한다.
- **장애와 제한.** [Toxiproxy](../verify/toxiproxy.md)로 지연과 끊김을 넣고, 429를 흉내 내는 가짜 서버로 재시도와 타임아웃 동작을 본다.

## 측정과 검증

- **비용.** 기능별 요청 수, 입력·출력·캐시 토큰, 성공한 결과 하나당 비용.
- **캐시 적중률.** 입력 토큰 중 캐시 읽기의 비율.
- **지연.** 첫 토큰까지의 시간과 전체 시간의 p50, p99.
- **신뢰성.** 형식 오류율, 재시도율, 거절·중단 비율.
- **품질.** 평가셋 점수를 모델과 설정별로 비교한다.

## 재검토 조건

- 벤더를 자주 바꾸게 됐다. 게이트웨이나 추상화 계층을 검토한다.
- 호출량이 커져 자체 서빙이 싸졌다. vLLM을 검토한다.

## 출처

- HTTPX, [Timeouts](https://www.python-httpx.org/advanced/timeouts/): 2026-09-29 본문 확인. 연결·읽기·쓰기·풀 대기 한도와 전체 요청 기한의 차이를 확인했다. 각 SDK 버전의 전송 계층과 재시도는 별도 확인 대상이다.

- OpenAI, [openai-python README](https://github.com/openai/openai-python/blob/main/README.md): Responses API가 주 API, 기본 2회 재시도 대상, 기본 타임아웃 10분, 스트림 소비는 재시도하지 않음.
- Google, [python-genai README](https://github.com/googleapis/python-genai/blob/main/README.md): `response_json_schema`, 캐시(`client.caches`, ttl), 일괄 작업(`client.batches`).
- Anthropic, [Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching#pricing): 2026-10-01 본문 재확인. Pricing의 쓰기·읽기 배율과 예외, Cache limitations의 모델별 최소 길이, 적중 시 수명 갱신. 다른 API 동작의 근거로 확대하지 않는다.
- OpenAI, [Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching#how-caching-works): 2026-10-01 본문 재확인. GPT-5.6 이후 최소 길이·지원 방식·쓰기 요금과 GPT-6.1 Sol의 읽기 배율 예외.
- Google, [Context caching](https://ai.google.dev/gemini-api/docs/caching#implicit-caching): 2026-10-01 본문 재확인. 모델별 최소 길이와 Interactions API의 명시적 캐시 미지원.
