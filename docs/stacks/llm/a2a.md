# A2A

확인: 2026-09-28, A2A 프로토콜 문서(a2aproject/A2A, main) 기준. v1.0은 2026-03-12에 나왔고, 2026-08-27에 Agentic AI Foundation 프로젝트가 됐다.

## 요약

A2A(Agent2Agent)는 서로 다른 팀이나 조직이 만든 에이전트끼리 일을 맡기고 결과를 주고받는 프로토콜이다.
상대 에이전트는 내부를 알 수 없는 블랙박스다. 명함(Agent Card)으로 능력을 알리고, 작업(Task) 단위로 일을 받아 상태와 결과물(Artifact)을 돌려준다.
문서는 MCP가 에이전트 하나에 도구를 붙이는 **수직** 연결이고, A2A는 에이전트 사이를 잇는 **수평** 연결이라고 설명한다.

## 문제 신호

- 다른 팀이나 협력사가 운영하는 에이전트에게 일을 맡겨야 한다.
- 맡긴 일이 몇 분~며칠 걸리고, 중간에 추가 정보를 물어 올 수 있다.
- 에이전트 프레임워크가 서로 달라 직접 통합하기 어렵다.

## 기준선의 한계

기준선은 상대 시스템의 REST API를 도구로 감싸 호출하는 것이다.

- 상대가 결정적인 API라면 이것으로 충분하다.
- 상대가 에이전트라 작업이 길고, 중간에 질문하고, 결과물이 여러 개면 API 설계를 매번 새로 해야 한다.
- 능력 발견, 인증, 진행 상황 알림이 통합마다 다르다.

## 원리

- **Agent Card.** 에이전트의 신원, 능력, 기술(skill), 엔드포인트, 인증 요구를 담은 JSON 문서다. 보통 `https://{도메인}/.well-known/agent-card.json`에 두고, 기업 환경에서는 등록소(registry)로 관리한다.
- **Task.** 고유 ID와 수명 주기를 가진 작업 단위다.
  - 중간 상태로 `input-required`, `auth-required`가 있다.
  - 끝 상태는 `completed`, `canceled`, `rejected`, `failed`다. 끝난 작업은 다시 시작할 수 없다.
- **Message와 Artifact.** 메시지는 대화 한 턴이고, 결과물은 작업의 실제 산출물이다. 내용은 텍스트, 파일, 구조화 데이터 파트로 담는다.
- **긴 작업의 전달.** 세 가지가 있다.
  - 폴링
  - SSE 스트리밍([SSE](../comm/sse.md))
  - 웹훅 푸시 알림([웹훅](../comm/webhook.md))

## 가치

A2A의 가치는 **조직 경계를 넘는 에이전트 협업에 공통 작업 모델을 주는 것**이다.

- 상대의 내부 구현을 몰라도 능력을 발견하고 일을 맡긴다.
- 긴 작업, 중간 질문, 여러 결과물을 표준 상태로 다룬다.
- 프레임워크가 달라도 같은 프로토콜로 통합한다.

## 트레이드오프와 리스크

- **아직 젊은 표준이다.** v1.0이 2026년 3월에 나왔다. 구현과 운영 경험이 MCP나 REST보다 적다.
- **대부분의 시스템에는 과하다.** 한 조직 안의 에이전트끼리는 함수 호출이나 큐가 더 단순하다.
- **신뢰 경계.** 상대 에이전트의 결과물은 신뢰할 수 없는 입력이다. 프롬프트 주입과 잘못된 결과를 검증해야 한다.
- **비결정성.** 같은 요청에 다른 결과가 나올 수 있어, 계약 시험과 품질 합의가 어렵다.
- **비용과 책임.** 맡긴 작업의 토큰 비용, 실패 책임, 데이터 처리 조건을 조직 사이에 정해야 한다.

## 대안과 경계

| 대안 | 고를 때 |
|---|---|
| [MCP](mcp.md) | 상대가 도구다. 입력과 출력이 정해져 있고, 우리 에이전트가 판단한다. |
| REST·[gRPC](../comm/grpc.md) | 상대가 결정적인 서비스다. |
| 메시지 브로커 | 한 조직 안에서 에이전트 사이 작업을 나눈다([Kafka](../async/kafka.md), [RabbitMQ](../async/rabbitmq.md)). |
| 단일 에이전트와 하위 에이전트 | 한 애플리케이션 안에서 일을 나눈다. 프로토콜이 필요 없다. |

## 깊이 있는 활용

- **먼저 경계를 확인한다.** 상대가 다른 조직이고, 작업이 길고, 상대 내부를 알 수 없을 때만 A2A를 고른다. 나머지는 도구 호출이나 API로 한다.
- **작업 ID로 멱등하게.** 재시도로 같은 일을 두 번 맡기지 않도록, 우리 쪽 요청 ID와 작업 ID를 연결해 기록한다.
- **결과물은 검증 후 사용.** 스키마 검증, 출처 확인, 민감 동작 전 사람 확인을 둔다.
- **긴 작업은 푸시 알림과 대사.** 웹훅으로 상태 변화를 받고, 놓친 알림은 주기적 조회로 메운다.

## 임시방책의 신호

- 같은 서비스 안의 모듈 둘을 A2A로 연결한다.
- 상대 에이전트의 결과를 검증 없이 DB에 쓴다.
- 긴 작업을 동기 호출로 기다리다 타임아웃을 계속 늘린다.

## 실패 재현

- **중간 질문.** 상대가 `input-required`를 돌려줄 때 우리 에이전트가 답하거나 사람에게 넘기는지 본다.
- **알림 유실.** 푸시 알림을 막고, 조회로 끝 상태를 찾는지 본다.
- **악성 결과물.** 결과물에 지시문을 심어 우리 에이전트가 따르는지 본다.

## 측정과 검증

- **작업 결과.** 끝 상태별 비율, 작업 완료 시간 분포, 중간 질문 횟수.
- **품질.** 맡긴 작업의 결과물을 평가셋으로 채점한다.
- **비용.** 작업당 비용과 재시도 수.

## 재검토 조건

- 상대가 사실상 결정적인 서비스다. API나 MCP 도구로 바꾼다.
- 표준이 크게 바뀌었다. 판 호환을 다시 확인한다.
