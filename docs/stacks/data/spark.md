# Spark

확인: 2026-09-28, Apache Spark v4.2.0 문서 기준.

## 요약

Spark는 큰 데이터를 여러 작업자에 나눠 처리하는 분산 처리 엔진이다.
SQL과 데이터프레임으로 쓴 처리를 실행 계획으로 바꾸고, 파티션 단위 작업으로 나눠 클러스터에서 돌린다. 같은 API로 배치와 스트림(Structured Streaming)을 다룬다.
강점은 한 대를 넘는 데이터다. 대가는 **셔플(작업자 간 데이터 재분배)과 클러스터 운영**이라, 한 대로 되는 일에 쓰면 느리고 비싸다.

## 문제 신호

- 데이터나 조인의 중간 결과가 한 대의 메모리와 디스크를 넘는다.
- 한 대로 돌리는 배치가 정해진 시간 안에 끝나지 않는다.
- 객체 저장소의 수 TB 파일을 정기적으로 가공해 다른 시스템에 넣어야 한다.
- 대규모 학습 데이터 준비, 임베딩 대량 계산 같은 병렬 작업이 있다.

## 기준선의 한계

기준선은 단일 노드 처리다([DuckDB와 단일 노드 분석](duckdb.md)).

- 한 대의 코어, 메모리, 디스크가 상한이다.
- 한 대가 죽으면 작업 전체를 처음부터 다시 한다.
- 데이터가 여러 대의 객체 저장소에 흩어져 있으면 한 대로 가져오는 네트워크가 병목이다.

## 원리

- **지연 실행과 최적화.** 변환은 계획만 쌓고, 결과를 요구할 때 최적화된 실행 계획으로 돈다.
- **파티션과 셔플.** 데이터는 파티션으로 나뉘어 작업자에서 처리된다. 조인과 집계는 같은 키를 한곳에 모으는 셔플이 필요하고, 셔플은 디스크와 네트워크를 쓰는 가장 비싼 단계다.
  - `spark.sql.shuffle.partitions` 기본값은 200이다.
- **적응형 쿼리 실행(AQE).** 3.2.0부터 기본으로 켜져 있다. 실행 중 통계로 계획을 다시 짠다.
  - 셔플 뒤 작은 파티션을 목표 크기(기본 64MB)로 합친다.
  - 치우친(skew) 조인의 큰 파티션을 쪼갠다.
  - 작은 쪽 테이블이 한도보다 작으면 브로드캐스트 조인으로 바꾼다.
- **브로드캐스트 조인.** 작은 테이블을 모든 작업자에 복사해 셔플 없이 조인한다. `spark.sql.autoBroadcastJoinThreshold` 기본값은 10MB다.
- **Structured Streaming.** 기본은 마이크로 배치로, 문서는 종단 지연 약 100ms와 정확히 한 번을 말한다. 재생 가능한 소스(offset), 체크포인트와 선행 기록 로그, 멱등한 싱크가 함께 있어야 종단 정확히 한 번이 된다.

## 가치

Spark의 가치는 **한 대를 넘는 데이터를 SQL 수준의 추상으로, 장애에 견디며 처리하는 것**이다.

- 작업자를 늘리면 처리량이 는다.
- 작업 하나가 실패하면 그 파티션만 다시 계산한다.
- 배치와 스트림, SQL과 Python을 한 엔진에서 다룬다.
- 객체 저장소의 열 지향 파일(Parquet, 테이블 포맷)과 잘 맞는다.

## 트레이드오프와 리스크

- **작은 데이터에서 느리다.** 작업 계획, 작업자 시작, 직렬화 비용이 있어, 한 대로 몇 초면 끝날 일이 몇 분이 된다.
- **셔플과 치우침.** 키 하나에 데이터가 몰리면 작업 하나가 전체를 붙잡는다. 셔플 파티션 수가 맞지 않으면 작은 작업이 너무 많거나 큰 작업이 넘친다.
- **운영 부담.** 클러스터(자체, Kubernetes, 관리형), 자원 할당, 의존성 배포, 로그 수집이 필요하다.
- **Python UDF의 비용.** 행 단위 Python 함수는 JVM과 Python 사이의 직렬화로 느리다. 내장 함수와 SQL을 먼저 쓴다.
- **작은 파일 문제.** 파티션마다 파일을 쓰므로, 파티션이 많으면 작은 파일이 쏟아져 다음 읽기가 느려진다.
- **스트림의 한계.** 마이크로 배치의 지연과 상태 관리 기능은 Flink보다 제한적이다. 1ms 수준의 연속 처리 모드는 at-least-once다.

## 대안과 경계

| 대안 | 고를 때 |
|---|---|
| [DuckDB와 단일 노드 분석](duckdb.md) | 데이터가 한 대에 들어간다. 대부분의 경우 먼저 이것이다. |
| [Flink](flink.md) | 연속 스트림에서 낮은 지연, 사건 시간 처리, 큰 상태가 핵심이다. |
| [Spring Batch](../batch/spring-batch.md) | 업무 DB의 행을 읽어 처리하고, 재시작과 건너뛰기 같은 업무 배치 의미론이 필요하다. |
| 관리형 웨어하우스 | SQL 분석이 주 용도이고, 클러스터를 운영하고 싶지 않다. |

## 깊이 있는 활용

- **셔플을 줄이는 설계.** 먼저 거르고 필요한 열만 고른 뒤 조인한다. 작은 차원 테이블은 브로드캐스트한다.
- **AQE에 맡기고 초기 파티션만 넉넉히.** 파티션 수를 손으로 맞추기보다, AQE가 합치도록 초기 수를 넉넉히 두고 목표 크기를 조정한다.
- **치우침을 먼저 본다.** 키별 개수 분포를 확인하고, 치우친 키는 AQE 조인 분할이나 소금 키(salting)로 나눈다.
- **출력 파일 크기를 맞춘다.** 쓰기 전에 파티션 수를 조정해 파일 하나가 수백 MB 정도가 되게 한다. (미검증: 적정 크기는 읽는 쪽 엔진에 따라 다르다.)
- **스트림은 체크포인트와 멱등 싱크로.** 체크포인트 위치를 영구 저장소에 두고, 싱크는 키 기준 덮어쓰기(upsert)나 배치 ID 기준으로 멱등하게 만든다.

## 임시방책의 신호

- 수십 GB 데이터를 위해 Spark 클러스터를 만들고, 작업 대부분이 시작 시간이다.
- `collect()`로 큰 결과를 드라이버에 모아 메모리 부족으로 죽는다.
- 행마다 Python UDF로 외부 API를 부른다.
- 느린 작업을 작업자 수만 늘려 해결하려 한다. 원인은 치우친 키 하나다.
- 스트림 싱크가 멱등하지 않아, 재시작하면 결과가 중복된다.

## 실패 재현

- **치우침.** 키 하나에 데이터의 절반을 몰아 조인하고, 단계별 작업 시간 분포에서 한 작업만 긴 것을 본다. AQE 분할을 켜고 비교한다.
- **작업자 장애.** 처리 중 작업자 하나를 죽여, 해당 파티션만 다시 계산되고 결과가 같은지 확인한다.
- **스트림 재시작.** 스트림 작업을 중간에 죽이고 재시작해, 싱크 결과의 중복과 누락을 번호로 센다.
- **작은 데이터 비용.** 같은 집계를 DuckDB와 Spark로 돌려 데이터 크기별 교차점을 찾는다.

## 측정과 검증

- **단계별 시간.** Spark UI의 단계와 작업 시간 분포, 셔플 읽기·쓰기 양, 넘침(spill) 양.
- **치우침.** 단계 안 작업 시간의 최대 ÷ 중앙값.
- **비용.** 작업당 코어·시간과 결과 데이터당 비용. 단일 노드 기준선과 같은 표로 비교한다.
- **스트림.** 배치당 처리 시간이 트리거 간격보다 짧은지, 입력 지연(lag)의 추세.

## 재검토 조건

- 데이터가 줄었거나 단일 노드 엔진이 따라왔다. DuckDB로 돌아간다.
- 스트림 지연과 상태 요구가 커졌다. Flink를 검토한다.
