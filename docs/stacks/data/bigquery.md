# BigQuery

확인: 2026-09-29 재검토. 최초 조사는 2026-09-28, Google Cloud 문서는 조사 환경에서 막혀 있어 검색 요약으로 확인했다. 가격은 2026년 5월 기준 검색 결과다.

## 요약

BigQuery는 Google Cloud의 서버리스 데이터 웨어하우스다.
저장과 계산이 분리돼 있어, 서버 없이 SQL을 보내면 필요한 만큼의 계산 자원(슬롯)이 붙어 수 TB를 훑는다.
강점은 운영 없는 대규모 분석과 여러 팀의 공유다. 대가는 **질의가 읽은 양이 곧 비용**이라는 과금 구조와, 업무 DB가 아니라는 점이다.

## 문제 신호

- 여러 팀이 같은 데이터를 SQL로 분석하고, 권한과 공유가 필요하다.
- 데이터가 수 TB 이상이고 계속 늘어난다.
- 분석용 서버나 클러스터를 운영하고 싶지 않다.
- 이미 Google Cloud를 쓰고, 로그와 이벤트가 그쪽에 모인다.

## 기준선의 한계

기준선은 단일 노드 분석이다([DuckDB와 단일 노드 분석](duckdb.md)).

- 한 사람이나 작업 하나가 분석할 때는 가장 싸고 빠르다.
- 여러 사용자의 동시 조회, 권한, 공유 데이터셋이 필요하면 한 프로세스 모델이 맞지 않는다.
- 데이터가 한 대의 디스크를 넘으면 한계다.

## 원리

- **저장과 계산의 분리.** 데이터는 열 지향으로 저장되고, 질의 때 슬롯이라는 계산 단위가 붙는다.
- **과금 모델.**
  - 온디맨드: 읽은 바이트로 낸다. 검색 결과 기준 TiB당 6.25달러, 매달 첫 1TiB는 무료다.
  - 용량(editions): 슬롯을 예약하고 자동 확장한다. 50슬롯 단위로 늘어난다.
- **읽은 열이 비용이다.** 열 지향이라 필요한 열만 읽는다. `SELECT *`는 모든 열을 읽고, 군집하지 않은 테이블에서 `LIMIT`은 읽는 양을 줄이지 않는다.
- **분할과 군집.** 날짜 등으로 분할(partitioning)하고 자주 거르는 열로 군집(clustering)하면, 조건에 맞는 부분만 읽어 비용과 시간이 준다.
- **청구 한도.** `maximum_bytes_billed`를 넘을 것으로 추정되면 질의가 비용 없이 실패한다. 군집 테이블은 추정이 상한이라 실제보다 크게 잡힐 수 있다.
- **제약 조건은 강제되지 않는다.** 기본 키와 외래 키를 선언할 수 있지만 강제하지 않는다. 어긋난 데이터가 있으면 최적화된 질의가 틀린 결과를 낼 수 있다.
- **쓰기.** Storage Write API의 committed 스트림은 클라이언트가 준 오프셋으로 스트림 안에서 정확히 한 번 쓰기를 한다. DML은 테이블별 동시 실행 제한이 있어 행 단위 잦은 갱신에 맞지 않는다.

## 가치

BigQuery의 가치는 **운영 없이 대규모 분석을 여러 사람이 공유하게 하는 것**이다.

- 서버와 클러스터 없이 수 TB를 SQL로 분석한다.
- 데이터셋 단위 권한으로 팀 간 공유가 쉽다.
- 저장이 싸서 원본 이벤트를 오래 보관하고 필요할 때 다시 가공한다.

## 트레이드오프와 리스크

- **비용 폭탄.** 분할 없는 큰 테이블에 `SELECT *`를 반복하는 대시보드 하나가 큰 청구서를 만든다.
- **업무 DB가 아니다.** 행 단위 잦은 갱신, 낮은 지연의 키 조회, 강제되는 제약 조건이 없다.
- **종속.** SQL 방언과 기능, 과금이 Google Cloud에 묶인다.
- **데이터 이동 비용.** 다른 클라우드나 온프레미스에서 데이터를 옮기는 비용과 지연이 있다.
- **지연.** 질의마다 수 초가 걸릴 수 있어, 사용자 요청 경로의 조회에는 맞지 않는다.

## 대안과 경계

| 대안 | 고를 때 |
|---|---|
| [DuckDB와 단일 노드 분석](duckdb.md) | 데이터가 한 대에 들어가고 사용자가 적다. |
| [Spark](spark.md) | 복잡한 변환과 ML 파이프라인을 직접 통제하고, 객체 저장소의 열린 형식을 쓴다. |
| 다른 클라우드 웨어하우스(Snowflake, Redshift) | 주 클라우드나 기존 계약이 다르다. |
| [PostgreSQL](../state/postgresql.md) 복제본 | 분석이 가볍고 업무 데이터와 가깝다. |

## 깊이 있는 활용

- **테이블은 처음부터 분할과 군집으로.** 이벤트 시각으로 분할하고, 필터에 자주 쓰는 열로 군집한다. 분할 필터를 필수로 요구하는 설정을 켠다.
- **비용 가드레일.** 사용자와 프로젝트에 `maximum_bytes_billed`와 일일 할당량을 둔다. 질의 전 예상 바이트를 확인하는 습관을 CI와 도구에 넣는다.
- **대시보드는 집계 테이블로.** 원본 이벤트를 매번 훑지 말고, 주기적으로 집계 테이블이나 구체화된 뷰를 만든다.
- **적재는 일괄이나 Storage Write API로.** 행마다 DML을 보내지 않는다. 정확히 한 번이 필요하면 committed 스트림과 오프셋을 쓴다.
- **제약 조건은 적재 파이프라인에서 검증한다.** 강제되지 않으므로 중복과 참조 오류를 적재 단계의 데이터 테스트로 잡는다.

## 임시방책의 신호

- 운영 DB의 테이블을 그대로 복사하고 분할 없이 전체를 매번 훑는다.
- 비용을 줄이려고 `LIMIT 100`을 붙인다.
- 애플리케이션이 사용자 요청마다 BigQuery를 조회한다.
- 행 단위 `UPDATE`를 초마다 보내 DML 제한에 걸린다.

## 실패 재현

- **비용.** 같은 질의를 분할·군집 전후로 돌려 읽은 바이트를 비교한다. `LIMIT` 유무로도 비교한다.
- **청구 한도.** `maximum_bytes_billed`를 낮게 두어 큰 질의가 비용 없이 거부되는지 본다.
- **중복 적재.** 적재 작업을 재시도해 중복이 생기는지 보고, 오프셋 기반 쓰기로 반복한다.

## 측정과 검증

- **비용.** 질의별·사용자별 읽은 바이트와 비용, 상위 비용 질의 목록.
- **효율.** 분할 필터가 걸린 질의의 비율, 슬롯 사용률.
- **데이터 품질.** 적재별 중복, 누락, 제약 위반 수.

## 재검토 조건

- 데이터와 사용자가 줄었다. DuckDB로 옮겨 비용을 줄인다.
- 주 클라우드가 바뀌었다. 데이터 이동 비용과 대안을 다시 계산한다.

## 출처

- Google Cloud, [BigQuery pricing](https://cloud.google.com/bigquery/pricing): 온디맨드 TiB당 가격과 무료 1TiB. 검색 요약으로 확인했다.
- Google Cloud, [Estimate and control costs](https://docs.cloud.google.com/bigquery/docs/best-practices-costs): 군집하지 않은 테이블에서 `LIMIT`이 비용을 줄이지 않음, 분할과 군집, `maximum_bytes_billed`와 군집 테이블의 추정 상한. 검색 요약으로 확인했다.
- Google Cloud, [Primary and foreign keys](https://docs.cloud.google.com/bigquery/docs/primary-foreign-keys): 강제되지 않는 제약과 틀린 결과 위험. 검색 요약으로 확인했다.
- Google Cloud, [Storage Write API](https://docs.cloud.google.com/bigquery/docs/write-api): committed 스트림과 오프셋의 정확히 한 번. 검색 요약으로 확인했다.
- Google Cloud, [Slots autoscaling](https://docs.cloud.google.com/bigquery/docs/slots-autoscaling-intro)과 [Quotas](https://docs.cloud.google.com/bigquery/quotas): 50슬롯 단위 확장, DML 동시 실행 제한. 검색 요약으로 확인했다.
