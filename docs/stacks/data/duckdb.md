# DuckDB와 단일 노드 분석

확인: 2026-09-28, DuckDB 문서(duckdb/duckdb-web, main의 current 문서, DuckDB 1.5.5) 기준.

## 요약

DuckDB는 애플리케이션 프로세스 안에서 도는 열 지향 분석 DB다.
서버 없이 라이브러리로 붙여 Parquet, CSV, DB 테이블을 SQL로 바로 읽고, 메모리보다 큰 데이터도 디스크로 넘쳐 가며 처리한다.
단일 노드 분석의 비교 기준으로 쓰기 좋다. 분산 엔진보다 빠르고 싼지는 질의·파일 배치·동시성·환경에 따라 측정한다. 작은 데이터로 분산 실행을 학습할 때도 같은 결과와 실행 계획을 비교하는 기준이 된다.

## 문제 신호

- 운영 DB에서 무거운 집계 쿼리를 돌려 서비스가 느려진다.
- 수 GB~수백 GB의 로그나 이벤트 파일을 분석해야 한다.
- pandas로 처리하다 메모리가 부족하거나 너무 느리다.
- 분석 때문에 Spark 클러스터를 검토하고 있지만, 데이터가 서버 한 대의 디스크에 들어간다.

## 기준선의 한계

기준선은 애플리케이션 코드의 반복문과 운영 DB의 집계 쿼리다.

- 행 단위 반복문은 느리고, 결과를 모두 메모리에 올린다.
- 운영 DB(행 지향 OLTP)는 넓은 범위의 집계에 약하고, 분석 부하가 서비스 쿼리와 자원을 다툰다.
- pandas는 데이터 전체를 메모리에 올리고, 대부분의 연산이 한 스레드다. (미검증: 버전과 연산에 따라 다르다.)

## 원리

- **프로세스 안에서 돈다.** 서버가 없고, 애플리케이션이 라이브러리로 연다. 네트워크 왕복과 운영할 서버가 없다.
- **열 지향과 벡터 실행.** 필요한 열만 읽고, 여러 값을 묶어 한 번에 처리해 집계와 스캔이 빠르다.
- **메모리보다 큰 처리.** 그룹, 조인, 정렬, 윈도 같은 차단 연산자가 디스크로 넘쳐 가며 끝까지 처리한다. 기본 메모리 한도는 RAM의 80%다.
  - 한 쿼리에 차단 연산자가 여럿이면 여전히 메모리 부족이 날 수 있다.
  - `list()`, `string_agg()` 같은 일부 집계는 디스크로 넘치지 못한다.
- **파일을 바로 읽는다.** Parquet의 열 통계(zonemap)로 필요 없는 부분을 건너뛴다. 다만 Parquet에는 DuckDB 자체 형식의 고급 통계가 없어, 조인 순서가 나쁘면 테이블로 적재해 보라고 문서가 권한다.
- **동시성 모델.** 한 프로세스만 읽고 쓸 수 있고, 여러 프로세스는 읽기 전용으로만 연다. 프로세스 안에서는 여러 스레드가 쓸 수 있고, 같은 행을 동시에 고치면 낙관적 동시성 충돌로 실패한다.

## 가치

DuckDB의 가치는 **분산 시스템 없이 한 대의 자원을 끝까지 쓰는 분석 엔진**이라는 점이다.

- 클러스터, 스케줄러, 직렬화 비용 없이 SQL 하나로 파일을 분석한다.
- 개발자 노트북, CI, 배치 작업자 어디서나 같은 엔진이 돈다.
- 운영 DB에서 분석 부하를 떼어 낸다.
- 데이터가 커지면 같은 SQL을 Spark SQL 같은 분산 엔진으로 옮기기 쉽다.

- **학습 실험.** 프로젝트 이벤트 파일을 Parquet로 분석한다. 열 선택·필터·메모리 한도를 바꾸어 실행 계획과 spill을 관찰하고, 원본 크기와 실행 중 필요한 자원이 다른 이유를 설명한다.

## 트레이드오프와 리스크

- **여러 프로세스의 쓰기가 안 된다.** 웹 서버 여러 대가 같은 DuckDB 파일에 쓰는 구조는 맞지 않는다. 문서는 원격 프로토콜(Quack, 베타)이나 PostgreSQL 카탈로그를 쓰는 DuckLake를 대안으로 든다.
- **OLTP가 아니다.** 한 행씩 자주 고치는 업무 데이터 저장소로 쓰면 느리고 충돌한다.
- **한 대의 실행 자원.** 원격 Parquet를 필요한 부분만 읽을 수 있어 원본 전체가 로컬 디스크에 들어갈 필요는 없다. 실행에 필요한 메모리, spill 공간, 네트워크와 시간 예산이 실제 한계다. 내장 엔진만으로 서비스의 고가용성이 구성되지는 않는다.
- **메모리 설정.** 컨테이너에서는 RAM의 80%가 컨테이너 한도가 아니라 호스트 기준일 수 있으므로 한도를 명시한다. (미검증: 환경마다 다르다.)

## 대안과 경계

| 대안 | 고를 때 |
|---|---|
| [Spark](spark.md) | 데이터나 중간 결과가 한 대를 넘는다. 여러 작업자에 나눠야 한다. |
| [PostgreSQL](../state/postgresql.md) | 분석이 가볍고 업무 데이터와 트랜잭션으로 묶여야 한다. 복제본에서 돌린다. |
| Polars | Python 데이터프레임 API가 필요하고, 한 대에서 빠르게 처리한다. |
| 데이터 웨어하우스(관리형) | 여러 팀이 같은 데이터를 동시에 조회하고 권한 관리가 필요하다. |

## 깊이 있는 활용

- **운영 DB를 직접 읽지 말고 스냅샷을 읽는다.** 운영 DB에서 Parquet으로 내보내고, 분석은 파일에서 한다. 운영 DB의 부하와 분석이 분리된다.
- **파일 설계.** 날짜 같은 자주 거르는 열로 파티션 폴더를 나누고, 너무 작은 파일을 많이 만들지 않는다. gzip 같은 무거운 압축은 읽을 때마다 해제 비용이 든다.
- **메모리와 임시 디렉터리를 명시한다.** `memory_limit`과 `temp_directory`를 정해, 넘침이 빠른 디스크로 가게 한다. 순서가 필요 없으면 `preserve_insertion_order = false`로 메모리를 줄인다.
- **`EXPLAIN ANALYZE`로 본다.** 느린 쿼리의 단계별 시간을 확인한다.
- **배치 작업자로 쓴다.** 작업 하나가 DuckDB를 열고, 파일을 읽고, 결과를 쓰고, 닫는다. 동시 쓰기 문제가 없다.

## 임시방책의 신호

- 운영 DB에 대시보드 집계 쿼리를 직접 건다.
- 로그 파일을 한 줄씩 읽어 딕셔너리에 누적한다.
- 메모리가 부족하자 데이터를 잘라 여러 번 돌리고 결과를 손으로 합친다.
- 데이터가 수십 GB인데 분석을 위해 Spark 클러스터부터 만든다.

## 실패 재현

- **메모리 초과.** 메모리 한도를 낮게 두고 큰 조인과 그룹을 돌려, 디스크로 넘치며 끝나는지, 차단 연산자가 여럿일 때 실패하는지 본다.
- **동시 쓰기.** 두 프로세스가 같은 파일을 읽기-쓰기로 열어 실패하는 것을 확인한다.
- **기준선 비교.** 같은 집계를 pandas 반복문, 운영 DB, DuckDB로 돌려 시간과 메모리를 잰다.

## 측정과 검증

- **처리 시간과 최대 메모리.** 데이터 크기를 늘려 가며 시간과 메모리 곡선을 그린다. 한 대의 한계가 어디인지 수치로 남긴다.
- **넘침.** 임시 디렉터리 사용량과 넘침이 있을 때의 시간 증가.
- **정확성.** 같은 집계를 기준선 도구와 비교해 결과가 같은지 확인한다.

## 재검토 조건

- 파일 배치와 실행 계획을 개선해도 메모리·spill 공간·처리 기한을 넘고 병렬화할 작업이 있다. [Spark](spark.md)에서 같은 질의를 실행해 병목 해소와 자원 비용을 측정한다.
- 여러 사용자와 서비스가 동시에 쓰고 조회한다. 웨어하우스나 DuckLake를 검토한다.
