# k6

확인: 2026-09-27, grafana/k6-docs 저장소의 `next` 문서, k6 최신 태그 v2.3.0 기준.

## 요약

k6는 JavaScript로 부하 시나리오를 쓰고, 요청 도착률이나 가상 사용자(VU) 수로 부하를 건 뒤, 지연 분포와 오류율을 통과 기준(threshold)과 함께 보고하는 부하 시험 도구다.
중요한 것은 도구 사용법보다 **부하 모델**이다. 응답이 느려지면 요청도 줄어드는 폐쇄형 모델로 재면 시스템이 버티는 것처럼 보인다. 도착률을 고정하는 개방형 모델로 재야 실제 트래픽에서의 한계가 보인다.

## 문제 신호

- "이 API가 초당 몇 요청까지 버티나", "캐시를 넣고 빨라졌나"에 답해야 한다.
- 성능 개선을 주장하는데 측정 조건이 없다.
- 배포 전 성능 회귀를 자동으로 잡고 싶다.
- 장애 주입 실험에서 일정한 배경 부하가 필요하다.

## 기준선의 한계

기준선은 브라우저나 `curl`로 몇 번 호출해 보는 것, 또는 반복문으로 요청을 쏘는 스크립트다.

- 한 번의 호출은 캐시 상태와 우연에 좌우된다. 분포가 없다.
- 반복문 스크립트는 응답을 기다린 뒤 다음 요청을 보내므로, 서버가 느려질수록 요청을 덜 보낸다. 부하가 서버 속도에 끌려간다.
- 통과 기준이 없어 결과 해석이 사람마다 다르다.

## 원리

- **폐쇄형과 개방형 모델.** 폐쇄형 실행기(`constant-vus`, `ramping-vus` 등)는 한 VU의 반복이 끝나야 다음 반복을 시작한다. 개방형 실행기(`constant-arrival-rate`, `ramping-arrival-rate`)는 반복 완료와 무관하게 정해진 도착률로 반복을 시작한다.
- **조정된 누락(coordinated omission).** k6 문서는 폐쇄형 모델에서 시스템이 느려지면 반복 시간이 길어지고 새 반복의 도착률이 줄어든다고 설명하고, 이것을 부하 시험 문헌의 coordinated omission 문제로 소개한다. 느린 구간의 요청이 덜 측정돼 지연 분포가 좋아 보인다.
- **누락된 반복(dropped iterations).** 도착률 실행기는 쓸 수 있는 VU가 없으면 반복을 시작하지 못하고 `dropped_iterations`로 센다. 문서는 시험 초반에 생기면 VU 할당이 부족한 것이고, 시험 후반에 생기면 대상 시스템 성능이 나빠져 반복이 길어진 것일 수 있다고 설명한다.
- **threshold.** `http_req_duration: ['p(95)<200']`, `http_req_failed: ['rate<0.01']`처럼 지표에 통과 기준을 선언한다. 기준을 넘으면 k6가 실패 종료 코드로 끝나 CI에서 막을 수 있고, `abortOnFail`로 중간에 멈출 수 있다.
- **시험 유형.** 문서는 목적에 따라 smoke(최소 부하 동작 확인), 평균 부하, stress(최대 부하), spike(급증), breakpoint(한계까지 점증), soak(장시간) 시험을 구분한다.

## 가치

k6의 가치는 **"얼마나 버티는가"를 재현 가능한 조건과 합격 기준으로 표현하는 것**이다.

- 시나리오, 부하 모델, 기준이 코드라서 리뷰하고 버전 관리하고 CI에서 돌린다.
- 개방형 모델로 실제 도착률을 흉내 내 조정된 누락 없이 꼬리 지연을 본다.
- 결과를 Prometheus 등으로 내보내 서버 지표와 같은 시간축에서 본다.

- **학습 실험.** 같은 API에 폐쇄형 부하와 일정 도착률 부하를 건다. 서버를 느리게 하며 실제 도착률·실패·지연·dropped iterations를 비교하고 부하기 자체의 용량도 확인한다.

## 트레이드오프와 리스크

- **부하 발생기가 병목일 수 있다.** 부하를 내는 기계의 CPU·네트워크가 모자라면 목표 도착률을 못 낸다. `dropped_iterations`와 부하 기계 자원을 함께 보지 않으면 서버 한계로 오해한다.
- **시나리오가 현실과 다르면 숫자도 의미가 없다.** 한 엔드포인트만 균일하게 때리는 시험은 캐시 적중률, 요청 비율, 데이터 분포가 운영과 달라 결과가 과대평가된다.
- **환경 차이.** 운영보다 작은 시험 환경, 다른 데이터 크기, 데워지지 않은 캐시가 결과를 바꾼다.
- **운영 환경 부하 시험의 위험.** 운영에서 돌리면 실제 사용자와 하위 시스템(결제, 메일)에 영향을 준다.
- **JavaScript 런타임은 Node.js가 아니다.** k6는 Go로 만든 자체 런타임에서 스크립트를 실행한다. npm 모듈을 그대로 쓸 수 없는 경우가 있다.

## 대안과 경계

| 대안 | 고를 때 |
|---|---|
| Gatling, JMeter | 팀이 Scala/Java나 GUI 기반 도구에 익숙하다. |
| wrk2 등 단순 HTTP 부하기 | 단일 엔드포인트의 최대 처리량만 빠르게 본다. |
| `pgbench`, `kafka-producer-perf-test.sh`, `vllm bench serve` | 특정 시스템(DB, 브로커, LLM 서버)의 한계를 그 시스템 고유 도구로 잰다. |
| 운영 트래픽 재생 | 실제 요청 기록이 있고, 재생 인프라를 갖췄다. |

## 깊이 있는 활용

- **도착률 실행기를 기본으로 쓴다.** "초당 N 요청을 견디는가"라는 질문에는 `constant-arrival-rate`를 쓴다. `preAllocatedVUs`는 `도착률 × 예상 응답 시간(초)`에 여유를 둬서 정한다(리틀의 법칙). 한계를 찾을 때는 `ramping-arrival-rate`로 도착률을 계단식으로 올린다.
- **`dropped_iterations`를 threshold에 넣는다.** 누락이 0이 아니면 목표 부하를 실제로 내지 못한 것이다. 이 시험의 지연 수치로 결론을 내지 않는다.
- **운영 요청 비율을 재현한다.** 운영 로그에서 엔드포인트별 비율, 사용자별 데이터 분포, 캐시 적중 조건을 가져와 시나리오를 여러 개 병렬로 둔다.
- **태그로 나눠 본다.** 요청에 이름 태그를 붙이고 엔드포인트별 threshold를 둔다. 전체 평균이 특정 느린 경로를 가린다.
- **단계별 시험을 나눈다.** smoke로 스크립트와 기준을 확인하고, 평균 부하로 기준선을 잡고, stress·breakpoint로 한계를 찾고, soak로 누수를 찾는다.
- **서버 지표와 함께 본다.** k6 결과만 보지 말고 같은 구간의 CPU, DB 연결 풀, GC, 하위 호출 지연을 [Prometheus와 Grafana](../ops/prometheus-grafana.md)에서 함께 본다. 병목 위치가 보인다.
- **CI에 짧은 회귀 시험을 넣는다.** 몇 분짜리 평균 부하 시험과 p95·오류율 기준을 파이프라인에 두고, 긴 시험은 야간에 돌린다.
- **장애 주입의 배경 부하로 쓴다.** 도착률 부하를 거는 중에 [Toxiproxy](toxiproxy.md)나 xk6-disruptor로 장애를 넣으면, 장애 동안의 오류율과 회복 시간을 잴 수 있다.

## 임시방책의 신호

- VU 몇 개로 돌려 본 평균 응답 시간 하나로 "빨라졌다"고 한다.
- 폐쇄형 실행기로 "초당 1,000 요청을 견딘다"고 보고한다. 실제로 보낸 요청 수는 보지 않는다.
- `dropped_iterations`가 쌓였는데 지연 수치만 본다.
- 캐시가 100% 적중하는 같은 요청만 반복한다.
- 부하 기계의 CPU가 100%인 것을 모른다.

## 실패 재현

- **조정된 누락.** 서버에 지연을 주입한 상태에서 같은 목표 부하를 `constant-vus`와 `constant-arrival-rate`로 각각 걸어, 실제 요청 수와 p99를 비교한다. 폐쇄형이 요청 수를 줄이고 꼬리를 가리는 것을 확인한다.
- **부하기 병목.** 부하 기계 자원을 제한하고 목표 도착률을 올려 `dropped_iterations`가 생기는 것을 본다.
- **비현실적 시나리오.** 같은 ID만 조회하는 시험과 운영 분포의 ID를 조회하는 시험의 결과를 비교한다.

## 측정과 검증

- **보고 형식.** 도착률(목표와 실제), 요청 수, 누락 수, 오류율, 지연 p50·p95·p99·최대를 함께 쓴다. 시험 환경, 데이터 크기, 캐시 상태, 버전을 적는다.
- **분포를 본다.** 평균이 아니라 백분위와 히스토그램을 본다. 백분위 추정에는 표본 수가 필요하다. p99를 안정적으로 보려면 수천 요청 이상이 필요하다(미검증: 필요한 수는 분포 모양에 따라 다르다).
- **반복한다.** 같은 시험을 여러 번 돌려 실행 간 변동을 본다. 변경 전후 비교는 번갈아 여러 번 돌려 환경 변화의 영향을 줄이고, 차이에 신뢰구간을 붙인다([측정 통계](statistics.md)).
- **한계 정의.** "p99 < 목표를 지키고 오류율 < 1%인 최대 도착률"처럼 한계를 목표 기반으로 정의한다.

## 재검토 조건

- 서비스가 HTTP가 아닌 프로토콜 중심으로 바뀌었다. 해당 시스템 고유 도구를 쓴다.
- 운영 트래픽 재생이 가능해져 합성 시나리오보다 현실적이다.
