# RAG 파이프라인

확인: 2026-09-28, 이 영역의 다른 조사 문서와 Liu 외 "Lost in the Middle"(2023), Anthropic "Contextual Retrieval"(2024, 검색 요약) 기준.

## 요약

RAG(검색 증강 생성)는 질문과 관련된 원문을 먼저 찾아 모델 입력에 넣고, 그 근거로 답하게 하는 방식이다.
파이프라인은 파싱 → 청킹 → 임베딩·색인 → 검색 → 리랭킹 → 생성 → 평가로 이어지고, **답의 품질은 가장 약한 단계가 정한다.**
이 문서는 영역의 입구다. RAG가 맞는지부터 정하고, 단계별 선택은 각 문서로 넘긴다.

## 문제 신호

- 사내 문서, 규정, 제품 설명서에 근거해 답해야 하고, 출처를 보여야 한다.
- 모델이 모르는 최신 정보나 비공개 정보를 다뤄야 한다.
- 문서가 자주 바뀌고, 사용자마다 볼 수 있는 문서가 다르다.

## 기준선의 한계

기준선은 두 가지다.

- **키워드 검색과 원문 제시.** 검색 결과를 사람에게 보여 주는 것이다. 정확하지만 사람이 읽고 종합해야 한다.
- **문서 전체를 긴 문맥에 넣기.** 문서가 적으면 검색 없이 가장 단순하다.
  - 문서가 늘면 입력 비용이 질문마다 커진다. 캐시로 줄여도 문맥 한도가 상한이다.
  - Liu 외(2023)는 긴 입력의 중간에 있는 정보를 모델이 잘 쓰지 못한다고 보고했다.
  - 사용자별 권한을 입력 단계에서 걸러야 한다.

## 원리

- **근거가 필요한 답은 검색과 생성을 함께 검증한다.** 필요한 원문이 검색되지 않아도 모델이 기억이나 추측으로 맞는 답을 낼 수는 있지만, 해당 원문에 근거한 답으로 검증할 수는 없다. 원문을 잘 찾고도 잘못 생성할 수 있으므로 어느 단계의 개선 효과가 큰지는 오류를 나눠 측정한다.
- **단계별 역할.**
  - [문서 파싱](document-parsing.md): 구조와 출처 정보를 보존한다.
  - [청킹](chunking.md): 검색 단위를 정하고 문맥을 붙인다.
  - [임베딩 모델 선택](embeddings.md): 우리 언어와 도메인에서 가까움을 잰다.
  - [하이브리드 검색과 리랭킹](../search/hybrid-rerank.md): 키워드와 의미 검색을 합치고 순위를 다듬는다.
  - 생성: 근거만으로 답하고 인용한다. 근거가 없으면 모른다고 답한다.
  - [LLM 평가](llm-evaluation.md): 실패를 검색, 생성, 원문, 권한으로 나눠 잰다.
- **청크에 문맥 붙이기.** Anthropic은 청크마다 문서 문맥을 붙여 색인하면 검색 실패가 준다고 보고했다. 검색 요약으로 확인했고, 수치는 우리 평가셋으로 다시 잰다.
- **에이전트형 검색.** 한 번 검색하고 답하는 대신, 모델이 검색 도구를 여러 번 부르며 질의를 고친다. 어려운 질문에 강하지만 지연과 비용이 크다.

## 가치

RAG의 가치는 **모델을 바꾸지 않고, 바뀌는 비공개 지식에 근거한 답을 출처와 함께 주는 것**이다.

- 문서를 고치면 다음 질문부터 반영된다. 학습이 필요 없다.
- 출처를 보여 사용자가 검증할 수 있다.
- 검색 단계에서 권한을 걸러, 볼 수 없는 문서는 모델에 들어가지 않는다.

- **학습 실험.** 문서 추가·수정·삭제가 가능한 작은 검색 답변 기능을 만든다. 각 단계의 문서 버전과 근거 ID를 추적하며 권한 변경·삭제 이후 답변에 옛 근거가 남는지 확인한다.

## 트레이드오프와 리스크

- **단계가 많다.** 단계마다 실패가 있고, 어디서 틀렸는지 나눠 재지 않으면 고칠 곳을 모른다.
- **색인 동기화.** 원문이 바뀌거나 지워져도 색인이 늦으면 옛 답이나 지운 문서가 나온다.
- **권한 누수.** 검색 필터를 빠뜨리면 권한 없는 문서가 답에 섞인다.
- **근거 없는 생성.** 검색이 비어도 모델은 그럴듯하게 답한다.
- **평가 비용.** 평가셋과 판정이 없으면 개선인지 퇴보인지 알 수 없다.

## 대안과 경계

| 대안 | 고를 때 |
|---|---|
| 긴 문맥 투입 | 문서가 적고 자주 묻는다. 공통 접두어 캐시로 비용을 줄인다([LLM API와 SDK](../llm/llm-api.md)). |
| 미세 조정 | 지식이 아니라 형식, 어조, 작업 방식을 바꾸려 한다. 지식 주입에는 맞지 않는다. |
| 에이전트형 검색 | 질문이 여러 단계의 탐색을 요구하고, 지연을 감수한다. |
| 구조화 질의(SQL 생성) | 답이 표 형태 데이터에 있다. 문서 검색보다 질의가 정확하다. |

## 깊이 있는 활용

- **평가셋을 첫 단계로.** 실제 질문과 정답 문서, 모범 답을 먼저 모은다. 모든 선택(청크 크기, 모델, 리랭커)을 이 셋으로 비교한다.
- **검색 지표와 답 지표를 나눈다.** 검색은 Recall@k와 nDCG, 답은 근거 충실도와 정답률로 따로 잰다. 검색이 맞는데 답이 틀리면 생성 문제다.
- **권한은 검색 필터와 재확인 두 겹.** 색인에 권한 필드를 두고 거르며, 답에 쓰기 전에 원본에서 다시 확인한다.
- **"모름"을 설계한다.** 리랭커 점수가 기준보다 낮으면 답을 유보하고 검색 결과를 보여 준다.
- **긴 문맥과 섞는다.** 검색으로 문서 몇 개를 고른 뒤, 청크가 아니라 문서 전체를 넣어 문맥 손실을 줄인다. 캐시와 함께 비용을 잰다.

## 임시방책의 신호

- 평가셋 없이 청크 크기와 모델을 바꿔 가며 "좋아진 것 같다"고 판단한다.
- 검색 결과가 비어도 모델에게 답을 시킨다.
- 권한 필터 없이 전체 색인을 검색하고, 답을 만든 뒤 걸러 낸다.
- 답이 틀리면 프롬프트만 계속 고친다. 원인은 검색이다.

## 실패 재현

- **검색 실패.** 평가셋에서 정답 문서가 상위 k에 없는 질문을 모아 원인(파싱, 청킹, 임베딩, 키워드 부재)을 분류한다.
- **근거 없는 생성.** 답이 없는 질문을 섞어 모델이 모른다고 하는 비율을 잰다.
- **권한 누수.** 사용자 A로 사용자 B만 볼 수 있는 문서의 내용을 묻는다.
- **오래된 원문.** 문서를 고친 직후 질문해 옛 내용이 나오는 시간을 잰다.

## 측정과 검증

- **검색.** Recall@k, nDCG@10, 정답 문서의 평균 순위.
- **답.** 근거 충실도, 정답률, "모름" 응답의 정확도.
- **운영.** 질문당 지연과 비용, 색인 반영 지연.
- **비교.** 변경 전후를 같은 평가셋으로, 질문별 대응 비교와 신뢰구간으로 본다([측정 통계](../verify/statistics.md)).

## 재검토 조건

- 문서가 적고 긴 문맥의 비용이 충분히 싸졌다. 검색 없이 전체 투입을 검토한다.
- 질문 대부분이 표 데이터에 관한 것이다. 구조화 질의로 옮긴다.
