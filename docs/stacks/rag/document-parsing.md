# 문서 파싱

확인: 2026-09-27, docling(main) 문서, PyMuPDF(main) 문서, HWP 파서 저장소들(검색으로 확인) 기준.

## 요약

RAG 품질의 상한은 파싱이 정한다.
PDF는 글자를 좌표에 찍은 그림에 가깝고, HWP는 한국 공공·기업 문서의 사실상 표준이지만 범용 파서 대부분이 읽지 못한다.
파싱의 목적은 텍스트 추출이 아니라 **구조(제목, 표, 목록, 읽기 순서)와 출처 정보(문서, 쪽, 개정일, 권한)를 보존한 중간 표현**을 만드는 것이다.

## 문제 신호

- RAG 답변이 틀렸는데, 원문을 보니 표의 행과 열이 섞였거나 2단 편집의 좌우 문단이 섞여 있었다.
- 머리글, 바닥글, 쪽 번호가 본문 중간에 끼어 있다.
- 스캔 PDF에서 텍스트가 전혀 나오지 않는다.
- HWP 파일을 처리하지 못해 PDF로 변환해 쓰고 있다.
- 답변에 인용한 문서가 이미 폐기된 개정판이다.

## 기준선의 한계

기준선은 PDF에서 텍스트만 뽑는 기본 추출(`get_text()` 등)이다.

- PyMuPDF 문서는 기본 추출이 문서에 코딩된 순서대로 나오며, PDF에서는 보통의 읽기 순서가 아니거나 예상치 못한 줄바꿈이 생길 수 있다고 설명한다. 읽기 순서는 PDF를 만든 소프트웨어나 사람의 책임이다.
- 표는 칸 경계가 사라지고 숫자가 한 줄로 이어진다.
- 스캔 PDF는 텍스트 층이 없어 OCR이 필요하다.
- HWP는 기본 추출 대상이 아니다. docling이 지원하는 입력 형식 목록(PDF, Office, HTML, 이미지 등)에도 HWP는 없다.

## 원리

- **PDF는 배치 정보다.** 글자와 좌표, 글꼴이 있을 뿐 문단, 표, 제목의 구조가 없다. 구조는 배치(layout) 분석으로 추정한다.
- **배치 분석 파이프라인.** docling 같은 도구는 형식별 백엔드로 읽고, 배치 분석, 읽기 순서, 표 구조 인식, OCR을 거쳐 통합 문서 표현(DoclingDocument)을 만든다. 이 표현에서 Markdown, HTML, 무손실 JSON으로 내보낸다.
- **표 구조 인식.** 칸의 행·열 좌표와 병합 칸을 복원한다. PyMuPDF의 `find_tables`는 외부 의존성이나 기계학습 없이 표를 찾는다고 설명하고, docling은 모델 기반 표 구조 인식을 쓴다.
- **변환 품질 신호.** docling은 2.34.0부터 문서 변환 품질을 등급(poor, fair, good, excellent)으로 알려주고, 문서는 사람 검토가 필요한 문서를 가려내는 데 쓰라고 한다.
- **HWP 두 형식.** HWP 5.0은 여러 압축 스트림이 든 복합 바이너리이고, HWPX는 OWPML(KS X 6101) 기반의 ZIP+XML이다. 한컴이 공개한 HWP 5.0 바이너리 명세와 OWPML 명세를 근거로 한 오픈소스 파서들(pyhwp, 여러 신규 라이브러리)이 있다.

## 가치

파싱에 투자하는 가치는 **틀린 근거가 검색되는 원인을 입구에서 없애는 것**이다.

- 구조를 보존하면 청크가 제목과 표를 따라 나뉘어, 검색과 답변이 문맥을 잃지 않는다.
- 출처(쪽, 표 번호, 개정일)를 보존하면 답변의 인용이 검증 가능해진다.
- 권한과 삭제 상태를 문서 단위로 붙여 두면 검색 단계에서 걸러낼 수 있다.

## 트레이드오프와 리스크

- **모델 기반 파서는 느리고 무겁다.** 배치 분석과 OCR 모델은 CPU로는 느리고 GPU가 필요할 수 있다. 대량 문서의 초기 적재 시간이 길다.
- **정답이 없는 추정이다.** 배치 분석과 표 인식은 확률적이다. 문서 유형이 바뀌면 품질이 조용히 떨어진다.
- **HWP 파서의 성숙도.** 한국어 문서용 파서는 대부분 개인·소규모 프로젝트이고, 표·수식·도형 처리 수준이 제각각이다. HWP를 PDF로 변환하면 원래 있던 구조(표, 개요 번호)를 잃고 PDF 파싱 문제를 새로 얻는다.
- **OCR 오류.** 스캔 품질, 표 선, 도장, 손글씨가 오류를 만든다. 숫자 하나의 오인식이 답변의 사실 오류가 된다.
- **메타데이터는 파서가 만들어주지 않는다.** 개정일, 효력 상태, 권한, 폐기 여부는 문서 관리 시스템에서 가져와 붙여야 한다. 파일 이름에서 추정하면 틀린다.
- **변환 결과 저장 비용.** 원본, 중간 표현, 청크, 임베딩을 모두 보관하면 저장과 재처리 파이프라인이 커진다. 대신 파서나 청크 규칙을 바꿨을 때 원본부터 다시 돌릴 수 있어야 한다.

## 대안과 경계

| 대안 | 고를 때 |
|---|---|
| 기본 텍스트 추출(PyMuPDF 등) | 문서가 단순한 1단 텍스트이고 표가 없다. 가장 빠르다. |
| 배치 분석 파서(docling 등) | 표, 다단, 머리글이 많은 PDF와 Office 문서다. |
| 원본 형식을 직접 읽기 | DOCX, HTML, HWPX처럼 구조가 있는 형식은 PDF로 바꾸지 말고 원본 구조를 읽는다. |
| 비전 언어 모델로 쪽 이미지를 읽기 | 복잡한 도표, 그림 속 글자, 파서가 실패하는 배치다. 비용과 환각 위험을 함께 잰다. |
| 문서 원천 시스템의 API | 위키, 게시판, DB처럼 원천이 구조화된 데이터면 파일을 파싱하지 않고 원천에서 가져온다. |

## 깊이 있는 활용

- **중간 표현을 보관한다.** 파일 → 구조화된 문서(JSON) → 청크 → 임베딩의 각 단계를 저장한다. 청크 규칙이나 임베딩 모델을 바꿀 때 파싱을 다시 하지 않는다. docling의 무손실 JSON이 이 중간 표현이 된다.
- **문서 유형별로 파이프라인을 나눈다.** 텍스트 층이 있는 PDF는 빠른 추출, 스캔 PDF는 OCR, 표가 많은 보고서는 배치 분석, HWPX는 XML 직접 파싱처럼 유형을 판별해 보낸다. 변환 품질 등급이 낮은 문서는 다른 파이프라인으로 재시도하거나 검토 대기열에 넣는다.
- **표는 표로 넘긴다.** 표를 한 줄 텍스트로 풀지 말고 Markdown 표나 HTML로 유지하고, 행마다 머리글을 반복하거나 "열 이름: 값" 형태로 풀어 쓴 텍스트를 함께 만든다. 숫자 질의의 정확도가 오른다.
- **머리글·바닥글을 걷어낸다.** 모든 쪽에 반복되는 줄을 탐지해 본문에서 빼고 메타데이터로 옮긴다.
- **출처 좌표를 남긴다.** 청크마다 문서 ID, 개정판, 쪽 번호, 표·그림 번호, 가능하면 좌표를 넣는다. 답변 화면에서 원문 위치로 바로 이동할 수 있다.
- **문서 수명 주기를 메타데이터로 둔다.** 개정일, 효력 시작·종료, 대체한 문서, 권한 그룹, 삭제 여부를 문서 관리 시스템에서 가져와 붙인다. 검색은 기본적으로 현행·권한 있는 문서만 대상으로 한다.
- **HWP는 HWPX를 우선한다.** 같은 문서가 HWPX로 있으면 XML을 직접 읽는다. HWP 5.0만 있으면 파서 후보 여러 개를 같은 표본 문서로 비교하고, 표와 개요 번호가 보존되는지 본다.

## 임시방책의 신호

- 모든 문서를 PDF로 바꾼 뒤 텍스트만 뽑는다.
- 답변이 틀리면 프롬프트를 고친다. 원인이 파싱인지는 보지 않는다.
- 파일 이름의 날짜로 최신판을 추정한다.
- 표가 깨진 문서를 "품질이 낮은 문서"로 보고 색인에서 뺀다.
- 파싱 결과를 저장하지 않아, 청크 규칙을 바꿀 때마다 전체를 다시 파싱한다.

## 실패 재현

- **읽기 순서.** 2단 편집 PDF, 머리글이 있는 PDF를 기본 추출과 배치 분석 파서로 각각 파싱해 문단이 섞이는지 본다.
- **표.** 병합 칸, 여러 쪽에 걸친 표, 선이 없는 표를 넣고 행·열이 보존되는지 본다.
- **스캔.** 해상도와 기울기를 바꾼 스캔본으로 OCR 결과의 문자 오류율을 본다.
- **HWP.** 같은 내용을 HWP, HWPX, PDF로 만들어 각 경로의 결과를 비교한다.
- **개정판.** 같은 문서의 옛 판과 새 판을 모두 색인하고, 질의가 옛 판을 인용하는지 본다.

## 측정과 검증

- **대표 문서 표본에 정답을 만든다.** 문서 유형별로 몇십 쪽을 골라 사람이 정답 텍스트와 표를 만든다.
- **텍스트 정확도.** 정답과 추출 결과의 문자 오류율(CER)이나 단어 오류율로 잰다. 숫자만 따로 떼어 오류율을 본다.
- **표 구조.** 표 편집 거리 기반 지표(TEDS 등)나 칸 단위 일치율로 잰다.
- **읽기 순서.** 문단 순서의 일치 정도(순위 상관)를 본다.
- **하류 영향.** 최종 판단은 RAG 평가셋의 근거 검색률 변화로 한다. 파싱을 바꾼 뒤 [LLM 평가](llm-evaluation.md)의 검색 실패 유형이 줄었는지 본다.
- **처리 비용.** 쪽당 처리 시간과 자원을 문서 유형별로 기록한다.

## 재검토 조건

- 문서 유형이 바뀌었다(새 양식, 새 원천). 표본 평가를 다시 한다.
- 변환 품질 등급이 낮은 문서 비율이 늘었다.
- 원천 시스템이 구조화된 API를 제공하기 시작했다. 파일 파싱을 걷어낸다.
