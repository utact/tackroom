# 객체 저장소

확인: 2026-09-28, Amazon S3 사용자 가이드(검색 요약)와 OWASP Cheat Sheet Series(main) 기준. S3 문서 사이트는 조사 환경에서 막혀 있었고, AWS의 공식 문서 저장소는 보관 처리되어 비어 있었다.

## 요약

객체 저장소는 파일을 "버킷 안의 키 → 바이트와 메타데이터" 형태로 저장하고 HTTP로 읽고 쓰는 저장소다.
S3와 그 호환 제품(MinIO, Cloudflare R2, GCS의 XML API 등)이 사실상의 표준이다.
핵심 가치는 **대용량 바이트를 애플리케이션 서버와 DB 밖으로 내보내는 것**이다. 서버는 권한만 발급하고, 바이트는 클라이언트와 저장소가 직접 주고받는다.

## 문제 신호

- 사용자가 올린 이미지, 첨부 파일, 동영상을 DB의 BLOB 열이나 서버 로컬 디스크에 저장하고 있다.
- 서버를 둘 이상으로 늘리자 한 서버에 올린 파일이 다른 서버에서 안 보인다.
- 큰 파일 업로드가 애플리케이션 서버의 메모리, 스레드, 요청 타임아웃을 잡아먹는다.
- DB 백업과 복제가 파일 때문에 느리고 커졌다.
- 컨테이너를 다시 띄우자 업로드한 파일이 사라졌다.

## 기준선의 한계

기준선은 DB BLOB 또는 애플리케이션 서버의 로컬 디스크다.

- **DB BLOB.** 트랜잭션과 함께 저장되어 정합성은 좋다. 대신 백업, 복제, 버퍼 풀이 파일 바이트로 채워지고, 읽을 때마다 DB 연결을 쓴다.
- **로컬 디스크.** 서버가 하나일 때만 맞다. 확장, 컨테이너 재시작, 서버 교체에서 파일이 갈라지거나 사라지고, 웹 루트 안이면 업로드 파일이 실행될 위험도 있다.
- 두 방식 모두 업로드와 다운로드 바이트가 애플리케이션 서버를 지나간다.

## 원리

- **키-값과 평평한 이름 공간.** 디렉터리 없이 키의 접두사로 목록을 흉내 낸다. 객체는 통째로 쓰고 바꾸며, 부분 수정이 없다.
- **강한 일관성.** S3는 2020년 12월부터 모든 요청에서 쓰기 후 읽기 강한 일관성을 제공한다. 새 객체를 쓰거나 덮어쓴 직후의 읽기와 목록 조회가 최신 상태를 본다. (검색 요약으로 확인. 호환 제품은 제품마다 다르다.)
- **조건부 쓰기.** S3는 2024년부터 `If-None-Match: *`(키가 없을 때만 생성)와 `If-Match: <ETag>`(내가 읽은 버전일 때만 덮어쓰기)를 지원한다. 저장소가 비교와 쓰기를 원자적으로 해 준다. (검색 요약으로 확인.)
- **사전 서명 URL.** 서버가 "이 키에 이 메서드를 언제까지"를 서명한 URL을 주면, 클라이언트는 자격 증명 없이 직접 올리거나 받는다. SigV4는 최대 7일이지만, 임시 자격 증명으로 서명했으면 그 만료와 함께 무효가 된다. (검색 요약으로 확인.)
- **멀티파트 업로드.** 큰 객체를 파트로 나눠 병렬로 올리고, 실패한 파트만 다시 올린 뒤 완료 요청으로 합친다. S3의 파트는 5 MiB~5 GiB(마지막 파트는 더 작아도 된다), 파트는 최대 10,000개다. (검색 요약으로 확인.)
- **미완료 멀티파트는 보이지 않는 비용이다.** 완료나 중단되지 않은 멀티파트 업로드의 파트는 저장 요금이 붙지만 객체 목록에는 나오지 않는다. 수명 주기 규칙 `AbortIncompleteMultipartUpload`로 정리한다. (검색 요약으로 확인.)
- **수명 주기와 버전 관리.** 규칙으로 오래된 객체를 싼 저장 등급으로 옮기거나 지운다. 버전 관리를 켜면 덮어쓰기와 삭제가 옛 버전을 남긴다.

## 가치

객체 저장소의 가치는 **바이트의 저장과 전송을 애플리케이션과 DB에서 떼어 내는 것**이다.

- 서버는 상태 없이 늘어나고, 파일은 어느 서버에서도 같은 키로 보인다.
- 사전 서명 URL로 바이트가 서버를 거치지 않아, 큰 파일이 서버 자원을 쓰지 않는다.
- DB에는 키와 메타데이터만 남아 백업과 복제가 가볍다.
- 내구성, 용량 확장, 저장 등급별 비용을 저장소가 맡는다. CDN을 앞에 두면 읽기 부하도 흡수한다.

## 트레이드오프와 리스크

- **DB와 트랜잭션을 공유하지 않는다.** "DB 행 저장"과 "객체 업로드"는 따로 성공하거나 실패한다. 행만 있고 객체가 없거나, 객체만 남는 고아가 생긴다.
- **공개 설정 사고.** 버킷이나 객체를 실수로 공개하면 전체가 노출된다. 권한 모델(버킷 정책, IAM, ACL)이 애플리케이션 권한과 따로 논다.
- **사전 서명 URL은 소지자 권한이다.** URL이 유출되면 만료 전까지 누구나 쓴다. 업로드 URL은 크기와 형식을 서명에 묶지 않으면 아무 내용이나 올라온다.
- **비용 구조가 다르다.** 저장량 외에 요청 수, 외부 전송량, 저장 등급 전환과 조기 삭제 요금이 붙는다. 작은 객체를 많이 만들면 요청 요금이 커진다.
- **호환성의 차이.** "S3 호환"이라도 조건부 쓰기, 일관성, 수명 주기 기능의 지원 범위가 다르다.
- **로컬 개발과 테스트.** 실제 저장소 없이는 동작을 확인하기 어렵다. MinIO나 LocalStack 컨테이너가 필요하다([Testcontainers](../verify/testcontainers.md)).
- **파일 시스템 의미가 없다.** 이름 바꾸기는 복사 후 삭제이고, 부분 수정과 잠금이 없다. 파일 시스템처럼 쓰는 라이브러리(FUSE 마운트)는 이 차이를 숨기다가 성능과 정합성에서 드러난다.

## 대안과 경계

| 대안 | 고를 때 |
|---|---|
| DB BLOB | 파일이 작고(수십 KB 이하) 적으며, 행과 함께 트랜잭션으로 묶여야 한다. |
| 공유 파일 시스템(NFS, EFS) | 기존 프로그램이 파일 경로와 부분 쓰기를 전제로 한다. |
| 로컬 디스크 | 임시 파일, 캐시, 처리 중간 산출물처럼 잃어도 되는 것이다. |
| 관리형 미디어 서비스 | 이미지 변환, 동영상 트랜스코딩, 전송 최적화까지 필요하다. |

## 깊이 있는 활용

- **업로드는 두 단계로.** 서버가 키(UUID)와 `pending` 행을 만들고 사전 서명 URL을 준다. 완료 알림이 오면 객체의 존재와 크기를 확인해 `ready`로 바꾼다([파일 업로드](file-upload.md)).
- **고아를 전제로 청소한다.**
  - 오래된 `pending` 행과 그 객체를 지우는 정리 작업을 둔다.
  - 행을 지울 때 객체 삭제는 [Outbox](../async/outbox-cdc.md)나 작업 큐로 넘겨 재시도한다.
  - 행 없는 객체는 수명 주기 규칙이나 목록 대조로 찾는다.
- **키 설계.** `tenant/{id}/{uuid}`처럼 권한 경계를 접두사에 넣어 정책과 수명 주기 규칙을 건다. 키는 바꾸지 않고, 표시용 파일명은 DB와 `Content-Disposition`에 둔다.
- **조건부 쓰기로 중복과 경쟁을 막는다.** 같은 키에 두 번 쓰면 안 되는 경우 `If-None-Match: *`를 쓴다. 메타데이터 객체를 읽고 고쳐 쓰는 경우 `If-Match`로 낙관적 잠금을 건다([잠금 전략](../api/locking.md)).
- **다운로드도 짧은 사전 서명 URL로.** 버킷은 비공개로 두고, 권한 확인 뒤 수 분짜리 다운로드 URL을 준다. 공개 자산은 CDN 앞단과 별도 버킷으로 분리한다.
- **수명 주기 규칙을 처음부터.** 미완료 멀티파트 정리, 임시 접두사 만료, 오래된 버전 삭제를 버킷 생성 때 함께 둔다.

## 임시방책의 신호

- 업로드 API가 파일 바이트를 받아 서버 메모리에 올린 뒤 저장소로 다시 보낸다.
- 사용자가 준 파일명을 그대로 키나 로컬 경로로 쓴다.
- 서버가 여럿이 되자 공유 볼륨을 마운트해 로컬 디스크 방식을 유지한다.
- 버킷을 공개로 열고 "URL을 추측할 수 없으니 괜찮다"고 한다.
- DB 행을 지우면서 객체 삭제 실패를 무시해 저장 비용이 계속 는다.
- 저장소 호출을 테스트에서 모두 모의 객체로 바꿔 실제 동작을 한 번도 확인하지 않는다.

## 실패 재현

- **고아와 유령.** 사전 서명 URL을 받은 뒤 업로드하지 않거나, 업로드 뒤 완료 알림을 보내지 않는다. 행을 지우는 중 저장소 호출을 실패시킨다([Toxiproxy](../verify/toxiproxy.md)). 정리 작업이 양쪽을 모두 치우는지 본다.
- **미완료 멀티파트.** 멀티파트 업로드를 시작하고 중단 없이 버린다. 객체 목록에는 없지만 미완료 업로드 목록에 남는 것을 확인하고, 수명 주기 규칙으로 정리되는지 본다.
- **URL 남용.** 업로드 URL로 허용 크기보다 큰 파일, 다른 형식의 파일을 올려 본다. 만료 뒤 요청이 거부되는지 본다.
- **경쟁.** 같은 키에 두 클라이언트가 동시에 쓰게 하고, 조건부 쓰기 유무에 따라 결과를 비교한다.
- **실제 저장소로 테스트.** MinIO 컨테이너로 위 시나리오를 통합 테스트에 고정한다.

## 측정과 검증

- **정합성.** DB의 `ready` 행 수와 실제 객체 수, 고아 객체 수와 크기, 오래된 `pending` 수를 주기적으로 대조한다.
- **업로드 성능.** 파일 크기별 업로드 시간과 실패율. 서버 경유 방식과 직접 업로드 방식을 같은 파일로 [k6](../verify/k6.md)에서 비교하고, 서버의 메모리와 스레드 사용을 함께 본다.
- **비용.** 저장량, 요청 수, 외부 전송량, 미완료 멀티파트 용량을 저장 등급별로 본다.
- **보안.** 공개 버킷과 공개 객체가 없는지 정기적으로 검사한다.

## 재검토 조건

- 파일이 작고 적으며 트랜잭션 결합이 중요해졌다. DB 저장을 다시 검토한다.
- 외부 전송 비용이 저장 비용을 넘었다. CDN, 전송 요금이 없는 호환 제품, 캐시 정책을 검토한다.
- 기존 프로그램이 파일 경로를 요구한다. 공유 파일 시스템을 검토한다.

## 출처

- Amazon S3, [Consistency](https://aws.amazon.com/s3/consistency/): 2020년 12월부터 강한 쓰기 후 읽기 일관성. 검색 요약으로 확인했다.
- Amazon S3 사용자 가이드, [Conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html): `If-None-Match`, `If-Match`. 검색 요약으로 확인했다.
- Amazon S3 사용자 가이드, [Multipart upload limits](https://docs.aws.amazon.com/AmazonS3/latest/userguide/qfacts.html)와 [Multipart upload overview](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html): 파트 크기, 파트 수, 미완료 파트 요금. 검색 요약으로 확인했다.
- Amazon S3 사용자 가이드, [Presigned URLs](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html): 최대 유효 기간과 임시 자격 증명의 영향. 검색 요약으로 확인했다.
- Amazon S3 사용자 가이드, [Aborting incomplete multipart uploads](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpu-abort-incomplete-mpu-lifecycle-config.html): 수명 주기 규칙. 검색 요약으로 확인했다.
- OWASP, [File Upload Cheat Sheet](https://github.com/OWASP/CheatSheetSeries/blob/master/cheatsheets/File_Upload_Cheat_Sheet.md): 저장 위치, DB 저장의 절충.
