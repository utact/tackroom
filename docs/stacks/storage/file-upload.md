# 파일 업로드

확인: 2026-09-29 재검토. 최초 조사는 2026-09-28, OWASP Cheat Sheet Series(master), tus 재개 가능 업로드 프로토콜 1.0(main), Amazon S3 사용자 가이드(검색 요약) 기준.

## 요약

파일 업로드는 신뢰할 수 없는 사용자가 보낸 임의의 바이트를 받아 저장하고 다시 내주는 기능이다.
기술 선택의 문제(어디에 저장하고 어떤 경로로 보낼지)와 보안의 문제(무엇을 받아 줄지)가 함께 있다.
직접 업로드는 파일 전송을 저장소에 맡기고 서버가 권한·검증·상태 전이를 관리하는 방식이다. 서버 중계 방식과 비교해 선택하고, 큰 파일이나 불안정한 연결에서는 재개 기능을 검토한다.

## 문제 신호

- 프로필 사진, 첨부 파일, 문서, 동영상을 받아야 한다.
- 큰 파일 업로드가 타임아웃이나 서버 메모리 부족으로 실패한다.
- 모바일 네트워크에서 업로드가 중간에 끊기면 처음부터 다시 올린다.
- 올라온 파일을 다른 사용자가 내려받거나, 서버가 그 파일을 처리(썸네일, 텍스트 추출)한다.

## 기준선의 한계

기준선은 `multipart/form-data`로 애플리케이션 서버가 받아 DB BLOB이나 로컬 디스크에 쓰는 방식이다.

- 바이트가 서버를 지나가며 요청 스레드, 메모리, 임시 디스크를 쓴다. 파일이 크면 프록시와 서버의 요청 크기 제한과 타임아웃에 걸린다.
- 끊기면 처음부터 다시 보낸다.
- 저장 위치의 한계는 [객체 저장소](object-storage.md)의 기준선과 같다.
- 검증을 확장자나 `Content-Type`만으로 하기 쉽다.

## 원리

- **받는 것은 모두 사용자 입력이다.** OWASP 치트 시트는 `Content-Type` 헤더가 사용자가 준 값이라 쉽게 속일 수 있고, 파일 시그니처(매직 바이트) 확인도 단독으로는 충분하지 않다고 한다. 확장자 허용 목록, 시그니처, 내용 검사를 겹겹이 둔다.
- **이름은 서버가 정한다.** 치트 시트는 서버가 무작위 이름(UUID 등)을 만들어 저장하고, 사용자 파일명을 써야 한다면 길이와 허용 문자를 제한하라고 한다. 경로 조작과 덮어쓰기를 막는다.
- **실행되지 않는 곳에 둔다.** 웹 루트 밖이나 다른 호스트에 저장하라고 한다. 웹 서버 설정 파일(`.htaccess`, `web.config`)이 업로드되어 동작을 바꾸는 위험도 경고한다.
- **내용 재작성도 방어의 일부다.** 이미지 재인코딩으로 불필요한 부가 내용을 제거할 수 있지만 파서 취약점과 자원 고갈까지 막는 보장은 아니다. 디코딩 크기·시간 제한과 격리도 적용한다. 압축 파일이 필요하면 해제 후 총 크기, 파일 수와 경로를 제한한다.
- **크기 제한과 권한.** 업로드와 다운로드 크기 제한, 인증된 사용자만 업로드, 파일마다 접근 권한 확인을 요구한다.
- **직접 업로드.** 서버는 [객체 저장소](object-storage.md)의 사전 서명 URL만 발급하고, 바이트는 클라이언트가 저장소로 직접 보낸다.
- **재개 가능 업로드.** tus 프로토콜의 흐름이다.
  1. 업로드를 만들 때 `Upload-Length`로 전체 크기를 알린다.
  2. 끊기면 `HEAD`로 서버가 받은 위치(`Upload-Offset`)를 묻는다.
  3. 그 위치부터 `PATCH`로 이어 보낸다.

  `OPTIONS`를 제외한 요청·응답에는 `Tus-Resumable`을 포함한다. 서버는 알려진 크기 상한이 있으면 `Tus-Max-Size`로 알리는 것이 권장되며, 항상 존재하는 헤더는 아니다. S3 멀티파트도 파트 단위로 재전송할 수 있지만 tus와 다른 프로토콜이다.

## 가치

좋은 업로드 설계의 가치는 **서버 자원, 신뢰 경계, 네트워크 실패를 각자 맞는 곳에서 다루는 것**이다.

- 직접 업로드로 서버 자원이 파일 크기와 무관해진다.
- 서버가 이름, 위치, 상태를 정해 사용자가 저장 구조에 영향을 주지 못한다.
- 재개 가능 업로드로 큰 파일과 불안정한 네트워크에서 재전송량이 끊긴 부분으로 준다.
- 검증과 후처리를 비동기 작업으로 분리해, 업로드 응답이 처리 시간과 무관해진다.

- **학습 실험.** 중단 가능한 업로드와 검증 상태를 만든다. 동일 키 재전송, 업로드 완료 후 상태 저장 실패와 잘못된 파일을 넣어 고아 객체·중복·공개 전 검증을 확인한다.

## 트레이드오프와 리스크

- **상태가 생긴다.** 발급, 업로드 중, 검증 중, 사용 가능, 거부 같은 상태와 그 사이의 실패를 관리해야 한다. 한 요청으로 끝나던 일이 여러 요청과 작업으로 나뉜다.
- **검증 시점이 늦어진다.** 직접 업로드에서는 바이트가 서버를 거치지 않아 받는 순간 검사할 수 없다. 검증 전 파일이 노출되지 않게 격리 접두사나 상태로 막아야 한다.
- **검증 도구의 위험.** 이미지 라이브러리, 문서 파서, 백신 엔진 자체가 악성 파일로 공격받는다. 처리는 격리된 작업자에서 한다.
- **재개 가능 업로드의 운영 부담.** tus 서버나 멀티파트 상태, 미완료 업로드 정리가 추가된다.
- **CORS와 클라이언트 복잡도.** 브라우저가 저장소로 직접 올리려면 저장소 CORS 설정과 클라이언트 코드가 필요하다.

## 대안과 경계

| 대안 | 고를 때 |
|---|---|
| 서버 경유 업로드 | 파일이 작고(수 MB 이하), 받는 즉시 동기적으로 검사해야 한다. |
| 사전 서명 단일 PUT | 파일이 수십~수백 MB이고 재개가 필요 없다. |
| 멀티파트 직접 업로드 | 파일이 크고 병렬 전송과 파트 단위 재시도가 필요하다. |
| tus | 저장소와 무관한 표준 재개 프로토콜과 기존 클라이언트 라이브러리를 원한다. tus 팀이 참여한 IETF 초안(Resumable Uploads for HTTP)이 표준화 중이라, 새로 만든다면 그 진행을 함께 본다. |
| 관리형 업로드 서비스 | 변환과 검사까지 맡기고 싶다. |

## 깊이 있는 활용

- **상태 기계로 만든다.** `requested → uploaded → scanning → ready | rejected`. 업로드 URL은 `requested` 행에만 발급하고, 사용자에게 보여주는 것은 `ready`만이다. 상태 전이는 조건부 갱신(`WHERE status = 'uploaded'`)으로 한 번만 일어나게 한다.
- **격리 접두사.** 업로드는 `incoming/`에 받고, 검증을 통과하면 `files/`로 옮기거나 상태만 바꾼다. `incoming/`은 다운로드 URL 발급 대상에서 빼고, 수명 주기 규칙으로 짧게 만료한다.
- **검증은 작업 큐에서.** 완료 알림이나 저장소 이벤트로 [DB 작업 큐](../async/db-job-queue.md)에 검사 작업을 넣는다. 작업자는 크기, 시그니처, 이미지 재인코딩, 필요하면 백신 검사를 하고, 원본 대신 재인코딩한 결과를 저장한다.
- **서명에 조건을 묶는다.** 업로드 URL의 유효 시간을 짧게 두고, 가능하면 크기 범위와 `Content-Type`을 서명 조건에 넣는다(POST 정책의 `content-length-range` 등). 조건이 없으면 완료 확인 때 실제 객체 크기를 다시 본다.
- **다운로드 응답 헤더를 서버가 정한다.** `Content-Disposition: attachment`와 서버가 정한 `Content-Type`, `X-Content-Type-Options: nosniff`로 브라우저가 업로드 파일을 페이지로 실행하지 않게 한다. 사용자 파일은 서비스와 다른 도메인에서 내준다.
- **재개는 크기로 고른다.** 대부분이 작은 파일이면 단일 PUT으로 두고, 큰 파일만 멀티파트나 tus로 보낸다. 파트 크기는 네트워크 상태에 맞추되 S3 하한(5 MiB)과 파트 수 상한(10,000개)을 함께 맞춘다.

## 임시방책의 신호

- 확장자나 `Content-Type`만 보고 허용한다.
- 사용자 파일명으로 저장 경로를 만든다(`uploads/` + `filename`).
- 큰 파일이 실패하자 서버와 프록시의 요청 크기 제한과 타임아웃만 계속 늘린다.
- 업로드 직후 같은 요청 안에서 썸네일을 만들어 응답이 느려진다.
- 업로드한 파일을 서비스와 같은 도메인에서 `inline`으로 내준다.
- 업로드가 끊기면 처음부터 다시 올리게 한다.

## 실패 재현

- **우회 파일.** 확장자를 바꾼 실행 파일, `Content-Type`을 속인 HTML, 시그니처 뒤에 스크립트를 붙인 이미지, `../`가 든 파일명, 아주 긴 파일명, `.htaccess`를 올려 모두 거부되거나 무해하게 저장되는지 자동 테스트로 고정한다.
- **크기와 폭탄.** 허용보다 큰 파일, 압축 폭탄, 해상도가 극단적인 이미지(픽셀 폭탄)를 올려 서버와 작업자가 견디는지 본다.
- **끊긴 업로드.** 전송 중 연결을 끊고([Toxiproxy](../verify/toxiproxy.md)) 재개했을 때 이어 올리는지, 전송량이 끊긴 이후분만인지 본다.
- **상태 이탈.** 완료 알림 없이 버린 업로드, 검사 작업 실패, 같은 완료 알림 두 번을 만들어 상태가 올바른지 본다.

## 측정과 검증

- **성공률과 재시도.** 파일 크기 구간별 업로드 성공률, 재개 횟수, 재전송 바이트 비율.
- **지연.** 업로드 시작부터 `ready`까지 시간을 단계별(전송, 검사, 후처리)로 나눠 p50, p99를 본다.
- **서버 자원.** 동시 업로드 수를 [k6](../verify/k6.md)로 늘리며 서버 경유 방식과 직접 업로드의 메모리, 스레드, 지연을 비교한다.
- **보안 회귀.** 위 우회 파일 모음을 CI에서 매번 돌려 거부율 100%를 유지한다.
- **정합성.** `pending`, `scanning`에 오래 머문 수와 고아 객체 수.

## 재검토 조건

- 파일이 모두 작고 드물다. 서버 경유 업로드로 단순하게 돌아간다.
- 변환과 검사 요구가 커졌다. 관리형 미디어 서비스를 검토한다.
- 대용량 업로드 실패가 여전히 많다. 파트 크기, 병렬도, 재개 방식을 다시 잰다.

## 출처

- tus, [Protocol 1.0](https://tus.io/protocols/resumable-upload): 2026-09-29 본문 확인. `OPTIONS`의 버전 헤더 예외와 최대 크기 헤더의 선택성을 확인했다.

- OWASP, [File Upload Cheat Sheet](https://github.com/OWASP/CheatSheetSeries/blob/master/cheatsheets/File_Upload_Cheat_Sheet.md): `Content-Type` 위조, 시그니처 확인의 한계, 무작위 파일명과 파일명 제한, 이미지 재작성, 압축 파일 비권장, 웹 루트 밖이나 다른 호스트 저장, `.htaccess`와 `web.config` 위험, 크기 제한, 인증과 권한.
- tus, [Resumable Upload Protocol 1.0](https://github.com/tus/tus-resumable-upload-protocol/blob/main/protocol.md): `HEAD`와 `Upload-Offset`, `PATCH`로 이어 보내기, `Upload-Length`, `Tus-Resumable`, `Tus-Max-Size`.
- Amazon S3 사용자 가이드, [Multipart upload limits](https://docs.aws.amazon.com/AmazonS3/latest/userguide/qfacts.html): 파트 크기와 수. 검색 요약으로 확인했다.
- Amazon S3 API Reference, [POST Policy](https://docs.aws.amazon.com/AmazonS3/latest/API/sigv4-HTTPPOSTConstructPolicy.html): `content-length-range` 조건으로 업로드 크기의 최소·최대를 정함. 검색 요약으로 확인했다(2026-09-29 재검토).
- IETF HTTP WG, [Resumable Uploads for HTTP](https://datatracker.ietf.org/doc/draft-ietf-httpbis-resumable-upload/) 초안: 표준화 중인 재개 업로드(104 응답, `Upload-Complete`). 검색 요약으로 확인했다(2026-09-29 재검토).
