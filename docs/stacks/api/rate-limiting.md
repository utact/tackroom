# 속도 제한

확인: 2026-09-28, IETF RateLimit 헤더 초안(ietf-wg-httpapi/ratelimit-headers, main), nginx 문서(main), Bucket4j 문서(master) 기준.

## 요약

속도 제한은 클라이언트나 키마다 일정 시간에 쓸 수 있는 요청 양을 정하고, 넘으면 늦추거나 거절하는 장치다.
목적은 한 사용자가 공유 자원을 독점하지 못하게 하고, 과부하와 남용에서 시스템을 지키는 것이다.
핵심은 알고리즘보다 **무엇을 키로 나누고, 상태를 어디에 두고, 제한 장치가 죽으면 어떻게 할지**다.

## 문제 신호

- 특정 클라이언트의 폭주나 스크립트가 다른 사용자의 지연을 늘린다.
- 로그인, 비밀번호 재설정, 인증 코드 발송 같은 엔드포인트가 무차별 시도에 노출돼 있다.
- 외부 유료 API(LLM, 문자 발송)를 대신 호출하는 기능이 비용 폭탄이 될 수 있다.
- 요금제별로 사용량 한도를 두어야 한다.

## 기준선의 한계

기준선은 제한 없이 서버 용량과 자동 확장에 맡기는 것이다.

- 확장이 따라가기 전에 폭주가 DB와 하위 시스템을 먼저 무너뜨린다.
- 외부 API 비용과 발송 비용은 확장으로 해결되지 않는다.
- 애플리케이션 메모리의 카운터로 막으면 인스턴스마다 따로 세어, 인스턴스 수만큼 한도가 늘어난다.

## 원리

- **토큰 버킷.** 일정 속도로 차는 토큰을 요청마다 쓴다. 버킷 크기만큼 순간 폭주를 허용하며 평균 속도를 제한한다(Bucket4j의 방식).
- **누수 버킷.** nginx `limit_req`의 방식이다. 초과 요청을 대기열에 넣어 정해진 속도로 흘려보내고, `burst`를 넘으면 거절한다.
  - `burst` 기본값은 0이다. `nodelay`가 없으면 초과 요청은 거절 대신 지연된다.
  - 거절 상태 코드 기본값은 503이다. `limit_req_status 429`로 바꾼다.
  - 상태는 공유 메모리 영역에 둔다. 1MB에 64바이트 상태 약 1만 6천 개가 들어간다.
- **고정 창과 이동 창.** 고정 창(분마다 카운터 초기화)은 단순하지만 창 경계에서 두 배가 통과한다. 이동 창은 경계 효과를 줄인다.
- **분산 상태.** 인스턴스가 여럿이면 카운터를 Redis나 DB 같은 공유 저장소에 두고 원자적으로 갱신한다. Bucket4j 문서는 저장소 장애 시 예외 처리, 백업, 키가 늘어나는 만큼의 만료 설정을 사용자 책임으로 둔다.
- **알려 주기.** IETF 초안은 `RateLimit-Policy`(정책)와 `RateLimit`(남은 양 `r`, 유효 창 `t`) 헤더를 정의한다.
  - 남은 양이 있어도 다음 요청이 성공한다는 보장은 아니다.
  - `Retry-After`가 함께 있으면 그것이 우선한다.
  - 유효 창을 초 단위로 주어 시계 차이와 동시 재시도 쏠림을 줄인다.

## 가치

속도 제한의 가치는 **공유 자원의 공정성을 지키고, 남용과 비용 폭주를 입구에서 끊는 것**이다.

- 한 클라이언트의 폭주가 다른 클라이언트의 지연으로 번지지 않는다.
- 무차별 로그인 시도와 발송 남용의 비용을 공격자 쪽으로 돌린다.
- 한도를 헤더로 알리면 착한 클라이언트는 스스로 속도를 맞춘다.

## 트레이드오프와 리스크

- **키 선택의 함정.** IP로 나누면 회사나 모바일 통신사 뒤의 사용자들이 한도를 공유하고, 공격자는 IP를 바꾼다. 인증된 사용자, API 키, 테넌트 단위가 대개 낫다.
- **제한 장치가 새 장애 지점이다.** Redis가 느려지면 모든 요청이 느려진다. 장애 때 통과시킬지(가용성) 막을지(보호) 미리 정해야 한다.
- **메모리 증가.** 사용자나 IP마다 상태가 생기므로 만료와 최대 크기를 두지 않으면 저장소가 찬다.
- **정확성과 비용.** 요청마다 원격 저장소를 부르면 지연이 늘고, 로컬에서 나눠 세면 한도가 부정확해진다.
- **정상 폭주를 막는다.** 배치 작업, 재시도, 앱 시작 시의 몰림이 한도에 걸린다. 한도와 버스트를 실제 사용 분포로 정해야 한다.
- **거절만으로는 과부하를 못 막는다.** 초안도 제한이 요청 자체를 막지 못한다고 적는다. 거절 처리 비용이 남으므로 부하 차단(load shedding)과 함께 둔다.

## 대안과 경계

| 대안 | 고를 때 |
|---|---|
| API 게이트웨이·프록시의 제한 | 키가 IP나 API 키처럼 요청에서 바로 보인다. 애플리케이션까지 오기 전에 끊는다. |
| 애플리케이션 제한(Bucket4j, Redis) | 키가 인증된 사용자, 테넌트, 요금제처럼 업무 문맥에 있다. |
| 동시성 제한(벌크헤드) | 요청 수가 아니라 동시에 도는 작업 수가 병목이다([Resilience4j](resilience4j.md)). |
| 큐로 평탄화 | 요청을 바로 처리할 필요가 없다. 받아 두고 처리 속도를 조절한다([DB 작업 큐](../async/db-job-queue.md)). |
| 사용량 과금 | 제한보다 비용으로 사용을 조절한다. 한도는 사기 방지용으로만 둔다. |

## 깊이 있는 활용

- **층을 나눈다.** 프록시에서 IP 단위의 굵은 제한으로 명백한 폭주를 끊고, 애플리케이션에서 사용자·테넌트 단위의 정확한 제한을 둔다.
- **민감한 엔드포인트는 따로.** 로그인은 계정 단위와 IP 단위 제한을 함께 두고, 실패 횟수로 제한한다. 인증 코드 발송은 전화번호 단위로 제한한다.
- **비용에 비례해 센다.** LLM 호출은 요청 수가 아니라 토큰 수로 센다. 초안의 할당 단위(`qu`)도 요청 수 외의 단위를 허용한다.
- **원자적으로 갱신한다.** Redis에서는 확인과 차감을 Lua 스크립트 하나로 한다. 확인 후 차감을 따로 하면 동시 요청이 한도를 넘는다.
- **거절 응답을 표준으로.** 429와 `Retry-After`, 가능하면 `RateLimit` 헤더를 준다. 클라이언트 SDK는 이를 존중해 지터를 둔 백오프로 재시도한다([타임아웃·재시도·멱등 키](timeout-retry-idempotency.md)).
- **먼저 기록만 한다.** nginx의 `limit_req_dry_run`처럼 막지 않고 초과만 세는 모드로 실제 분포를 보고 한도를 정한다.

## 임시방책의 신호

- 인스턴스 메모리의 `HashMap`으로 사용자별 요청 수를 센다. 인스턴스가 늘면 한도도 는다.
- `if (count > limit)`를 읽고 나서 `count++`를 따로 한다.
- 제한 저장소 장애 때 모든 요청이 500으로 실패한다.
- 로그인 무차별 시도를 IP 차단 목록을 손으로 관리해 막는다.
- 거절 응답이 500이나 빈 200이라, 클라이언트가 곧바로 다시 시도한다.

## 실패 재현

- **경쟁.** 한도 10인 키에 동시 요청 100개를 보내 통과 수를 센다. 비원자적 구현에서 10을 넘는 것을 확인하고, 원자적 구현으로 반복한다.
- **분산 누수.** 인스턴스 셋 뒤에서 같은 키로 요청해, 인스턴스별 카운터라면 한도의 세 배가 통과하는 것을 본다.
- **저장소 장애.** [Toxiproxy](../verify/toxiproxy.md)로 Redis를 늦추고 끊어, 요청 지연과 정한 장애 정책(통과 또는 거절)대로 동작하는지 본다.
- **창 경계.** 고정 창 경계 직전과 직후에 몰아 보내 두 배가 통과하는지 본다.

## 측정과 검증

- **거절률.** 키별, 엔드포인트별 429 비율. 정상 사용자의 거절이 늘면 한도가 너무 낮다.
- **정확도.** 한도 대비 실제 통과 수의 초과율.
- **오버헤드.** 제한 검사에 드는 지연(p99)과 저장소 호출 수.
- **보호 효과.** 폭주 시험에서 제한이 있을 때와 없을 때 다른 사용자의 지연을 [k6](../verify/k6.md)로 비교한다.

## 재검토 조건

- 제한 검사가 요청 지연의 큰 부분이 됐다. 로컬 근사와 주기적 동기화를 검토한다.
- 거절이 대부분 정상 사용자다. 키와 한도를 실제 분포로 다시 정한다.

## 출처

- IETF, [RateLimit header fields for HTTP](https://github.com/ietf-wg-httpapi/ratelimit-headers/blob/main/draft-ietf-httpapi-ratelimit-headers.md): `RateLimit-Policy`와 `RateLimit`, 할당 단위와 분할 키, 남은 양이 보장이 아님, `Retry-After` 우선, 제한이 요청을 막지 못한다는 보안 고려.
- nginx 문서, [ngx_http_limit_req_module](https://github.com/nginx/nginx.org/blob/main/xml/en/docs/http/ngx_http_limit_req_module.xml): 누수 버킷, `burst` 기본 0, `nodelay`, 거절 코드 기본 503, 공유 메모리 크기, `limit_req_dry_run`.
- Bucket4j, [Distributed usage checklist](https://github.com/bucket4j/bucket4j/blob/master/asciidoc/src/main/docs/asciidoc/distributed/distributed-checklist.adoc): 분산 저장소 장애 시 예외 처리, 백업, 키별 상태의 만료와 최대 크기.
