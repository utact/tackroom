# Flink

확인: 2026-09-27, Apache Flink release-2.3.0 문서와 flink-connector-kafka(main) 문서 기준.

## 요약

Flink는 끝없이 들어오는 사건 흐름을 상태를 가진 연산으로 계속 처리하는 스트림 처리 엔진이다.
분산 스냅샷(체크포인트)으로 연산자 상태와 입력 위치를 함께 저장해, 장애가 나도 상태를 정확히 한 번 반영한 것처럼 복구한다.
사건 시간(event time)과 워터마크로 늦게 도착한 사건까지 올바른 시간 창에 넣는다. "지금 이 순간의 집계"를 배치 주기 없이 유지하는 것이 핵심 가치다.

## 문제 신호

- 몇 분~몇 초 단위의 실시간 집계(이상 거래 탐지, 실시간 대시보드, 사용량 과금)가 필요하다.
- 배치 주기(시간, 일)가 지연 요구를 맞추지 못한다.
- 사건이 순서 없이, 늦게 도착하는데 사건이 일어난 시각 기준으로 집계해야 한다.
- 사건 흐름 둘을 시간 조건으로 붙여야 한다(주문과 결제 맞추기).
- 소비자 코드 안에서 상태(카운터, 세션)를 직접 관리하다 장애 때 상태를 잃는다.

## 기준선의 한계

기준선은 배치 집계([Spring Batch](../batch/spring-batch.md), [Airflow](../batch/airflow.md))나, 큐 소비자에서 직접 집계하는 코드다.

- 배치는 주기만큼 늦다. 주기를 줄이면 매번 전체를 다시 읽는다.
- 소비자 코드의 메모리 상태는 재시작하면 사라지고, DB에 두면 사건마다 쓰기가 생긴다. 상태 저장과 입력 위치 커밋이 원자적이지 않아 장애 후 중복이나 누락이 생긴다.
- 늦게 온 사건을 어느 시간 창에 넣을지, 창을 언제 닫을지를 직접 만들어야 한다.

## 원리

- **상태를 가진 연산자.** 연산자가 키별 상태(카운터, 목록, 맵)를 가지고, 상태는 상태 백엔드(힙 또는 RocksDB 등)에 저장된다.
- **체크포인트와 배리어.** 소스가 데이터 흐름에 배리어를 끼워 넣고, 배리어는 레코드를 앞지르지 않고 함께 흐른다. 각 연산자는 배리어를 받으면 상태를 스냅샷한다. 문서는 배리어가 가볍고 흐름을 멈추지 않는다고 설명한다. 장애가 나면 마지막 완료된 체크포인트의 상태와 입력 위치로 되돌아가 다시 처리한다. Flink 내부 상태 기준으로 정확히 한 번이다.
- **체크포인트와 세이브포인트.** 문서는 체크포인트를 DB의 복구 로그, 세이브포인트를 백업에 비유한다. 체크포인트는 Flink가 만들고 지우는 장애 복구용이고, 세이브포인트는 사용자가 만들어 버전 업그레이드와 작업 변경에 쓴다.
- **연산자 ID.** 세이브포인트에서 상태를 되살릴 때 연산자 ID로 상태를 찾는다. 문서는 `uid(String)`로 ID를 지정할 것을 강하게 권한다. 지정하지 않으면 작업 구조가 바뀔 때 상태를 찾지 못한다.
- **사건 시간과 워터마크.** 워터마크는 "이 시각 이전의 사건은 대체로 다 왔다"는 진행 신호다. 워터마크가 지난 뒤 도착한 사건은 늦은 사건이고, 허용 지연(allowed lateness)으로 처리 방식을 정한다.
- **외부 시스템까지의 정확히 한 번.** Kafka 싱크의 기본 보장은 `NONE`이다. `EXACTLY_ONCE`는 체크포인트 때 커밋되는 Kafka 트랜잭션에 쓰므로, `read_committed` 소비자는 체크포인트가 끝나야 데이터를 본다. 문서는 Kafka 트랜잭션 타임아웃을 최대 체크포인트 시간 + 최대 재시작 시간보다 크게 두지 않으면 커밋되지 않은 트랜잭션이 만료돼 데이터를 잃을 수 있다고 경고한다.

## 가치

Flink의 가치는 **상태와 입력 위치를 함께 스냅샷해, 연속 처리에서도 장애 복구 후 결과가 맞게 하는 것**이다.

- 수십억 건의 키별 상태를 유지하면서 사건마다 결과를 갱신한다.
- 늦게 온 사건을 사건 시간 기준으로 올바른 창에 넣는다.
- 세이브포인트로 상태를 보존한 채 코드를 바꾸고 다시 시작한다.
- SQL(Table API)로 스트림을 테이블처럼 질의한다.

그래서 Flink가 맞는 상황은 지연 요구가 초~분 단위이고, 상태가 크고, 결과의 정확성이 중요한 경우다.

## 트레이드오프와 리스크

- **운영이 어렵다.** 클러스터(JobManager, TaskManager), 상태 백엔드, 체크포인트 저장소, 역압(backpressure) 튜닝, 버전 업그레이드가 모두 새 일이다.
- **상태 스키마 변경.** 상태의 타입이 바뀌면 세이브포인트 호환이 깨질 수 있다. 연산자 ID를 빼먹으면 구조 변경 때 상태를 잃는다.
- **정확히 한 번의 대가는 지연이다.** 트랜잭션 싱크는 체크포인트 주기만큼 결과가 늦게 보인다. 체크포인트를 자주 하면 부하가, 드물게 하면 지연이 는다.
- **워터마크 설계가 정확성과 지연을 맞바꾼다.** 기다리는 시간을 길게 잡으면 늦은 사건을 더 받지만 결과가 늦고, 짧게 잡으면 빠르지만 늦은 사건을 버린다. 입력 파티션 하나가 멈추면 워터마크 전체가 멈출 수 있다(유휴 소스 처리가 필요하다).
- **역압과 체크포인트.** 처리가 밀리면 배리어도 밀려 체크포인트가 오래 걸리거나 실패한다.
- **배치로 충분한 문제에 과하다.** 지연 요구가 시간 단위면 배치가 훨씬 싸다.

## 대안과 경계

| 대안 | 고를 때 |
|---|---|
| 배치 집계 | 지연 요구가 시간·일 단위다. |
| Kafka Streams | 입력과 출력이 모두 Kafka이고, 별도 클러스터 없이 애플리케이션 라이브러리로 돌리고 싶다. |
| 소비자 + DB 상태 | 상태가 작고, 사건당 DB 쓰기를 감당한다. 처리 결과와 offset을 같은 트랜잭션에 쓰면 정확성을 얻는다([Kafka](../async/kafka.md)). |
| 실시간 OLAP DB(ClickHouse 등) | 사건을 바로 적재하고 질의 시점에 집계해도 지연 요구를 맞춘다. (미검증: 이 조사에서는 비교하지 않았다.) |

## 깊이 있는 활용

- **모든 상태 연산자에 `uid`를 준다.** 처음부터 붙이면 나중의 구조 변경, 연산자 추가, 버전 업그레이드에서 세이브포인트로 상태를 이어간다.
- **업그레이드는 세이브포인트로.** 작업을 세이브포인트와 함께 멈추고, 새 버전을 그 세이브포인트에서 시작한다. 상태 스키마 변경은 호환 가능한 직렬화 형식(Avro, POJO 규칙)으로 한다.
- **트랜잭션 타임아웃을 계산한다.** Kafka 싱크 `EXACTLY_ONCE`라면 `transaction.timeout.ms`를 최대 체크포인트 시간 + 최대 재시작 시간보다 크게, 브로커의 최대 트랜잭션 타임아웃보다는 작게 둔다. 작업마다 고유한 트랜잭션 ID 접두어를 쓴다.
- **정확히 한 번이 필요 없으면 멱등 싱크로.** 결과를 키로 upsert하는 싱크(DB, 압축 토픽)는 at-least-once로도 결과가 같다. 지연과 운영이 단순해진다.
- **워터마크 지연은 데이터로 정한다.** 사건 시각과 도착 시각의 차이 분포를 재고, 원하는 백분위(예: p99.9)를 워터마크 지연으로 삼는다. 그 너머의 늦은 사건은 부수 출력(side output)으로 모아 보정 배치로 처리한다.
- **유휴 입력을 처리한다.** 일부 파티션에 사건이 없을 때 워터마크가 멈추지 않게 유휴 감지(`withIdleness`)를 둔다.
- **큰 상태는 RocksDB와 증분 체크포인트로.** 힙에 안 들어가는 상태는 RocksDB 백엔드와 증분 체크포인트로 체크포인트 크기와 시간을 줄인다.

## 임시방책의 신호

- 실시간 집계를 1분 주기 배치로 흉내 내고, 주기를 계속 줄인다.
- 소비자 메모리에 카운터를 두고, 재시작 뒤 값이 틀어지는 것을 "잠깐이니까" 넘긴다.
- 연산자 `uid` 없이 운영하다, 코드 변경 후 상태를 잃고 처음부터 다시 돌린다.
- 늦은 사건이 버려지는 것을 모른다. 결과가 배치 결과와 조금씩 다르다.
- `EXACTLY_ONCE` 싱크를 켜고 결과가 늦게 보이는 이유를 모른다.

## 실패 재현

- **장애 복구 정확성.** 체크포인트 사이에 TaskManager를 죽이고, 복구 후 결과(키별 합계)가 장애 없는 실행과 같은지 비교한다. 싱크 보장(`NONE`, `AT_LEAST_ONCE`, `EXACTLY_ONCE`)별로 중복을 센다.
- **트랜잭션 만료.** Kafka 트랜잭션 타임아웃을 체크포인트 시간보다 짧게 두고, 체크포인트를 느리게 만들어 데이터 유실이 나는지 본다.
- **늦은 사건.** 사건 시각을 과거로 섞은 입력을 넣어, 워터마크 지연 설정별로 버려지는 사건 수를 센다.
- **유휴 파티션.** 파티션 하나에 입력을 끊어 워터마크와 창 출력이 멈추는지 보고, 유휴 감지로 해결되는지 본다.
- **세이브포인트 호환.** `uid`가 없는 작업에 연산자를 추가하고 세이브포인트에서 시작해 상태를 잃는 것을 확인한다.

## 측정과 검증

- **정확성은 배치 결과와 대조한다.** 같은 입력을 배치로 집계한 결과를 정답으로 두고, 스트림 결과와의 차이(늦은 사건으로 인한 차이 포함)를 잰다.
- **종단 지연.** 사건 시각에서 결과 반영까지의 지연을 p50, p99로 본다. 싱크 보장 방식과 체크포인트 주기에 따라 비교한다.
- **체크포인트 상태.** 체크포인트 소요 시간, 크기, 실패 수, 정렬 대기 시간을 본다.
- **역압.** 연산자별 역압 비율과 입력 소비 지연(Kafka lag)을 본다.

## 재검토 조건

- 지연 요구가 시간 단위로 완화됐다. 배치로 돌아간다.
- 입력과 출력이 모두 Kafka이고 상태가 작다. Kafka Streams나 소비자 + DB로 단순화한다.

- Apache Flink 2.3.0, [Checkpoints vs. Savepoints](https://github.com/apache/flink/blob/release-2.3.0/docs/content/docs/ops/state/checkpoints_vs_savepoints.md), [Savepoints](https://github.com/apache/flink/blob/release-2.3.0/docs/content/docs/ops/state/savepoints.md): 복구 로그와 백업의 비유, `uid` 지정 권고.
