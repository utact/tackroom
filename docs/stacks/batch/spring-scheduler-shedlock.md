# Spring 스케줄러와 ShedLock

확인: 2026-09-27, Spring Framework 7.0.9 문서, Spring Boot 4.1.1 소스, ShedLock 7.9.0 README 기준.

## 요약

Spring의 `@Scheduled`는 애플리케이션 안에서 정해진 시각이나 간격으로 메서드를 실행한다.
ShedLock은 여러 인스턴스가 같은 스케줄을 가질 때, 공유 저장소(DB 등)의 잠금 행으로 한 인스턴스만 실행하게 한다.
둘을 합치면 "하루 한 번 정산"을 새 인프라 없이 여러 인스턴스 환경에서 돌릴 수 있다. 다만 ShedLock은 잠금일 뿐 스케줄러가 아니다.

## 문제 신호

- 매일 새벽 집계, 만료 데이터 정리, 외부 시스템 동기화처럼 시각에 따라 도는 작업이 있다.
- 인스턴스를 둘 이상으로 늘렸더니 정기 작업이 두 번씩 돈다.
- 서버의 crontab에 `curl`로 내부 API를 부르는 줄이 늘어난다.

## 기준선의 한계

기준선은 OS cron이다.

- 서버 한 대의 crontab에 두면 그 서버가 죽으면 작업도 없다. 모든 서버에 두면 여러 번 돈다.
- 컨테이너와 오토스케일 환경에서는 "그 서버"가 없다.
- 실행 이력, 실패 알림, 재시도가 없다. 로그 파일을 뒤져야 한다.
- 애플리케이션 코드와 배포 주기가 분리돼, 작업 로직과 스케줄이 따로 논다.

## 원리

- **`@Scheduled`.** `fixedDelay`는 이전 실행이 끝난 뒤 간격을 두고, `fixedRate`는 시작 시각 기준으로 간격을 둔다. `cron`은 6개 필드(초 포함) 표현식이고, `zone`으로 시간대를 정한다.
- **스레드 하나가 기본이다.** Spring Boot의 스케줄링 스레드 풀 크기 기본값은 1이다. 한 작업이 오래 걸리면 다른 모든 스케줄 작업이 밀린다.
- **ShedLock의 동작.** `@SchedulerLock` 메서드는 실행 전에 공유 저장소의 잠금 행을 "만료됐으면 내 것으로" 갱신한다. 성공한 인스턴스만 실행하고, 나머지는 기다리지 않고 건너뛴다.
- **시간 기반 잠금.**
  - `lockAtMostFor`는 실행 노드가 죽었을 때의 안전망이다. 지나면 잠금이 무조건 풀리므로, 정상 실행 시간보다 훨씬 길게 둔다. 작업이 더 오래 걸리면 두 노드가 동시에 실행한다.
  - `lockAtLeastFor`는 아주 짧은 작업이 노드 간 시계 차이로 두 번 도는 것을 막는다.
- **시계 가정.** ShedLock은 노드들의 시계가 동기화돼 있다고 가정한다. JDBC 제공자는 `usingDbTime()`으로 DB 시각을 기준으로 쓸 수 있다.

## 가치

이 조합의 가치는 **새 인프라 없이 "여러 인스턴스 중 한 곳에서, 정해진 때에" 실행하는 것**이다.

- 작업 코드와 스케줄이 애플리케이션과 함께 버전 관리되고 배포된다.
- 이미 쓰는 DB 테이블 하나로 중복 실행을 막는다.
- 대부분의 서비스가 가진 정기 작업(수십 개 이하, 분~일 단위, 몇 분 안에 끝남)에는 이걸로 충분하다.

## 트레이드오프와 리스크

- **놓친 실행은 다시 하지 않는다.** 배포나 장애로 모든 인스턴스가 내려가 있던 동안의 실행은 사라진다. `@Scheduled`에는 "놓친 실행을 보충하는" 개념이 없다.
- **ShedLock은 건너뛴다.** 잠금이 잡혀 있으면 다른 노드는 기다리지 않고 건너뛴다. 이전 실행이 길어져 다음 주기와 겹치면 그 주기는 실행되지 않는다.
- **`lockAtMostFor`보다 길어지면 중복 실행이다.** 시간 기반 잠금의 본질적 한계다. 작업 시간의 분포가 넓으면 값을 정하기 어렵다.
- **작업이 멱등해야 한다.** README는 ShedLock이 "병렬로 실행될 준비는 안 됐지만 반복 실행은 안전한" 작업을 위한 것이라고 적는다. 반복 실행이 위험한 작업에는 맞지 않는다.
- **잠금 행을 손으로 지우면 안 된다.** README는 ShedLock이 잠금 행 존재를 메모리에 캐시하므로, 지우면 재시작 전까지 다시 만들어지지 않는다고 경고한다.
- **실행 이력과 재시도가 없다.** 실패 알림, 재실행, 진행 상황은 직접 만들어야 한다.
- **스케줄 시각에 부하가 몰린다.** 모든 인스턴스가 같은 시각에 깨어나 잠금 경쟁을 한다. 스케줄이 많으면 정각마다 DB에 잠금 쿼리가 몰린다.

## 대안과 경계

| 대안 | 고를 때 |
|---|---|
| [Quartz](quartz.md) | 놓친 실행 처리(misfire), 클러스터 모드, 동적 스케줄 추가, 작업별 영속 이력이 필요하다. |
| [DB 작업 큐](../async/db-job-queue.md), db-scheduler | 작업이 시각뿐 아니라 사건으로도 생기고, 재시도와 죽은 작업 감지가 필요하다. ShedLock README도 분산 스케줄러가 필요하면 db-scheduler나 JobRunr을 쓰라고 한다. |
| [Spring Batch](spring-batch.md) | 작업 자체가 대량 데이터를 나눠 처리하고 실패 지점에서 재개해야 한다. 실행 시점은 이 문서의 방식이나 외부 스케줄러가 정한다. |
| [Airflow](airflow.md) | 여러 단계의 의존성, 실행 이력, 과거 구간 재실행이 필요하다. |
| Kubernetes CronJob | 작업을 별도 컨테이너로 실행하고, 동시 실행 정책(`concurrencyPolicy`)과 놓친 실행 기한을 인프라에서 정한다. |

## 깊이 있는 활용

- **스레드 풀을 늘리거나 작업을 분리한다.** 스케줄 작업이 여럿이면 `spring.task.scheduling.pool.size`를 늘린다. 오래 걸리는 작업은 스케줄러 스레드에서 실행하지 말고 별도 실행기로 넘긴다.
- **`lockAtMostFor`는 작업 시간 분포의 최대값보다 넉넉히, 긴 작업은 연장한다.** ShedLock의 `KeepAliveLockProvider`는 `lockAtMostFor` 구간 중간에 잠금을 연장한다. 연장이 있어도 멈춘 프로세스(GC 정지)는 막지 못하므로, 작업은 여전히 중복 실행에 안전해야 한다.
- **DB 시각을 쓴다.** `usingDbTime()`으로 노드 시계 차이를 없앤다.
- **"놓친 실행"은 작업이 스스로 메운다.** 마지막으로 처리한 구간을 DB에 기록하고, 실행될 때마다 그 이후부터 지금까지를 처리한다. 놓친 실행과 중복 실행이 모두 무해해진다.
- **cron의 시간대를 명시한다.** `zone`이 없으면 서버 기본 시간대를 따라, UTC 컨테이너에서 "새벽 3시"가 한국 시각 정오가 된다. 일광 절약 시간 지역에서는 한 시각이 두 번 오거나 오지 않는다.
- **정각을 피한다.** 여러 스케줄을 몇 분씩 어긋나게 두어 DB와 하위 시스템에 부하가 몰리지 않게 한다.
- **실행 결과를 지표로 남긴다.** 작업마다 마지막 성공 시각, 소요 시간, 처리 건수를 기록하고, "마지막 성공 이후 경과 시간"에 경보를 건다. 실패보다 "안 돌았다"가 더 잘 숨는다.

## 임시방책의 신호

- 인스턴스가 늘자 "스케줄러용 인스턴스"를 하나 따로 띄우고 환경 변수로 켠다. 그 인스턴스가 죽으면 작업이 멈춘다.
- 중복 실행이 나자 `lockAtMostFor`를 몇 시간으로 늘린다.
- 작업이 겹치자 cron 간격만 늘린다.
- 놓친 실행을 사람이 기억해서 수동으로 API를 호출한다.
- 모든 스케줄 작업이 스레드 하나를 나눠 쓰고, 한 작업이 느려지면 전부 밀린다.

## 실패 재현

- **중복 실행.** 인스턴스 두 개를 같은 스케줄로 띄우고, ShedLock 없이와 있을 때 실행 횟수를 센다.
- **잠금 만료 중복.** `lockAtMostFor`를 작업 시간보다 짧게 두고, 두 번째 인스턴스가 잠금을 잡아 겹쳐 실행되는지 본다.
- **노드 사망.** 작업 도중 실행 노드를 `kill -9`로 죽이고, `lockAtMostFor`가 지난 다음 주기에 다른 노드가 실행하는지 본다. 그 사이 주기가 사라지는 것도 확인한다.
- **스레드 기아.** 풀 크기 1에서 한 작업에 `sleep`을 넣고 다른 작업의 실제 실행 시각이 밀리는 것을 본다.
- **시간대.** 컨테이너 시간대를 UTC로 두고 `zone` 없는 cron의 실제 실행 시각을 확인한다.
- **시계 차이.** 한 노드의 시계를 몇 초 틀어 놓고 짧은 작업이 두 번 도는지 본다. `lockAtLeastFor`나 `usingDbTime()`으로 반복한다.

## 측정과 검증

- **실행 횟수는 전수로 센다.** 작업 실행 기록 테이블에 주기마다 실행 수를 남기고, 한 주기에 0이나 2 이상인 경우를 센다.
- **지연.** 예정 시각과 실제 시작 시각의 차이를 작업별로 본다.
- **소요 시간 분포.** 작업별 소요 시간의 p99와 최대값을 `lockAtMostFor`, 스케줄 간격과 비교한다. 최대값이 간격에 가까워지면 설계를 바꿀 때다.
- **처리 누락.** "마지막 처리 구간" 방식이라면 처리되지 않은 구간이 있는지 데이터로 검증한다.

## 재검토 조건

- 놓친 실행을 보충해야 하는 요구가 생겼다. Quartz나 작업 큐를 검토한다.
- 작업 시간이 스케줄 간격에 가까워졌거나 분포가 넓어 `lockAtMostFor`를 정하기 어렵다.
- 작업 간 의존성(A가 끝나면 B)이 생겼다.
- 작업 수가 늘어 실행 이력과 재실행 도구가 필요해졌다.
