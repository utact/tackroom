# WebSocket

확인: 2026-09-28, MDN(mdn/content, main), nginx.org 문서(main), Spring Framework 7.0.9 문서 기준.

## 요약

WebSocket은 HTTP 요청으로 시작해 프로토콜을 전환(Upgrade)한 뒤, 하나의 TCP 연결 위에서 서버와 클라이언트가 아무 때나 양방향으로 메시지를 주고받는 방식이다.
채팅의 전송 계층으로 가장 먼저 떠올리는 기술이지만, WebSocket은 **전송**만 준다. 메시지 저장, 순서, 재연결 뒤 이어받기, 여러 인스턴스 사이의 전파는 모두 그 위에 설계해야 한다.
채팅을 폴링으로 만드는 실수와 WebSocket만 붙이면 채팅이 된다는 실수는 같은 뿌리다. 전달과 정합성을 나눠 보지 않는 것이다.

## 문제 신호

- 채팅, 입력 중 표시, 읽음 표시, 협업 편집, 실시간 게임처럼 양쪽이 자주 짧은 메시지를 주고받는다.
- 폴링으로 만든 채팅의 요청 수와 지연이 감당 범위를 넘었다([폴링과 롱 폴링](polling.md)).
- 클라이언트에서 서버로 가는 메시지도 초 단위보다 잦다.
- 이진 데이터를 실시간으로 주고받는다.

## 기준선의 한계

기준선은 폴링, 그리고 한 방향 푸시인 [SSE](sse.md)다.

- 폴링은 요청 수와 지연이 간격에 묶인다.
- SSE는 서버 → 클라이언트는 푸시지만 클라이언트 → 서버는 요청마다 HTTP 왕복이다. 입력 중 표시처럼 잦은 짧은 신호에는 요청 비용이 크다.

## 원리

- **HTTP/1.1 Upgrade 핸드셰이크.** 클라이언트가 `Upgrade: websocket` 헤더와 무작위 키를 보내고, 서버가 101 응답과 키에서 계산한 값을 돌려주면 연결이 WebSocket으로 바뀐다. 이후 프레임 단위로 주고받는다. HTTP/2·3의 연결 절차와는 구분한다.
- **프록시는 명시적으로 넘겨야 한다.** nginx 문서는 `Upgrade`가 홉 단위(hop-by-hop) 헤더라 역방향 프록시가 그대로 전달하지 않으므로, `Upgrade`와 `Connection` 헤더를 명시적으로 설정해야 한다고 설명한다. 기본적으로 60초 동안 데이터가 없으면 연결을 닫으므로, 타임아웃을 늘리거나 서버가 ping 프레임을 주기적으로 보내라고 한다.
- **ping과 pong.** 제어 프레임으로 연결이 살아 있는지 확인한다. ping을 받은 쪽은 가능한 빨리 pong을 보낸다.
- **보내기는 비동기다.** MDN은 `send()`가 전송을 기다리지 않고 내부 버퍼에 넣을 뿐이라고 설명한다. `WebSocket` 인터페이스는 역압(backpressure)을 지원하지 않아, 메시지가 처리보다 빨리 오면 메모리가 차거나 CPU를 다 쓴다.
- **재연결은 없다.** 오류로 닫히면 `close` 이벤트만 온다. 재연결, 백오프, 끊긴 동안의 복구는 애플리케이션 몫이고, SSE의 `Last-Event-ID` 같은 표준 이어받기가 없다.
- **Origin 검사.** 브라우저는 핸드셰이크에 `Origin`을 보낸다. 쿠키 인증을 쓰면서 이를 검사하지 않으면 다른 사이트가 사용자 권한으로 연결을 연다.
- **STOMP 같은 하위 프로토콜.** Spring은 WebSocket 위에 STOMP로 구독·발행 모델을 얹는다.
  - 내장 단순 브로커는 메모리에서 일부 명령만 지원해 클러스터에 맞지 않는다. 여러 인스턴스에서는 외부 브로커(RabbitMQ 등)로 중계한다.
  - 서버 → 클라이언트 전송이 스레드 풀에서 처리돼 순서가 바뀔 수 있다. 순서가 필요하면 `setPreservePublishOrder`를 켠다.

## 가치

WebSocket의 가치는 **양방향으로 잦은 작은 메시지를 연결 하나로 싸게 주고받는 것**이다.

- 요청마다 헤더와 인증을 반복하지 않는다.
- 입력 중 표시, 읽음 표시, 실시간 커서처럼 버려도 되는 잦은 신호를 가볍게 흘린다.
- 이진 프레임을 주고받는다.

채팅에서 WebSocket의 역할은 "빠른 전달"이다. "메시지가 사라지지 않고 순서대로 한 번 보인다"는 성질은 저장소와 순번이 지킨다.

- **학습 실험.** 협업 화면의 양방향 메시지를 만들고 느린 수신자와 재연결을 재현한다. 송신 큐 크기, 전달 지연, 복구 후 누락을 기록해 연결 유지와 업무 메시지 복구의 차이를 설명한다.

## 트레이드오프와 리스크

- **상태 있는 연결.** 연결이 인스턴스에 묶여, 배포마다 모든 연결이 끊기고 재연결이 몰린다. 인스턴스를 늘려도 기존 연결은 옮겨 가지 않는다.
- **인스턴스 간 전파가 필요하다.** A 인스턴스에 붙은 사용자가 보낸 메시지를 B 인스턴스에 붙은 사용자에게 전하려면 공유 경로(Redis Pub/Sub, 브로커)가 있어야 한다. 단순 브로커는 인스턴스 하나에서만 동작한다.
- **메시지 유실.** 전송 중 끊기면 양쪽 모두 상대가 받았는지 모른다. 전파에 흔히 쓰는 Redis Pub/Sub은 구독자가 없으면 메시지를 저장하지 않는다.
- **순서.** 인스턴스 간 전파와 서버 쪽 스레드 풀이 순서를 바꿀 수 있다.
- **중간 장치.** 프록시 설정 누락, 유휴 타임아웃, 기업 프록시의 WebSocket 차단이 연결 실패의 흔한 원인이다.
- **역압 부재.** 느린 클라이언트에게 보낼 메시지가 서버 메모리에 쌓인다.
- **운영 관측이 어렵다.** 요청 단위 로그와 지표가 없다. 연결 수, 메시지 처리량, 연결 수명을 따로 계측해야 한다.

## 대안과 경계

| 대안 | 고를 때 |
|---|---|
| [폴링과 롱 폴링](polling.md) | 사용자와 메시지가 적고, 운영 단순성이 중요하다. |
| [SSE](sse.md) + POST | 클라이언트가 보내는 일이 드물다. 재연결과 이어받기를 표준으로 얻는다. 채팅의 상당수는 이것으로 충분하다. |
| 관리형 실시간 서비스 | 연결 계층 운영(확장, 전파, 재연결)을 맡긴다. |
| WebTransport | MDN은 WebTransport가 여러 용도에서 WebSocket을 대체할 것으로 본다. 역압과 여러 스트림이 필요하다. 지원 범위를 확인해야 한다. |

## 깊이 있는 활용

채팅을 예로 든다.

- **메시지는 먼저 저장하고, 그 다음 전달한다.** 서버가 DB에 저장하며 방별 단조 증가 순번을 붙이고, ack로 순번을 돌려준 뒤 퍼뜨린다. 저장된 것만 전달하므로 "보였는데 사라진" 메시지가 없다.
- **보낸 쪽 재시도는 멱등하게.** 클라이언트가 메시지마다 고유 ID를 만들어 보내고, 서버는 그 ID에 유일 제약을 건다. ack를 못 받아 다시 보내도 한 번만 저장된다([타임아웃·재시도·멱등 키](../api/timeout-retry-idempotency.md)).
- **복구 조회와 실시간 구독의 경계를 설계한다.** 구독을 먼저 열어 버퍼링한 뒤 확정된 경계까지 재생하고 ID로 중복을 제거하거나, 하나의 내구성 로그에서 이어 읽는다. 조회 후 구독만 하면 사이의 이벤트를 놓친다. 순번은 해당 스트림의 가시성 순서와 맞아야 하며, 마지막 이벤트만 빠지면 다음 순번으로 탐지할 수 없으므로 주기적 상태·커서 대조도 둔다([SSE](sse.md)의 복구 경계 참고).
- **전파 경로를 고른다.** 인스턴스가 여럿이면 Redis Pub/Sub(가볍지만 저장하지 않음), [Redis Streams](../async/redis-streams.md)나 [Kafka](../async/kafka.md)(저장하고 다시 읽음), 외부 STOMP 브로커(RabbitMQ) 중에서 고른다. 방 ID를 파티션 키로 쓰면 방 안의 순서가 유지된다.
- **버려도 되는 신호와 아닌 것을 나눈다.** 입력 중 표시와 접속 상태는 저장하지 않고 흘린다. 메시지와 읽음 위치는 저장한다.
- **재연결에 지터와 백오프.** 배포 때 몰리는 재연결을 흩뜨린다. 서버는 배포 전에 연결을 천천히 비운다(drain).
- **연결을 살리고 죽은 연결을 치운다.** 서버가 주기적으로 ping을 보내 프록시 유휴 타임아웃을 막고, pong이 오지 않는 연결은 정리한다.
- **인증과 Origin.** 핸드셰이크에서 인증하고 Origin을 허용 목록으로 검사한다. 연결 중 토큰 만료와 권한 변경(방에서 강퇴)을 서버가 확인해 연결을 끊는다.
- **느린 소비자를 끊는다.** 클라이언트별 송신 대기열에 상한을 두고, 넘으면 연결을 끊어 재연결 뒤 순번으로 메우게 한다. 서버 메모리를 지킨다.

## 임시방책의 신호

- 폴링·SSE·WebSocket의 요청 비용, 지연과 학습 목표를 비교하지 않고 방식부터 확정한다. 폴링으로도 요구를 충족할 수 있으며, 양방향 연결의 학습은 별도의 선택 근거가 된다.
- 반대로 WebSocket으로 받은 메시지를 저장 전에 바로 퍼뜨린다. 서버가 죽으면 메시지가 사라진다.
- 인스턴스를 늘리자 일부 사용자에게 메시지가 안 가서, 로드 밸런서에 고정 세션(sticky session)만 건다.
- 재연결 뒤 빠진 메시지를 새로고침으로 해결하게 둔다.
- nginx 뒤에서 연결이 60초마다 끊기는 것을 클라이언트 재연결로 덮는다.
- 순서가 가끔 바뀌는 것을 "네트워크 문제"로 둔다.

## 실패 재현

- **전송 중 끊김.** 클라이언트가 메시지를 보낸 직후 연결을 끊고 재전송하게 해, 멱등 ID가 없을 때 중복 저장되는지 센다.
- **재연결 누락.** 수신 중 네트워크를 끊고 그동안 다른 사용자가 메시지를 보낸 뒤 복구해, 순번 기반 복구가 있을 때와 없을 때 누락을 센다.
- **인스턴스 간 전파.** 인스턴스 둘에 사용자를 나눠 붙이고 전파 경로 없이 메시지를 보내 절반만 받는 것, Redis Pub/Sub 전파 중 구독자를 재시작해 유실되는 것을 본다.
- **순서.** 한 방에 빠르게 연속 메시지를 보내고, 스레드 풀 전송이나 여러 전파 경로에서 순서가 바뀌는지 순번으로 본다.
- **프록시.** `Upgrade`·`Connection` 헤더 설정을 빼고 연결 실패를, 유휴 60초 끊김을 재현한다.
- **느린 소비자.** 수신을 멈춘 클라이언트에게 메시지를 계속 보내 서버 메모리 증가를 본다.
- 장애 주입은 [Toxiproxy](../verify/toxiproxy.md)로 연결을 지연·절단한다.

## 측정과 검증

- **정확성은 전수로.** 메시지마다 순번과 ID를 기록하고, 장애 주입을 반복하며 클라이언트별 누락, 중복, 순서 뒤바뀜을 센다. 목표는 셋 다 0이다.
- **지연.** 전송부터 상대 수신까지 p50, p99. 폴링·SSE와 같은 표로 비교한다.
- **연결 계층.** 인스턴스별 동시 연결 수, 연결 수명, 재연결률, 송신 대기열 길이, 메모리.
- **배포 영향.** 배포 한 번에 끊긴 연결 수와 재연결 완료까지의 시간.
- **부하.** [k6](../verify/k6.md)의 WebSocket 지원으로 동시 연결과 메시지 속도를 늘려 한계를 찾는다.

## 재검토 조건

- 클라이언트 → 서버 통신이 드문 독립 요청이고 서버 푸시는 텍스트다. SSE + POST로 같은 재연결·인증 요구를 충족하면서 연결 관리 코드를 줄일 수 있으면 전환한다.
- 연결 계층 운영이 부담이다. 관리형 실시간 서비스를 검토한다.
- 역압이나 여러 스트림이 필요하고 대상 브라우저가 지원한다. WebTransport를 검토한다.
