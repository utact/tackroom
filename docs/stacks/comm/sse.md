# SSE

확인: 2026-09-29 재검토. 최초 조사는 2026-09-28, MDN(mdn/content, main), nginx.org 문서(main), WHATWG HTML 표준(검색 요약) 기준.

## 요약

SSE(Server-Sent Events)는 HTTP 응답 하나를 열어 둔 채 서버가 `text/event-stream` 형식의 이벤트를 계속 흘려보내는 방식이다.
서버에서 클라이언트로 한 방향이고, 브라우저의 `EventSource`가 끊기면 알아서 다시 연결하며, 마지막으로 받은 이벤트 ID를 `Last-Event-ID` 헤더로 보내 이어받는다.
"서버가 알려야 하는데 클라이언트가 보낼 것은 평범한 요청이면 되는" 경우에 WebSocket보다 단순한 선택지다.

## 문제 신호

- 알림, 진행률, 새 메시지 도착 신호처럼 서버에서 클라이언트로만 흐르는 실시간 갱신이 필요하다.
- LLM 응답을 토큰 단위로 흘려보내야 한다.
- 폴링 간격과 요청 수 계산이 맞지 않기 시작했다([폴링과 롱 폴링](polling.md)).
- 클라이언트가 보내는 일(메시지 전송)은 드물고 일반 POST로 충분하다.

## 기준선의 한계

기준선은 폴링이다. 요청 수가 클라이언트 수 ÷ 간격이고, 지연이 간격의 절반이다.
롱 폴링은 지연을 줄이지만, 응답마다 연결을 다시 열고 재요청 사이의 틈을 직접 메워야 한다.

## 원리

- **하나의 긴 HTTP 응답.** 서버는 `text/event-stream`으로 응답하고 연결을 닫지 않는다. 이벤트는 UTF-8 텍스트이고, 빈 줄 하나(줄바꿈 두 번)로 구분된다.
- **필드.** `data`(내용), `event`(이벤트 이름), `id`(이벤트 ID), `retry`(재연결 대기 밀리초). 콜론으로 시작하는 줄은 주석이다. MDN은 주석을 주기적으로 보내 연결이 시간 초과로 끊기지 않게 하라고 설명한다.
- **자동 재연결과 이어받기.** 끊기면 브라우저가 `retry` 간격 뒤 다시 연결하고, 마지막으로 받은 `id`를 `Last-Event-ID` 헤더로 싣는다. 서버는 그 이후의 이벤트부터 보내면 된다.
- **연결 수 제한.** MDN은 HTTP/2가 아닐 때 브라우저별 도메인당 동시 연결이 6개로 제한되어, 탭을 여러 개 열면 SSE 연결이 다른 요청을 막을 수 있다고 경고한다. HTTP/2에서는 한 연결 위의 스트림으로 다룬다.
- **요청 헤더를 못 바꾼다.** `EventSource` 생성자는 URL과 `withCredentials` 옵션만 받는다. `Authorization` 헤더를 직접 넣을 수 없어, 쿠키 인증이나 짧은 수명의 토큰을 URL에 싣는 방식, 또는 `fetch` 스트림으로 직접 구현하는 방식을 쓴다.

## 가치

SSE의 가치는 **푸시의 지연과 HTTP의 단순함을 함께 얻는 것**이다.

- 새 이벤트가 생기면 바로 보낸다. 빈 응답이 없다.
- 평범한 HTTP라 인증, 로깅, 프록시, 압축을 그대로 쓴다. 별도 프로토콜 전환이 없다.
- 재연결과 이어받기가 표준에 들어 있어, 클라이언트 쪽 복구 코드를 거의 쓰지 않는다.
- 클라이언트 → 서버 방향은 평범한 POST로 두므로, 쓰기 경로는 기존 API의 검증·멱등 처리를 그대로 쓴다.

## 트레이드오프와 리스크

- **한 방향이다.** 클라이언트가 자주 보내야 하면(입력 중 표시, 실시간 커서) 요청이 따로 나간다.
- **서버가 연결을 붙잡는다.** 동기 스레드 모델에서는 연결마다 스레드가 묶인다. 비동기 서버가 필요하다.
- **중간 장치가 끊거나 모은다.** nginx 기준으로 읽기 타임아웃(기본 60초)은 조용한 연결을 끊고, 버퍼링(기본 on)은 이벤트를 모아 보낸다. 압축 설정도 흘려보내기를 막을 수 있다.
- **이어받기는 서버가 구현해야 한다.** 브라우저는 `Last-Event-ID`를 보낼 뿐이다. 서버가 그 ID 이후의 이벤트를 다시 찾아 보낼 저장소(메시지 테이블, 스트림)가 없으면 끊긴 동안의 이벤트는 사라진다.
- **여러 인스턴스.** 사용자가 연결된 인스턴스와 이벤트가 생긴 인스턴스가 다르다. 인스턴스 사이에 이벤트를 퍼뜨리는 경로가 필요하다.
- **이진 데이터가 없다.** 텍스트만 보낸다.

## 대안과 경계

| 대안 | 고를 때 |
|---|---|
| [폴링과 롱 폴링](polling.md) | 변화가 드물고 지연 허용이 크다. |
| [WebSocket](websocket.md) | 클라이언트도 자주 보낸다. 이진 데이터가 필요하다. |
| [gRPC](grpc.md) 서버 스트리밍 | 받는 쪽이 브라우저가 아니라 서비스다. |
| 모바일 푸시 | 앱이 꺼져 있어도 알려야 한다. |

## 깊이 있는 활용

- **이벤트 ID를 저장소의 순번으로 쓴다.** 방별 메시지 순번이나 사용자별 알림 순번을 `id`로 보낸다. 재연결 때 `Last-Event-ID` 이후를 DB나 [Redis Streams](../async/redis-streams.md), [Kafka](../async/kafka.md)에서 먼저 보내고 실시간 이벤트를 이으면 누락이 없다.
- **보내기는 POST, 받기는 SSE로 나눈다.** 채팅 메시지 전송은 멱등 키가 있는 POST로 받아 DB에 저장하고([타임아웃·재시도·멱등 키](../api/timeout-retry-idempotency.md)), 저장된 메시지를 SSE로 퍼뜨린다. 쓰기와 전달의 책임이 분리된다.
- **인스턴스 간 전파를 둔다.** 이벤트가 생기면 Redis Pub/Sub이나 브로커로 모든 인스턴스에 알리고, 각 인스턴스는 자기에게 연결된 클라이언트에게 보낸다. 전파 경로에서 메시지를 놓쳐도 클라이언트가 재연결 때 저장소에서 메우므로, 전파는 최선 노력이어도 된다.
- **주석으로 연결을 살린다.** 경로 위 가장 짧은 유휴 타임아웃보다 짧은 간격으로 `:` 주석 줄을 보낸다.
- **SSE 경로만 프록시 설정을 바꾼다.** 해당 경로에서 버퍼링을 끄고(`proxy_buffering off` 또는 응답 헤더 `X-Accel-Buffering: no`), 읽기 타임아웃을 주석 간격보다 넉넉히 둔다([Nginx와 TLS](../ops/nginx-tls.md)).
- **HTTP/2로 서빙한다.** 연결 6개 제한을 피한다.
- **재연결 폭주를 흩뜨린다.** 서버 배포로 모든 연결이 끊기면 동시에 재연결한다. `retry` 값에 사용자별 무작위 지연을 넣는다.

## 임시방책의 신호

- 이벤트에 `id`를 넣지 않아, 재연결 뒤 끊긴 동안의 메시지가 사라진다.
- 프록시 뒤에서 이벤트가 몰려서 오자 서버 코드의 flush만 반복해서 고친다.
- 60초마다 연결이 끊기는 것을 클라이언트 재연결로 덮는다.
- 인스턴스를 둘로 늘리자 일부 사용자가 메시지를 못 받는다.
- 인증 헤더를 못 넣어 장수명 토큰을 URL에 붙인다.

## 실패 재현

- **이어받기.** 메시지를 보내는 중에 클라이언트 네트워크를 끊었다가 복구하고, `Last-Event-ID`로 끊긴 구간의 메시지가 모두 오는지 번호로 확인한다. `id` 없이 반복해 누락을 본다.
- **프록시 타임아웃과 버퍼링.** nginx 기본 설정 뒤에서 이벤트 없이 60초를 두어 끊기는 것, 버퍼링 때문에 이벤트가 모여 오는 것을 본다.
- **연결 수 제한.** HTTP/1.1에서 같은 도메인 탭을 7개 열어 요청이 막히는 것을 본다.
- **인스턴스 간 전달.** 인스턴스 둘에 클라이언트를 나눠 연결하고, 전파 경로 없이 이벤트를 보내 절반만 받는 것을 확인한다.

## 측정과 검증

- **전달 지연.** 이벤트 생성부터 수신까지 p50, p99. 폴링과 같은 표로 비교한다([폴링과 롱 폴링](polling.md)).
- **정확성.** 재연결 실험을 반복하며 클라이언트별 누락·중복 번호를 전수로 센다.
- **자원.** 인스턴스당 동시 연결 수, 연결당 메모리, 재연결 빈도를 본다.
- **부하.** [k6](../verify/k6.md)로 동시 연결을 늘리면서 이벤트를 보내 지연 꼬리를 본다.

## 재검토 조건

- 클라이언트 → 서버 메시지가 잦아졌다. WebSocket을 검토한다.
- 연결 수가 인스턴스 감당 범위를 넘는다. 연결 전용 계층이나 관리형 실시간 서비스를 검토한다.
