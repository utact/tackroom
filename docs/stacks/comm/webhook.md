# 웹훅

확인: 2026-09-28, Standard Webhooks 명세(standard-webhooks, main)와 GitHub 문서(github/docs, main)의 웹훅 모범 사례 기준.

## 요약

웹훅은 어떤 사건이 생겼을 때 제공자 서버가 소비자가 등록한 URL로 HTTP POST를 보내는 방식이다.
받는 쪽이 서버일 때의 푸시이고, 결제 완료, 저장소 변경, 배송 상태 같은 외부 시스템의 변화를 알리는 사실상의 표준이다.
평범한 HTTP 요청처럼 보이지만, 실제로는 **인터넷을 건너는 메시지 전달 시스템**이다. 그래서 인증, 재시도, 중복, 순서, 유실을 모두 설계해야 한다.

## 문제 신호

- 외부 서비스(결제사, 저장소 호스팅, 메신저)의 상태 변화를 받아야 하는데, 그 서비스의 API를 주기적으로 조회하고 있다.
- 반대로 우리 서비스의 사건을 고객사 시스템에 알려야 한다.
- 외부 API 조회 한도에 걸리거나 반영이 늦다.

## 기준선의 한계

기준선은 외부 API를 주기적으로 조회하는 폴링이다.

- 호출 수가 "대상 수 ÷ 간격"이고, 반영 지연이 간격에 묶인다([폴링과 롱 폴링](polling.md)).
- 제공자의 호출 한도에 걸린다.
- 다만 폴링은 받는 쪽이 통제하므로 유실이 없다. 웹훅은 이 장점을 잃고 푸시의 지연을 얻는다.

## 원리

- **사건마다 POST.** 제공자가 사건을 본문에 담아 등록된 URL로 보낸다. 2xx 응답이 성공이고, 그 외(리다이렉트, 404, 500, 시간 초과)는 실패다.
- **인증은 서명으로.** Standard Webhooks 명세는 진위 검증을 필수로 둔다.
  - `msg_id.timestamp.payload`를 서명해 `webhook-id`, `webhook-timestamp`, `webhook-signature` 헤더로 보낸다.
  - 대칭 서명은 상수 시간 비교로 검증한다.
  - 서명 헤더가 목록이라, 키를 바꾸는 동안 옛 키와 새 키 서명을 함께 보낸다.
- **재시도와 멱등.** 제공자는 성공할 때까지 며칠에 걸쳐 지수 백오프와 지터로 재시도한다(명세의 예시는 즉시, 5초, 5분, 30분, 2시간, … 24시간). 메시지 ID는 재시도해도 같아서 소비자가 멱등 키로 쓴다. GitHub 문서는 `X-GitHub-Delivery` 헤더로 재생 공격을 막으라고 하고, 재전송해도 같은 값이라고 설명한다.
- **빠르게 답한다.** GitHub는 10초 안에 2xx가 없으면 실패로 보고, 받은 즉시 응답한 뒤 큐에서 처리하라고 권한다. 명세의 권장 요청 타임아웃은 15~30초다.
- **얇은 본문과 두꺼운 본문.** 얇은 본문은 ID만 보내고 소비자가 API로 최신 상태를 조회한다. 두꺼운 본문은 상태 전체를 담는다.
- **보내는 쪽의 SSRF 위험.** 명세는 고객이 아무 URL이나 등록할 수 있어 웹훅 시스템이 서버 측 요청 위조(SSRF)에 특히 취약하다고 경고하고, 내부망 호출을 막는 전용 프록시를 권한다.

## 가치

웹훅의 가치는 **시스템 경계를 넘어 변화를 즉시, 조회 비용 없이 알리는 것**이다.

- 받는 쪽은 조회 한도와 폴링 지연에서 벗어난다.
- 보내는 쪽은 소비자가 몇이든 사건마다 한 번씩만 보낸다.
- 평범한 HTTP라 어떤 언어·플랫폼의 소비자도 받을 수 있다.

## 트레이드오프와 리스크

- **도착이 보장되지 않는다.** 받는 서버가 오래 죽어 있으면 재시도 기간이 끝나고 사건이 사라진다. 제공자가 재시도를 안 하거나 짧게 하기도 한다.
- **중복과 순서.** 재시도로 같은 사건이 여러 번 온다. 사건 A의 재시도가 사건 B보다 늦게 도착해 순서가 뒤집힌다.
- **위조와 재생.** 서명을 검증하지 않으면 누구나 "결제 완료"를 보낼 수 있다. 검증해도 가로챈 요청을 다시 보내는 재생 공격은 타임스탬프와 ID로 막아야 한다.
- **처리 시간 제한.** 응답 제한 시간 안에 무거운 처리를 하면 제공자가 실패로 보고 재시도해 중복이 늘어난다.
- **공개 엔드포인트.** 인터넷에 열린 URL이 생긴다. 속도 제한과 입력 검증이 필요하다.
- **보내는 쪽의 운영 부담.** 재시도 대기열, 실패 기록, 고객별 엔드포인트 관리, 키 회전, SSRF 방어를 모두 만들어야 한다.

## 대안과 경계

| 대안 | 고를 때 |
|---|---|
| [폴링과 롱 폴링](polling.md) | 제공자가 웹훅을 주지 않거나, 유실이 절대 없어야 하고 지연 허용이 있다. 웹훅과 함께 대사용으로도 쓴다. |
| 메시지 브로커 공유 | 같은 조직 안의 시스템이다([Kafka](../async/kafka.md), [RabbitMQ](../async/rabbitmq.md)). |
| [SSE](sse.md), [WebSocket](websocket.md) | 받는 쪽이 브라우저다. |
| 관리형 웹훅 발송 서비스 | 보내는 쪽 기능(재시도, 서명, 고객 관리 화면)을 직접 만들고 싶지 않다. |

## 깊이 있는 활용

받는 쪽:

- **검증 → 저장 → 응답 → 처리.** 서명과 타임스탬프를 확인하고, 메시지 ID에 유일 제약을 건 테이블에 저장한 뒤 바로 2xx로 답한다. 처리는 [DB 작업 큐](../async/db-job-queue.md)로 넘기고, 중복 수신은 유일 제약이 흡수한다.
- **순서는 본문이 아니라 상태로 판단한다.** 웹훅은 "무언가 바뀌었다"는 신호로 보고, 처리할 때 제공자 API로 최신 상태를 조회한다(얇은 본문 방식). 뒤늦게 도착한 옛 사건이 새 상태를 덮어쓰지 않는다. 두꺼운 본문이라면 사건의 버전이나 시각으로 더 오래된 것을 무시한다.
- **대사 작업을 둔다.** 웹훅을 놓쳤을 경우를 대비해, 긴 간격의 조회로 제공자 상태와 우리 상태를 맞춘다. GitHub 문서도 실패한 전달을 주기적으로 찾아 재전송하는 스크립트를 소개한다.
- **사건 유형과 동작을 확인한다.** 제공자는 사건 유형을 계속 추가한다. 모르는 유형은 무시하고 2xx로 답한다.

보내는 쪽:

- **[Outbox](../async/outbox-cdc.md)에서 발송한다.** 업무 트랜잭션과 함께 발송 대상 사건을 기록하고, 별도 작업자가 보낸다. 발송 실패가 업무 요청을 실패시키지 않는다.
- **Standard Webhooks 형식을 따른다.** ID·타임스탬프·본문 서명, 키 회전을 위한 다중 서명, 며칠에 걸친 재시도, `410 Gone`이면 비활성화, `429`와 `Retry-After` 존중.
- **SSRF를 막는다.** 발송은 내부망에 접근할 수 없는 전용 프록시를 거치게 한다. 등록 때와 발송 때 모두 목적지 주소를 검사한다.
- **실패를 보여준다.** 고객이 전달 기록과 실패 이유를 보고 재전송할 수 있게 한다. 오래 실패하면 다른 경로(이메일)로 알리고 발송을 멈춘다.

## 임시방책의 신호

- 서명을 검증하지 않는다. "URL을 아무도 모르니까".
- 웹훅 요청 안에서 무거운 처리를 끝낸 뒤 응답한다. 제공자가 시간 초과로 재시도해 중복 처리된다.
- 중복이 보이자 "최근 처리한 ID"를 메모리에 둔다.
- 결제 상태를 웹훅 본문만 믿고 바꾼다. 늦게 온 옛 사건이 상태를 되돌린다.
- 웹훅이 안 온 날의 누락을 사람이 수동으로 맞춘다.
- 보내는 쪽이 고객 URL로 직접 요청해 내부 관리 페이지에 접근된다.

## 실패 재현

- **중복.** 같은 사건을 두 번 보내 한 번만 반영되는지 본다. 처리 시간을 응답 제한보다 길게 두어 재시도로 인한 중복을 만든다.
- **순서 역전.** 같은 대상의 사건 두 개를 역순으로 보내 최종 상태가 올바른지 본다.
- **위조와 재생.** 서명 없는 요청, 서명이 틀린 요청, 오래된 타임스탬프의 요청을 보내 모두 거부되는지 자동 테스트로 고정한다.
- **장기 중단.** 받는 서버를 재시도 기간보다 오래 멈춘 뒤, 대사 작업이 누락을 메우는지 본다.
- **SSRF(보내는 쪽).** 내부 주소(`169.254.169.254`, `localhost`, 사설 대역)를 엔드포인트로 등록해 발송이 막히는지 본다.

## 측정과 검증

- **정합성.** 제공자의 사건 목록과 우리 처리 기록을 대조해 누락과 중복을 센다. 대사 작업이 메운 건수가 크면 수신 경로에 문제가 있다.
- **수신 지연.** 사건 발생 시각(본문의 타임스탬프)과 수신 시각의 차이.
- **응답 시간.** 웹훅 엔드포인트의 p99 응답 시간이 제공자 제한 시간보다 충분히 짧은지.
- **보내는 쪽.** 첫 시도 성공률, 최종 성공률, 고객별 실패율, 대기열 길이.

## 재검토 조건

- 제공자의 웹훅 신뢰성이 낮아 대사가 주된 동기화 수단이 됐다. 폴링 중심으로 바꾸고 웹훅은 신호로만 쓴다.
- 같은 조직 안의 시스템끼리 웹훅을 쓰고 있다. 브로커로 옮긴다.

## 출처

- Standard Webhooks, [Specification](https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md): 진위 검증 필수, 메시지 ID·타임스탬프·본문 서명과 헤더, 상수 시간 비교, 다중 서명 키 회전, 재시도 일정 예시, 상태 코드별 처리, 요청 타임아웃 15~30초, 얇은·두꺼운 본문, SSRF 방어.
- GitHub 문서, [Best practices for using webhooks](https://github.com/github/docs/blob/main/content/webhooks/using-webhooks/best-practices-for-using-webhooks.md): 10초 안의 2xx, 큐를 통한 비동기 처리, 사건 유형 확인, `X-GitHub-Delivery`로 재생 방지.
- GitHub 문서, [Handling failed webhook deliveries](https://github.com/github/docs/blob/main/content/webhooks/using-webhooks/handling-failed-webhook-deliveries.md): 실패 전달의 주기적 확인과 재전송.
