# 폴링과 롱 폴링

확인: 2026-09-28, MDN(mdn/content, main), nginx.org 문서(main), Spring Framework 7.0.9 문서 기준. 요청 수 계산은 이 문서에서 직접 했다.

## 요약

폴링은 클라이언트가 정해진 간격으로 "새 것 있나"를 묻는 방식이고, 롱 폴링은 서버가 새 것이 생기거나 제한 시간이 될 때까지 응답을 붙잡아 두는 방식이다.
둘 다 평범한 HTTP 요청-응답이라 캐시, 재시도, 프록시, 로드 밸런서, 인증을 그대로 쓴다.
통신 영역의 기준선이다. 틀린 방식이 아니라, **간격과 지연과 비용의 관계를 계산하지 않고 고르는 것**이 문제다.

## 문제 신호

- 채팅, 알림, 작업 진행률처럼 서버 쪽에서 생긴 변화를 클라이언트가 알아야 한다.
- AI나 개발자가 `setInterval(fetch, 1000)`이나 스케줄 루프로 새 메시지를 가져오는 코드를 쓴다.
- 사용자 수가 늘자 서버 요청의 대부분이 "변화 없음" 응답이다.
- 반응이 늦다는 불만에 폴링 간격만 줄인다.

## 기준선의 한계

이 문서가 기준선 자체다. 한계는 계산으로 드러난다.

- **요청 수 = 연결된 클라이언트 수 ÷ 간격.** 동시 접속 1만 명이 2초마다 물으면 초당 5,000 요청이다. 새 메시지가 드물면 대부분이 빈 응답이다.
- **평균 지연 = 간격의 절반.** 2초 간격이면 새 메시지를 평균 1초, 최악 2초 늦게 본다. 지연을 줄이려 간격을 줄이면 요청 수가 반비례로 는다.
- **요청마다 전체 비용.** 인증, 세션 조회, DB 조회가 빈 응답에도 일어난다.

## 원리

- **짧은 폴링.** 매 요청이 독립적이다. 서버는 상태를 들고 있지 않고, 요청은 어느 인스턴스로 가도 된다.
- **조건부 요청.** 응답에 `ETag`나 마지막 변경 시각을 주고, 클라이언트가 `If-None-Match`로 물으면 변화가 없을 때 `304 Not Modified`로 본문 없이 답한다. 전송량은 줄지만 요청 수와 서버 조회는 그대로다.
- **커서 기반 조회.** "마지막으로 받은 메시지 번호 이후"를 묻는다(`?after=1234`). 중복과 누락 없이 이어받는 원리는 이후 모든 방식에서 재사용된다.
- **롱 폴링.** 서버가 새 데이터가 생기거나 제한 시간(예: 25~30초)이 될 때까지 응답을 보류한다. 새 데이터가 생기면 즉시 응답하므로 지연은 거의 푸시와 같고, 빈 응답은 제한 시간마다 한 번으로 준다.
- **롱 폴링의 서버 자원.** 요청마다 스레드를 붙잡는 서버에서는 대기 요청 수만큼 스레드가 묶이므로, 비동기 처리(서블릿 비동기, WebFlux, 가상 스레드)가 필요하다. Spring의 SockJS도 롱 폴링을 대체 전송으로 쓴다.
- **중간 장치의 제한 시간.** nginx의 `proxy_read_timeout` 기본값은 60초다. 롱 폴링 제한 시간은 경로 위 모든 프록시·로드 밸런서의 제한 시간보다 짧아야 한다.

## 가치

폴링의 가치는 **가장 단순한 운영 모델**이다.

- 서버에 연결 상태가 없어 수평 확장, 배포, 장애 복구가 평범한 HTTP API와 같다.
- 방화벽, 프록시, 모바일 네트워크 어디서나 동작한다.
- 캐시와 CDN을 쓸 수 있다.

그래서 폴링이 맞는 상황은 문제의 성질로 정해진다. 변화가 드물거나, 지연 허용이 크거나(분 단위 대시보드, 배치 작업 상태), 긴 연결을 유지할 수 없는 실행 환경이다.
채팅도 예외가 아니다. 상담원이 분 단위로 답하는 문의 채팅이나 요청 시간이 제한된 서버리스 환경에서는 폴링이나 롱 폴링이 맞을 수 있다.
반면 "지금은 사용자가 적다"는 근거가 아니다. 목표 규모로 계산했을 때 초 단위 반응과 많은 동시 접속이 함께 오면 계산이 맞지 않기 시작한다.

## 트레이드오프와 리스크

- **간격과 비용의 반비례.** 지연을 줄이는 유일한 손잡이가 요청 수를 늘린다.
- **동시 폭주.** 모든 클라이언트가 같은 시각에 시작하면 같은 박자로 요청이 몰린다. 서버 재시작 직후 재연결도 몰린다.
- **롱 폴링의 연결 관리.** 제한 시간, 재요청 간격, 응답 직후 다음 요청 사이의 틈에 온 메시지 처리(커서로 해결)를 직접 설계해야 한다.
- **배터리와 데이터.** 모바일에서 짧은 간격의 폴링은 배터리와 데이터를 쓴다. (미검증: 영향 크기는 플랫폼마다 다르다.)

## 대안과 경계

| 대안 | 고를 때 |
|---|---|
| [SSE](sse.md) | 서버에서 클라이언트로 한 방향 알림이면 된다. 브라우저가 재연결과 이어받기를 해준다. |
| [WebSocket](websocket.md) | 양방향으로 자주 주고받는다(채팅 입력 표시, 협업 편집, 게임). |
| [웹훅](webhook.md) | 받는 쪽이 서버다. 외부 시스템에 변화를 알린다. |
| 모바일 푸시(APNs, FCM) | 앱이 꺼져 있을 때도 알려야 한다. 신뢰성 있는 전달 수단은 아니다. |

## 깊이 있는 활용

- **먼저 계산한다.** 동시 접속 수, 원하는 지연, 메시지 빈도로 초당 요청 수와 빈 응답 비율을 계산해 표로 둔다. 이 계산이 푸시 방식을 도입할 근거가 된다.
- **커서로 이어받는다.** 어떤 전달 방식이든 "마지막으로 받은 번호 이후"를 묻는 API를 두고, 푸시가 놓친 메시지를 이것으로 메운다. 채팅이라면 방마다 단조 증가 번호를 둔다.
- **간격에 지터와 백오프를 둔다.** 초기 지연을 무작위로 흩뜨리고, 오류가 나면 간격을 늘린다. 화면이 보이지 않을 때(`visibilitychange`)는 멈추거나 늘린다.
- **롱 폴링은 비동기 서버에서.** 대기 요청이 스레드를 쥐지 않게 비동기로 처리하고, 새 데이터 도착은 내부 이벤트(Redis Pub/Sub, [DB `LISTEN/NOTIFY`](../async/db-job-queue.md))로 깨운다. 제한 시간은 경로의 프록시 제한보다 몇 초 짧게 둔다.
- **폴링을 대체 경로로 남긴다.** 푸시 연결이 막힌 환경(엄격한 프록시)에서 롱 폴링으로 떨어지게 한다.

## 임시방책의 신호

- "사용자가 적으니 일단 폴링"이라며 목표 규모의 계산 없이 고른다.
- 채팅 화면에 `setInterval(() => fetch('/messages'), 1000)`을 두고, 매번 전체 메시지 목록을 받는다.
- 반응이 느리다는 말에 간격을 500ms로 줄인다.
- 서버 부하가 늘자 폴링 응답을 캐시해 새 메시지가 늦게 보인다.
- 커서 없이 "최근 50개"를 반복 조회해, 빠르게 쌓이면 메시지가 빠진다.

## 실패 재현

- **요청 수 폭증.** [k6](../verify/k6.md)로 동시 접속 가상 사용자 수를 늘려 가며 초당 요청 수, 빈 응답 비율, 서버 CPU를 잰다. 계산과 맞는지 본다.
- **메시지 누락.** "최근 N개" 조회에서 폴링 간격 사이에 N개보다 많은 메시지를 넣어 빠지는 것을 확인한다. 커서 조회로 바꿔 반복한다.
- **롱 폴링 스레드 고갈.** 동기 서버에서 롱 폴링 대기 요청을 스레드 풀 크기보다 많이 만들어 다른 API가 멈추는 것을 본다.
- **프록시 제한 시간.** 롱 폴링 제한 시간을 프록시 읽기 타임아웃보다 길게 두고 504가 나는 것을 본다.

## 측정과 검증

- **전달 지연.** 메시지 생성 시각과 클라이언트 수신 시각의 차이를 p50, p99로 잰다.
- **효율.** 초당 요청 수, 빈 응답 비율, 메시지당 요청 수를 잰다.
- **정확성.** 클라이언트별로 받은 메시지 번호를 모아 누락과 중복을 전수로 센다.
- 이 측정을 SSE와 WebSocket에도 똑같이 적용해 같은 표로 비교한다.

## 재검토 조건

- 동시 접속과 지연 요구가 커져 요청 수 계산이 감당 범위를 넘는다. SSE나 WebSocket으로 옮긴다.
- 반대로 실시간 요구가 사라졌다. 푸시 인프라를 걷고 폴링으로 돌아온다.
