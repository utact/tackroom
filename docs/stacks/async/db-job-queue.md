# DB 작업 큐

확인: 2026-09-27, PostgreSQL 문서(master 브랜치)와 db-scheduler README 기준.

## 요약

업무 데이터가 있는 RDB의 테이블 하나를 작업 목록으로 쓴다.
작업자는 `SELECT ... FOR UPDATE SKIP LOCKED`로 다른 작업자가 잡지 않은 행만 가져간다.
작업 등록이 업무 데이터 변경과 같은 트랜잭션에 들어가므로, "저장은 됐는데 작업은 안 생긴" 상태가 없다.

## 문제 신호

- 주문 저장 후 메일 발송, 결제 후 정산 요청처럼 DB 변경 뒤에 느린 후속 작업이 있다.
- 후속 작업이 저장과 함께 확실히 생겨야 하고, 저장이 취소되면 작업도 없어야 한다.
- 기존 DB의 트랜잭션과 작업 생성의 원자성을 활용하거나, 작업 선점·임대·재처리를 직접 학습하고 싶다. 처리량 한계는 업무 쿼리와 함께 부하를 걸어 확인한다.
- 메시지 브로커를 새로 운영할 여력이 없다.

## 기준선의 한계

- 요청 스레드 안에서 동기로 처리하면 응답이 느려지고, 외부 API 장애가 요청 실패가 된다.
- 프로세스 안 비동기 실행(`@Async`, 스레드 풀, 메모리 큐)은 배포나 장애로 프로세스가 죽을 때 작업을 잃는다.
- 상태 컬럼(`status = 'PENDING'`)을 두고 `SELECT` 후 `UPDATE`로 가져가면 두 작업자가 같은 행을 가져간다. 잠금을 걸면(`FOR UPDATE`) 다른 작업자가 줄을 서서 기다린다.

## 원리

- **행 잠금을 건너뛴다.** `FOR UPDATE SKIP LOCKED`는 이미 잠긴 행을 기다리지 않고 건너뛴다. 공식 문서는 이것이 일관된 조회가 아니어서 일반 용도에는 맞지 않지만, 여러 소비자가 큐 같은 테이블에 접근할 때 잠금 경합을 피하는 데 쓸 수 있다고 적는다.
- **잠금이 곧 소유권이다.** 작업자가 행을 잠근 트랜잭션 안에서 처리하고 커밋하면 완료, 작업자가 죽으면 트랜잭션이 끝나며 잠금이 풀려 다른 작업자가 가져간다. 브로커의 확인(ack)과 재전달을 DB 트랜잭션이 대신한다.
- **작업 등록은 업무 트랜잭션의 일부다.** 주문 행과 작업 행을 같은 트랜잭션에 넣으면 둘 다 생기거나 둘 다 없다. 이중 쓰기 문제가 구조적으로 없다.
- **깨우기는 `LISTEN/NOTIFY`로 한다.** `NOTIFY`는 트랜잭션이 커밋될 때만 전달되고, 커밋 순서대로 전달된다. 작업자는 폴링 주기를 길게 두고, 알림을 받으면 즉시 확인한다.

## 가치

DB 작업 큐의 가치는 **새 인프라 없이 트랜잭션 일관성을 얻는 것**이다.

- 업무 데이터 변경과 작업 생성이 원자적이다. 메시지 브로커를 쓰면 [Outbox](outbox-cdc.md)로 따로 풀어야 하는 문제다.
- 작업 상태를 SQL로 조회하고 고칠 수 있다. 실패한 작업을 찾고, 다시 돌리고, 통계를 내는 운영 도구가 이미 있다.
- 백업, 모니터링, 권한, 장애 대응이 기존 DB와 같다.

그래서 DB 작업 큐가 맞는 상황은 작업량이 DB가 감당할 만하고, 작업이 업무 데이터와 강하게 묶인 경우다.
대부분의 서비스가 처음 비동기 처리가 필요할 때 여기서 시작하고, 한계를 측정한 뒤 옮기는 편이 낫다.

- **학습 실험.** 파일 처리 작업을 두 작업자가 가져가게 한다. 한 작업자를 임대보다 오래 멈췄다가 되살려 소유권 갱신과 중복 부작용을 관찰하고, 토큰 조건부 갱신과 멱등 처리가 각각 막는 문제를 구분한다.

## 트레이드오프와 리스크

- **DB가 큐의 부하를 진다.** 폴링 쿼리, 잠금, 상태 변경 쓰기가 업무 쿼리와 같은 DB 자원을 쓴다. 작업량이 늘면 업무 쿼리의 지연이 먼저 나빠진다.
- **테이블이 부푼다.** PostgreSQL의 `UPDATE`와 `DELETE`는 죽은 행을 남기고, VACUUM은 다른 트랜잭션이 볼 수 있는 행을 치우지 못한다. 긴 트랜잭션 하나가 큐 정리를 막고, 폴링 쿼리는 죽은 행을 계속 훑는다.
- **긴 작업과 트랜잭션 잠금이 충돌한다.** 처리 내내 행 잠금을 쥐고 있으면 트랜잭션이 길어진다. 외부 API 호출을 트랜잭션 안에서 하면 연결 풀과 VACUUM을 함께 막는다.
- **순서 보장이 약하다.** `SKIP LOCKED`는 잠긴 행을 건너뛰므로 여러 작업자 사이의 순서는 보장되지 않는다.
- **fanout과 다시 읽기가 없다.** 한 작업을 여러 종류의 소비자가 각자 처리하려면 소비자별로 행을 만들어야 한다.
- **`NOTIFY`는 신호일 뿐이다.** 리스너가 연결돼 있지 않을 때 보낸 알림은 받지 못한다. 알림만 믿으면 작업을 놓치므로 폴링을 함께 둬야 한다.

## 대안과 경계

| 대안 | 고를 때 |
|---|---|
| [RabbitMQ](rabbitmq.md) | 작업량이 DB를 압박하고, 메시지별 라우팅·우선순위·지연 재시도가 필요하다. |
| [Kafka](kafka.md) | 같은 사건을 여러 소비자가 각자 처리하고, 과거 사건을 다시 읽는다. |
| [Outbox와 CDC](outbox-cdc.md) | DB 트랜잭션 일관성은 유지하면서 브로커로 사건을 내보내야 한다. DB 큐의 "등록" 부분만 쓰고 전달은 브로커에 맡기는 구조다. |
| [Spring 스케줄러와 ShedLock](../batch/spring-scheduler-shedlock.md), [Quartz](../batch/quartz.md) | 작업이 사건이 아니라 시각에 따라 생긴다. |

Java에서는 db-scheduler, JobRunr 같은 라이브러리가 이 패턴을 구현한다.
직접 만들기 전에 이들이 이미 푼 문제(죽은 작업 감지, 재시도, 정리)를 확인한다.

## 깊이 있는 활용

- **가져가기와 처리를 분리한다.**
  1. 짧은 트랜잭션에서 `SKIP LOCKED`로 고르고 `status='RUNNING', locked_until=now()+임대시간, attempts=attempts+1`과 새 소유 토큰으로 바꿔 커밋한다.
  2. 처리는 트랜잭션 밖에서 하고, 끝나면 완료로 바꾼다.
  3. 작업자가 죽으면 `locked_until`이 지난 행을 다시 가져간다.
- **임대 시간과 소유권을 함께 검사한다.** heartbeat와 완료 갱신은 `WHERE id=:id AND status='RUNNING' AND owner_token=:token`처럼 현재 소유권을 조건으로 한다. 갱신이 0행이면 소유권을 잃은 작업자다. 임대 만료 후 이전 작업자가 살아나도 새 작업자의 상태를 덮지 못하게 한다. 외부 API나 파일 쓰기는 이 조건으로 보호되지 않으므로 멱등 처리나 대상의 펜싱이 별도로 필요하다.
- **폴링 쿼리를 부분 인덱스로 받친다.** `WHERE status = 'READY'` 조건의 부분 인덱스를 `(run_at)`에 걸어 탐색 범위를 줄인다. 인덱스와 테이블의 죽은 튜플, 잠긴 작업, VACUUM 상태에 따라 비용은 여전히 늘 수 있다. `EXPLAIN (ANALYZE, BUFFERS)`로 실제 비용을 확인한다.
- **완료 행은 지우거나 옮긴다.** 큐 테이블에 완료 행을 계속 두지 않는다. 기간별 파티션을 두면 오래된 파티션을 통째로 떼어 내 VACUUM 부담 없이 정리한다.
- **큐 테이블의 autovacuum을 따로 조인다.** 행 변경이 잦은 테이블은 테이블 단위로 autovacuum 기준을 낮춰 죽은 행을 빨리 치운다. 같은 DB의 긴 트랜잭션(`pg_stat_activity`의 오래된 `xact_start`)을 감시한다.
- **`NOTIFY`를 트리거에 둔다.** 공식 문서의 권고로, 등록 코드가 알림을 잊지 않고 커밋된 작업만 알린다. 같은 트랜잭션의 같은 알림은 하나로 합쳐진다.
- **재시도는 `run_at`을 미룬다.** 실패하면 `run_at = now() + 백오프`로 바꾸고 `attempts`가 한도를 넘으면 `FAILED`로 둔다. 실패 작업은 SQL로 찾아 고친 뒤 `READY`로 되돌린다.
- **멱등 키를 둔다.** `(작업 종류, 업무 키)`에 유일 제약을 걸고, 처리도 재실행에 안전하게 만든다. 임대가 만료된 뒤 원래 작업자가 살아나 같은 일을 끝낼 수 있다.

## 임시방책의 신호

- `SELECT` 후 `UPDATE`로 작업을 가져가고, 중복 처리가 보이자 `synchronized`나 애플리케이션 락을 건다. 인스턴스가 둘이 되면 다시 깨진다.
- 작업을 잡은 트랜잭션 안에서 외부 API를 부른다.
- 죽은 작업을 되살리는 로직 없이 `RUNNING`에 멈춘 행을 사람이 손으로 고친다.
- 폴링 주기를 100ms로 줄여 지연을 해결한다.
- 완료 행이 수백만 건 쌓여 폴링이 느려지자 인덱스를 하나 더 건다.
- `@Async`로 작업을 넘기고 "재시도는 나중에"라고 둔다.

## 실패 재현

- **동시 가져가기.** 작업자 여러 개가 같은 테이블을 동시에 폴링하게 하고, 같은 작업이 두 번 처리되는지 센다. `SKIP LOCKED`를 뺀 버전과 비교해 대기 시간도 잰다.
- **작업자 종료.** 작업을 가져간 직후와 처리 도중에 `kill -9`로 죽이고, 임대 만료 뒤 다른 작업자가 다시 가져가는지, 결과가 두 번 반영되지 않는지 본다.
- **업무 트랜잭션 롤백.** 주문 저장과 작업 등록을 같은 트랜잭션에 넣고 롤백시킨다. 작업이 남지 않는지, `NOTIFY`가 가지 않는지 본다.
- **긴 트랜잭션.** 다른 세션에서 트랜잭션을 열어 둔 채 큐를 계속 돌린다. 죽은 행 수(`pg_stat_user_tables.n_dead_tup`)와 폴링 쿼리 시간이 늘어나는 것을 본다.
- **알림 유실.** 리스너 연결을 끊은 상태에서 작업을 넣고, 폴링만으로도 처리되는지 본다.
- 재현 환경은 [Testcontainers](../verify/testcontainers.md)로 실제 PostgreSQL을 띄운다. H2 같은 대체 DB는 잠금 동작이 달라 재현이 되지 않는다.

## 측정과 검증

- **중복과 누락은 전수로 센다.** 작업마다 업무 키를 두고, 결과 테이블에서 키별 반영 횟수를 센다. 목표는 모두 정확히 1이다.
- **대기 지연.** 작업 생성 시각과 처리 시작 시각의 차이를 p50, p99로 본다. 폴링 주기와 `NOTIFY` 사용 여부에 따라 비교한다.
- **DB 영향.** 큐를 켜기 전후로 업무 쿼리의 p99 지연, DB CPU, 초당 트랜잭션 수를 비교한다. 큐 때문에 업무 쿼리가 나빠지는 지점이 DB 큐의 한계다.
- **테이블 상태.** `n_dead_tup`, 테이블 크기, autovacuum 실행 간격을 추세로 본다.
- **부하 시험.** `pgbench`에 폴링·완료 쿼리를 사용자 정의 스크립트로 넣어 작업자 수를 늘려 가며 처리량 곡선을 그린다. 실제 작업 생성은 [k6](../verify/k6.md)로 API에 도착률을 걸어 만든다.

## 재검토 조건

- 폴링·선점·정리 쿼리를 개선해도 큐와 업무 쿼리의 자원 경쟁으로 업무 지연 목표를 넘는다. 큐 부하를 분리할 브로커를 검토한다. 초당 작업 수 하나를 제품 공통의 한계로 쓰지 않는다.
- 같은 사건을 여러 소비자가 각자의 진행 위치로 처리하거나 재생해야 한다. 한 작업을 한 작업자에게 배분하는 큐와 구분해 사건 로그나 발행·구독 구조를 검토한다.
- 폴링과 `NOTIFY`를 조정해도 작업 생성부터 처리 시작까지의 지연 목표를 맞추지 못한다. 푸시 전달을 시험하되 작업자 포화가 원인이면 처리 용량부터 조정한다.

## 출처

- PostgreSQL, [SELECT의 잠금 절](https://github.com/postgres/postgres/blob/master/doc/src/sgml/ref/select.sgml): `SKIP LOCKED`의 의미와 "큐 같은 테이블" 용도, 일반 용도 부적합.
- PostgreSQL, [NOTIFY](https://github.com/postgres/postgres/blob/master/doc/src/sgml/ref/notify.sgml): 커밋 시 전달, 커밋 순서 보장, 같은 내용 합치기, 트리거 기법, 8GB 알림 큐.
- PostgreSQL, [Routine Vacuuming](https://github.com/postgres/postgres/blob/master/doc/src/sgml/maintenance.sgml): 옛 행 버전과 VACUUM, 공간 회수.
- db-scheduler, [README](https://github.com/kagkarlsson/db-scheduler/blob/master/README.md): `fetch`와 `lock-and-fetch`(`select for update .. skip locked`) 전략, heartbeat 기본 5분, 놓친 heartbeat 한도 6, 죽은 실행 재예약.
