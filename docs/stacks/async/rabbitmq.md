# RabbitMQ

확인: 2026-09-27, RabbitMQ 4.3 문서(rabbitmq-website 저장소) 기준.

## 요약

RabbitMQ는 메시지를 exchange에서 규칙(binding)에 따라 큐로 보내고, 큐는 소비자에게 나눠 준다.
소비자가 확인(ack)하기 전까지 메시지는 큐에 남고, 확인하지 못한 채 연결이 끊기면 다시 큐로 돌아간다.
그래서 "일을 나눠 맡기고, 끝났다는 확인을 받을 때까지 책임지는" 작업 분배에 맞다.

## 문제 신호

- 요청 안에서 끝내기엔 오래 걸리는 작업(메일 발송, 이미지 변환, 외부 API 호출)을 여러 작업자에게 나눠야 한다.
- 메시지 종류나 속성에 따라 다른 작업자 집단으로 보내야 한다.
- 작업자가 죽으면 그 작업을 다른 작업자가 이어받아야 한다.
- 실패한 작업을 몇 번 재시도하고, 계속 실패하면 따로 모아 사람이 봐야 한다.
- 작업마다 우선순위가 다르다.

## 기준선의 한계

- DB 테이블을 큐로 쓰면 작업자 수가 적을 때는 충분하다. 폴링 주기가 지연의 하한이 되고, 작업자가 늘면 폴링 쿼리가 DB 부하가 된다.
- 요청 스레드에서 비동기 실행(`@Async`, 스레드 풀)을 하면 프로세스가 죽을 때 작업이 사라진다.
- 여러 종류의 작업자에게 라우팅하려면 DB 큐에서는 조건 컬럼과 쿼리가 늘어난다.

## 원리

- **exchange와 binding이 라우팅을 맡는다.** 발행자는 큐가 아니라 exchange로 보낸다. direct, topic, fanout, headers 규칙이 어느 큐에 사본을 넣을지 정한다. 발행 코드는 누가 받는지 모른다.
- **큐는 소비하면 지운다.** 소비자가 확인한 메시지는 삭제된다. 큐는 FIFO이고, 한 채널에서 발행한 메시지는 발행 순서대로 들어간다.
- **확인 창(prefetch).** 채널마다 확인되지 않은 전달 수의 상한을 `basic.qos`로 정한다. 상한에 닿으면 브로커는 확인이 올 때까지 더 보내지 않는다. 0은 무제한이다.
- **확인 전 연결이 끊기면 재전달.** 수동 확인에서 확인되지 않은 전달은 채널이나 연결이 닫히면 큐로 돌아간다. 재전달된 메시지에는 `redelivered` 표시가 붙고, 다른 소비자에게 갈 수 있다.
- **발행 확인(publisher confirm).** 채널을 confirm 모드로 두면 브로커가 메시지마다 ack나 nack를 한 번씩 보낸다. 쿼럼 큐에서는 과반 복제본이 받은 뒤에 확인한다. AMQP 트랜잭션보다 가볍다(문서는 처리량이 250배 줄어드는 트랜잭션의 대안이라고 설명한다).
- **쿼럼 큐.** Raft 합의로 복제되는 큐다. 4.0부터 클래식 큐 미러링은 제거됐고, 복제가 필요한 큐는 쿼럼 큐나 스트림을 쓴다.

## 가치

RabbitMQ의 가치는 **메시지 단위의 책임 이전**이다.

- 작업자마다 처리 속도가 달라도 prefetch가 느린 작업자에게 일이 쌓이지 않게 한다. 파티션 같은 고정 배정이 없어서, 한 메시지가 느려도 다른 메시지는 다른 작업자가 처리한다.
- 메시지별로 확인, 거절, 재전달, 격리(dead letter)를 할 수 있다. Kafka 소비자 그룹처럼 한 메시지가 파티션 전체를 막지 않는다.
- 라우팅이 브로커의 설정이라서, 새 작업자 집단을 붙일 때 발행 코드를 바꾸지 않는다.

그래서 RabbitMQ가 맞는 상황은 "누가 이 일을 끝냈는가"가 중요한 작업 큐다.
사건을 오래 보관하고 여러 소비자가 다시 읽어야 한다면 큐가 아니라 로그(Kafka, RabbitMQ 스트림)가 맞다.

## 트레이드오프와 리스크

- **다시 읽기가 없다.** 큐에서 확인된 메시지는 지워진다. 버그를 고친 뒤 지난 메시지를 다시 처리하려면 따로 저장해 둬야 한다. 스트림은 예외다.
- **순서는 쉽게 깨진다.** 소비자가 여럿이면 재전달이 순서를 바꾼다. 우선순위도 순서를 바꾼다. 순서가 필요하면 단일 활성 소비자(single active consumer)나 스트림을 써야 하고, 그만큼 병렬성을 잃는다.
- **발행 확인이 "소비자에게 갔다"는 뜻이 아니다.** 어떤 큐로도 라우팅되지 않은 메시지도 브로커는 확인(ack)한다. `mandatory` 기본값은 false라서, 바인딩이 빠져 있으면 메시지는 조용히 버려진다.
- **기본값은 유실 쪽이다.** 자동 확인 모드, 확인 없는 발행, 기본 dead letter 전략(`at-most-once`)은 모두 유실을 허용한다. 안전하게 쓰려면 발행 확인, 수동 확인, 쿼럼 큐, `at-least-once` dead letter를 직접 켜야 한다.
- **긴 적체에 약하다.** 쿼럼 큐 문서는 500만 건 이상 적체나 큰 fanout에는 스트림이 더 맞다고 적는다. 메모리나 디스크가 경고 수위에 닿으면 브로커가 발행 연결을 막는다. 소비자 장애가 발행자 장애로 번진다.
- **재전달 폭주.** 처리할 수 없는 메시지를 `requeue=true`로 계속 돌려보내면 무한 루프가 된다. 쿼럼 큐는 4.0부터 기본 전달 한도 20을 두고 넘으면 버리거나 dead letter로 보낸다. prefetch가 크면 소비자 장애 한 번에 묶음 전체가 한도에 가까워질 수 있다고 문서가 경고한다.
- **운영 부담.** Erlang 기반 클러스터, 쿼럼 큐의 복제본 수, 정책(policy), 메모리·디스크 경고 수위를 관리해야 한다.

## 대안과 경계

| 대안 | 고를 때 |
|---|---|
| [DB 작업 큐](db-job-queue.md) | 작업 생성이 업무 데이터 변경과 같은 트랜잭션이어야 하고, 작업량이 작다. 새 인프라를 늘리지 않는다. |
| [Kafka](kafka.md) | 같은 사건을 여러 소비자가 각자 처리하고, 과거 사건을 다시 읽는다. 엔터티별 순서가 필요하다. |
| RabbitMQ 스트림 | RabbitMQ를 이미 운영하면서 다시 읽기, 긴 보관, 큰 fanout이 필요하다. |
| [Redis Streams](redis-streams.md) | Redis를 이미 쓰고, 작업량과 보관 기간이 메모리 안에 들어간다. |

RabbitMQ도 저장과 발행 사이의 이중 쓰기를 풀지 않는다.
DB에 쓰고 발행하는 코드에는 [Outbox](outbox-cdc.md)가 필요하다.

## 깊이 있는 활용

- **발행 확인과 `mandatory`를 같이 쓴다.** 확인은 "브로커가 책임진다", `mandatory`의 반환은 "받을 큐가 없다"를 알려준다. 둘을 같이 써야 바인딩 누락을 발견한다. 버려지면 안 되는 메시지는 대체 exchange(alternate exchange)로 받아 둔다.
- **확인은 비동기로 모아서 받는다.** 메시지마다 동기로 기다리면 처리량이 크게 준다. 순번과 `multiple` 플래그로 한꺼번에 확인되는 구간을 추적하고, 확인되지 않은 메시지만 재발행한다.
- **prefetch는 처리 시간으로 정한다.** 처리가 빠르고 균일하면 크게, 느리거나 편차가 크면 작게 둔다. 1은 공정하지만 처리량이 낮다. 무제한(0)은 소비자 메모리를 무한히 쓰게 둔다.
- **재시도는 지연을 두고, 한도를 두고, 끝은 격리한다.** 쿼럼 큐는 4.3부터 선형 백오프 지연 재시도를 지원한다(`delay = min(min_delay × delivery_count, max_delay)`). 그 이전 버전이나 지수 백오프가 필요하면 TTL을 건 대기 큐와 dead letter exchange로 되돌리는 구조를 쓴다. 전달 한도를 넘은 메시지는 dead letter로 보내고 사람이 본다.
- **격리 큐의 유실을 막는다.** 쿼럼 큐의 dead letter를 `at-least-once`로 켜려면 `overflow=reject-publish`와 길이 한도가 함께 필요하다. 문서는 낮은 비용으로 격리 메시지를 보관하는 방법으로 스트림 하나를 dead letter 대상으로 두는 것을 권한다.
- **느린 소비자는 소비자 타임아웃으로 풀어준다.** 4.3부터 쿼럼 큐에서 확인이 늦은 전달을 큐로 되돌린다. 전역 기본 설정 예시는 30분(`consumer_timeout = 1800000`)이다. 작업이 이보다 길면 작업을 쪼개거나, 메시지는 "시작 신호"로만 쓰고 진행 상태는 DB에 둔다.
- **순서와 병렬성을 같이 원하면 키로 큐를 나눈다.** 일관 해시 exchange나 라우팅 키로 엔터티를 여러 큐에 나누고, 큐마다 단일 활성 소비자를 둔다. Kafka의 파티션을 흉내 내는 구조이며, 큐 수를 바꾸면 배치가 바뀐다는 한계도 같다.
- **소비자는 멱등하게 만든다.** 재전달은 정상 동작이다. 메시지 ID를 유일 제약으로 가진 처리 기록에 먼저 쓰고 결과와 같은 트랜잭션으로 커밋한다.

## 임시방책의 신호

- 소비자에서 예외가 나면 `basic.nack(requeue=true)`만 한다. 처리할 수 없는 메시지가 무한히 돈다.
- 자동 확인 모드로 받고 처리 중 예외를 로그로만 남긴다. 유실이다.
- 발행 후 확인을 기다리지 않는다. 브로커 재시작이나 네트워크 끊김에 조용히 잃는다.
- 순서가 꼬이자 소비자를 하나로 줄이고, 처리량이 모자라자 다시 늘린다.
- 긴 작업 때문에 채널이 닫히자 타임아웃만 늘린다.
- 재시도를 소비자 안에서 `sleep` 루프로 한다. 그동안 prefetch 창이 막혀 다른 메시지도 멈춘다.

## 실패 재현

- **바인딩 누락.** 바인딩이 없는 라우팅 키로 발행하고, 발행 확인은 ack인데 메시지가 사라지는지 본다. `mandatory=true`로 반복해 반환을 받는지 본다.
- **처리 중 소비자 종료.** 수동 확인 모드에서 처리 도중 `kill -9`로 죽이고, 재전달과 `redelivered=true`를 확인한다. 소비자가 멱등하지 않으면 결과가 두 번 반영된다.
- **독 메시지.** 항상 예외를 내는 메시지를 넣고, 전달 한도(기본 20)를 넘은 뒤 dead letter로 가는지, 설정이 없으면 버려지는지 본다.
- **브로커 노드 손실.** 3노드 클러스터에서 쿼럼 큐의 노드 하나를 멈추고 발행·소비가 계속되는지, 둘을 멈추면 발행 확인이 멈추는지 본다.
- **메모리 경고.** 소비자를 멈추고 큐를 쌓아 메모리 경고 수위를 넘긴다. 발행 연결이 막히는 것을 확인한다.
- **네트워크 지연과 끊김.** [Toxiproxy](../verify/toxiproxy.md)로 발행자와 브로커 사이를 끊어 확인되지 않은 메시지의 재발행 로직을 시험한다.

## 측정과 검증

- **유실과 중복은 전수로 센다.** 메시지마다 연속 번호를 넣고, 장애 주입 후 결과에서 빠진 번호와 두 번 반영된 번호를 센다. 목표는 둘 다 0이다. 장애 주입은 여러 번 반복한다.
- **적체.** 큐 길이(ready, unacked)와 그 추세를 본다. 유입률과 확인률의 차이가 적체 증가 속도다. RabbitMQ Prometheus 플러그인의 큐 지표로 수집한다.
- **처리 지연.** 발행 시각을 메시지에 넣고 확인 시각과의 차이를 p50, p99로 본다. 재전달된 메시지를 따로 집계한다.
- **처리량.** RabbitMQ의 PerfTest 도구로 브로커 한계를 먼저 재고, 실제 소비 로직을 넣어 다시 잰다. prefetch 값을 바꿔 가며 처리량과 지연의 곡선을 그린다.
- **재시도 비용.** 재전달 비율과 dead letter 유입률을 본다. 재전달 비율이 오르면 원인은 대개 소비자 쪽 장애나 독 메시지다.

## 재검토 조건

- 지난 메시지를 다시 처리해야 하는 요구가 생겼다. 스트림이나 Kafka를 검토한다.
- 같은 메시지를 받는 소비자 종류가 계속 늘어난다. fanout 큐가 늘어나는 대신 로그가 맞을 수 있다.
- 작업량이 작고 업무 데이터와의 트랜잭션 일관성이 더 중요하다. DB 작업 큐로 줄인다.
- 적체가 수백만 건 단위로 자주 쌓인다.
