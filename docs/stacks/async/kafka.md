# Kafka

확인: 2026-09-27, Apache Kafka 4.3.1 문서와 소스 기준.

## 요약

Kafka는 메시지를 지우지 않고 파티션별 순서가 있는 로그에 쌓는다.
소비자는 "어디까지 읽었는지"를 숫자 하나(offset)로만 기억한다.
그래서 여러 소비자가 같은 기록을 서로 독립적으로, 원하는 시점부터 다시 읽을 수 있다.

## 문제 신호

- 하나의 사건(주문 생성, 결제 완료)을 여러 서비스가 각자 처리해야 하고, 새 소비자가 나중에 합류한다.
- 처리 로직의 버그를 고친 뒤 지난 사건을 다시 처리해야 한다.
- 같은 엔터티의 사건은 순서대로, 다른 엔터티끼리는 병렬로 처리해야 한다.
- 초당 수만 건 이상의 사건을 받아 여러 저장소(검색 색인, 분석 저장소, 캐시)로 흘려보내야 한다.
- 조회 모델을 사건 기록에서 다시 만들어야 한다.

## 기준선의 한계

- DB 테이블을 큐로 쓰면 소비자가 하나이거나 적을 때는 충분하다. 소비자 종류가 늘면 소비자마다 "처리함" 상태 컬럼이나 테이블이 생기고, 쓰기 경합과 정리 작업이 DB에 몰린다.
- RabbitMQ 같은 브로커는 소비자가 확인하면 메시지를 지운다. 지난 사건을 다시 읽으려면 따로 저장해 둬야 한다.
- HTTP로 각 서비스를 직접 부르면 받는 쪽이 늘 때마다 보내는 쪽 코드가 바뀌고, 받는 쪽 장애가 보내는 쪽 장애가 된다.

## 원리

- **파티션 로그.** 토픽은 파티션으로 나뉘고, 파티션은 추가만 되는 순서 있는 로그다. 순서는 파티션 안에서만 보장된다.
- **소비 위치는 소비자가 가진 숫자 하나.** 브로커는 메시지별 확인 상태 없이, 소비자 그룹의 파티션별 다음 offset만 저장한다. 그래서 확인이 싸고 되감기가 가능하다.
- **파티션 하나는 그룹 안의 소비자 하나에게만.** 그래서 같은 그룹 안 병렬성의 상한은 파티션 수다. 순서와 병렬성을 한 설정으로 함께 정한다.
- **보존은 소비와 무관하다.** 기본 삭제 정책은 시간(`retention.ms`, 기본 7일)이나 크기 한도로 오래된 세그먼트를 지운다. 압축(`cleanup.policy=compact`) 토픽은 키마다 마지막 값을 남긴다.
- **커밋의 정의.** 메시지는 ISR(동기화된 복제본)이 모두 받았을 때 커밋된다. `acks=all`은 "현재 ISR 전체"의 확인이지 복제본 전체의 확인이 아니다.
- **멱등 프로듀서와 트랜잭션.** 브로커는 프로듀서 ID와 순번으로 재전송 중복을 걸러낸다. 트랜잭션은 여러 파티션에 쓰기와 소비 offset 갱신을 원자적으로 묶는다.

## 가치

Kafka의 가치는 "메시지 전달"보다 **공유되고 다시 읽을 수 있는 사건 기록**에 있다.

- 소비자 종류가 늘어도 프로듀서와 브로커의 부담이 거의 늘지 않는다. 소비 상태가 소비자 쪽 숫자 하나이기 때문이다.
- 버그를 고친 뒤 offset을 되돌려 다시 처리할 수 있다. 새 소비자도 과거 사건부터 읽어 상태를 만든다.
- 엔터티 ID를 키로 쓰면 "같은 엔터티는 순서대로, 다른 엔터티는 병렬로"를 설정 하나로 얻는다.

그래서 Kafka가 맞는 상황은 사건이 여러 곳에서 오래 쓰이는 경우다.
소비자가 하나이고 작업을 나눠 처리하기만 하면 되는 경우에는 이 가치가 거의 쓰이지 않는다.

## 트레이드오프와 리스크

- **순서의 범위가 파티션이다.** 키 없이 보내면 순서가 없다.
  - 파티션 수를 늘리면 `hash(key) % 파티션 수`가 바뀌어 같은 키가 다른 파티션으로 가고, 기존 키의 순서가 깨진다.
  - 파티션은 줄일 수 없다.
- **병렬성 상한이 파티션 수다.** 한 메시지 처리가 느리면 그 파티션 전체가 막힌다(head-of-line blocking). 메시지별 재시도나 지연 재처리가 기본 기능에 없다.
- **소비자 기본값은 at-least-once다.** `enable.auto.commit` 기본값이 true라, 처리 전 커밋이면 유실, 처리 후 커밋 전 장애면 중복이다. 외부 DB에 쓰는 소비자는 중복을 스스로 흡수해야 한다.
- **exactly-once는 Kafka 안에서만이다.** 트랜잭션은 Kafka 토픽을 읽고 Kafka 토픽에 쓰는 경우에 성립한다. 외부 시스템으로 쓰는 경우는 그 시스템의 협조가 필요하다고 문서가 밝힌다.
- **기본 내구성 설정이 느슨하다.** `acks` 기본값은 `all`이지만 `min.insync.replicas` 기본값은 1이다. 복제본이 하나만 남아도 쓰기가 성공하고, 그 복제본마저 잃으면 확인받은 메시지가 사라진다.
- **리밸런스.** `max.poll.interval.ms`(기본 300초) 안에 다음 poll을 못 하면 소비자가 그룹에서 빠지고 파티션이 재배정된다. 처리 중이던 메시지는 다른 소비자가 다시 처리한다.
- **운영 부담.** 브로커 클러스터(KRaft 컨트롤러 포함), 토픽별 파티션·보존·복제 설정, 스키마 호환성, 소비 지연(lag) 감시가 새 일이 된다. 관리형 서비스를 써도 파티션 설계와 스키마 관리는 남는다.
- **되돌리기 어렵다.** 한번 여러 팀이 토픽을 구독하면 메시지 형식과 키 설계를 바꾸기 어렵다.

## 대안과 경계

| 대안 | 고를 때 |
|---|---|
| [DB 작업 큐](db-job-queue.md) | 소비자가 하나이고 작업량이 DB로 감당된다. 업무 데이터와 같은 트랜잭션에 작업을 넣을 수 있다. |
| [RabbitMQ](rabbitmq.md) | 작업을 나눠 처리하고, 메시지별 확인·재전달·라우팅이 중요하다. 다시 읽기는 필요 없다. |
| [Redis Streams](redis-streams.md) | 이미 Redis를 운영하고, 규모가 작고, 소비자 그룹과 보류 목록 정도면 충분하다. 메모리가 한도다. |
| Kafka 공유 그룹 | Kafka 4.2부터 운영 수준이다. 파티션 수보다 많은 소비자가 메시지 단위로 확인하며 나눠 처리한다. 순서를 포기하는 대신 큐처럼 쓴다. |

Kafka는 저장과 발행 사이의 이중 쓰기 문제를 풀지 않는다.
DB에 쓰고 Kafka에 발행하는 코드는 [Outbox와 CDC](outbox-cdc.md)가 필요하다.

## 깊이 있는 활용

- **순서가 필요한 단위를 키로 설계한다.** "주문 순서"가 필요하면 주문 ID, "계좌 잔액 순서"가 필요하면 계좌 ID를 키로 쓴다. 키의 분포가 치우치면 한 파티션이 뜨거워지므로, 키를 정하기 전에 키별 사건 수 분포를 본다.
- **파티션 수는 처음에 넉넉히 정한다.** 늘리면 키 배치가 바뀌므로, 예상 최대 소비자 수를 기준으로 처음부터 여유를 둔다. 순서가 중요한 토픽을 늘려야 하면 새 토픽을 만들고 옮기는 편이 안전하다.
- **외부 DB에 쓰는 소비자는 offset을 결과와 같은 곳에 저장한다.** 결과와 `(토픽, 파티션, offset)`을 한 트랜잭션으로 저장하고, 파티션 배정 때 그 offset으로 `seek`한다. 공식 설계 문서가 권하는, 2단계 커밋 없는 한 번 반영이다.
- **그렇지 않으면 소비자를 멱등하게 만든다.** 사건 ID를 유일 제약으로 가진 처리 기록 테이블(inbox)에 먼저 넣고, 충돌하면 건너뛴다. 같은 트랜잭션 안에서 결과도 쓴다.
- **압축 토픽을 엔터티의 최신 상태 저장소로 쓴다.** 새 소비자는 처음부터 읽어 현재 상태를 복원하고, 삭제는 null 값(tombstone)으로 표현한다. 소비자가 `delete.retention.ms`(기본 24시간)보다 밀리면 tombstone을 놓친다.
- **내구성이 중요한 토픽은 `replication.factor=3`, `min.insync.replicas=2`로 둔다.** 복제본 하나를 잃어도 쓰기가 계속되고, 둘을 잃으면 쓰기를 멈춰 유실 대신 불가용을 고른다. `unclean.leader.election.enable`은 기본값 false를 유지한다.
- **배포 때 리밸런스를 줄인다.** 인스턴스마다 고정된 `group.instance.id`를 주는 정적 멤버십을 쓰면 재시작해도 파티션이 다시 섞이지 않는다. Kafka 4.0부터 운영 수준이 된 새 리밸런스 프로토콜(KIP-848)은 증분 방식이라 전체 멈춤이 없다.
- **느린 처리는 poll 루프 밖으로 뺀다.** 한 번에 가져오는 수(`max.poll.records`, 기본 500)와 처리 시간의 곱이 `max.poll.interval.ms`를 넘지 않게 잡는다. 긴 처리는 파티션을 멈추고(`pause`) 별도 스레드에서 끝낸 뒤 재개한다.
- **처리 불가 메시지는 파티션을 막지 않게 뺀다.** 재시도 토픽과 격리 토픽(DLT)을 두고, 원래 메시지의 토픽·파티션·offset을 헤더에 남긴다. 순서가 중요한 키라면 격리 후 같은 키의 다음 메시지를 어떻게 할지 정책을 정한다.

## 임시방책의 신호

- 소비자에서 예외를 잡고 로그만 남긴 채 다음 메시지로 넘어간다. 유실이다.
- 중복이 보이자 `Thread.sleep`이나 짧은 캐시로 "최근 처리한 ID"를 걸러낸다. 재시작하면 사라지는 중복 제거다.
- 순서가 꼬이자 파티션을 1개로 줄인다. 병렬성을 통째로 버린다.
- 리밸런스가 잦자 `max.poll.interval.ms`만 크게 늘린다. 멈춘 소비자를 늦게 발견하게 될 뿐이다.
- DB 저장 후 `send()`를 호출하고, 실패하면 로그만 남긴다. 이중 쓰기다.
- 트랜잭션 프로듀서를 쓰면서 소비자는 `read_uncommitted`(기본값)로 둔다. 중단된 트랜잭션의 메시지를 읽는다.

## 실패 재현

- **처리 후 커밋 전 종료.** 소비자가 DB에 쓴 직후, offset 커밋 직전에 프로세스를 강제로 죽인다(`kill -9`). 재시작 후 같은 메시지가 다시 처리되는지 본다.
- **커밋 후 처리 전 종료.** 자동 커밋을 켠 채 처리 중간에 죽여서 유실을 만든다.
- **복제본 손실.** 복제본 3, `min.insync.replicas=1`로 확인받은 메시지가 사라지는 것을 본다.
  1. 팔로워 둘을 멈추고 `acks=all`로 쓴다.
  2. 리더를 멈추고 팔로워를 되살린다.
  3. `min.insync.replicas=2`로 반복하면 1단계의 쓰기가 거부된다.
- **파티션 증설.** 키가 있는 메시지를 보내는 중에 파티션 수를 늘리고, 같은 키가 두 파티션에 나뉘어 순서가 뒤집히는지 본다.
- **느린 처리.** 처리 시간을 `max.poll.interval.ms`보다 길게 만들어 리밸런스와 중복 처리를 만든다.
- **네트워크 지연.** [Toxiproxy](../verify/toxiproxy.md)로 클라이언트와 브로커 사이에 지연과 끊김을 넣어 프로듀서 재시도를 일으킨다. 멱등 설정을 끄고 켜서 중복을 비교한다.
- 재현 환경은 [Testcontainers](../verify/testcontainers.md)의 Kafka 모듈로 테스트 안에 만든다. 브로커 여러 대가 필요한 실험은 Docker Compose로 띄운다.

## 측정과 검증

- **유실과 중복은 전수로 잰다.** 메시지마다 연속 번호를 붙이고, 장애 주입을 여러 번(예: 30회) 반복하며 빠진 번호와 두 번 반영된 번호를 센다. 한 번이라도 0이 아니면 실패다.
- **소비 지연(lag).** `records-lag-max`나 `kafka-consumer-groups.sh --describe`의 LAG로 본다. 절대값보다 추세가 중요하고, 계속 늘면 처리량이 유입을 못 따라간다.
- **종단 지연.** 메시지에 생성 시각을 넣고 소비 시점과의 차이를 분포로 모은다. 평균이 아니라 p50, p99, 최대값을 보고, 리밸런스나 배포 구간을 따로 표시한다.
- **처리량.** perf-test 도구로 브로커 한계를 먼저 재고, 실제 소비 로직을 넣어 다시 재 병목을 가린다.
- **리밸런스 비용.** 배포 한 번에 리밸런스가 몇 번 일어나고, 그동안 소비가 몇 초 멈추는지 기록한다.

## 재검토 조건

- 소비자 종류가 하나로 줄었고 다시 읽기를 쓰지 않는다. DB 큐나 RabbitMQ로 충분할 수 있다.
- 순서가 필요 없고 메시지별 재시도가 주된 요구다. 공유 그룹이나 RabbitMQ를 검토한다.
- 사건량이 작아 클러스터 운영 비용이 이득보다 크다.
- 파티션 수를 늘려야 하는데 순서 보장이 걸린다.
