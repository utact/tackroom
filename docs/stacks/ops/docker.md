# Docker

확인: 2026-09-27, docker/docs 저장소(main) 기준. JVM 컨테이너 설정은 검색 요약으로 확인했다.

## 요약

Docker는 애플리케이션과 그 실행 환경(OS 패키지, 런타임, 설정)을 이미지 하나로 묶고, 격리된 프로세스(컨테이너)로 실행한다.
이미지는 층(layer)의 쌓음이고, 빌드는 바뀌지 않은 층을 캐시로 재사용한다.
가치의 핵심은 "내 PC에서는 되는데"를 없애는 **재현 가능한 산출물**이다. 그 재현성은 Dockerfile을 어떻게 쓰느냐에 달려 있다.

## 문제 신호

- 개발자 PC, CI, 서버에서 런타임이나 라이브러리 버전이 달라 동작이 다르다.
- 배포가 서버에 접속해 명령을 치는 절차다.
- 테스트용 DB, 브로커를 매번 손으로 설치한다.
- 이미지 빌드가 느리거나 이미지가 수 GB다.

## 기준선의 한계

기준선은 서버에 런타임을 설치하고 산출물(JAR)을 복사해 실행하는 방식이다.

- 서버마다 OS 패키지와 런타임 버전이 조금씩 다르다. 시간이 지나면 서버 상태가 문서와 달라진다(configuration drift).
- 되돌리기가 "옛 JAR 다시 복사"여서 런타임 변경은 되돌리지 못한다.
- 여러 서비스가 한 서버를 나누면 의존성과 자원이 충돌한다.

## 원리

- **층과 캐시.** 명령 하나가 층 하나이고, 층이 바뀌면 뒤의 모든 층을 다시 만든다. 그래서 자주 바뀌는 소스를 뒤에, 드물게 바뀌는 의존성 설치를 앞에 둔다.
- **다단계 빌드.** 빌드 도구가 있는 단계에서 산출물을 만들고, 실행 단계에는 산출물만 복사한다. 최종 이미지에 컴파일러와 빌드 캐시가 남지 않는다.
- **태그는 바뀐다.** 문서는 이미지 태그가 가변이라 같은 태그가 시간이 지나면 다른 이미지를 가리킬 수 있다고 설명한다. 다이제스트(`@sha256:...`)로 고정하면 바뀌지 않지만, 자동 보안 패치를 받지 못한다.
- **빌드 비밀.** 문서는 빌드 인자와 환경 변수가 최종 이미지에 남으므로 비밀을 넘기는 데 부적절하고, 비밀 마운트나 SSH 마운트를 쓰라고 한다.
- **PID 1과 신호.** 주 프로세스는 PID 1이다. 셸 스크립트 진입점에서 `exec` 없이 실행하면 애플리케이션이 종료 신호를 받지 못한다.
- **자원 제한.** 기본적으로 컨테이너에는 메모리 제한이 없다. 문서는 호스트 메모리가 부족하면 커널이 OOM으로 프로세스를 죽이고, 컨테이너가 데몬보다 먼저 죽을 가능성이 높다고 설명한다.

## 가치

Docker의 가치는 **빌드한 것과 실행하는 것이 같다는 보장**이다.

- 한 번 만든 이미지를 개발, 시험, 운영에 그대로 쓴다. 차이는 설정(환경 변수, 마운트)으로만 준다.
- 되돌리기가 이전 이미지로 다시 실행하는 것이다. 런타임과 OS 패키지까지 함께 되돌아간다.
- 테스트에서 실제 DB와 브로커를 컨테이너로 띄운다([Testcontainers](../verify/testcontainers.md)).
- 오케스트레이터([Kubernetes](kubernetes.md))와 CI([GitHub Actions](github-actions.md))의 공통 단위가 된다.

## 트레이드오프와 리스크

- **재현성은 공짜가 아니다.** 태그를 고정하지 않거나 빌드 중 `apt-get update`로 최신 패키지를 받으면 같은 Dockerfile이 다른 이미지를 만든다.
- **이미지에 비밀이 남는다.** `ENV`나 `ARG`로 넘긴 비밀, 한 층에서 복사하고 다음 층에서 지운 파일은 이미지 층에 남는다.
- **보안 표면.** 기본 이미지의 취약점, root로 실행하는 컨테이너, 불필요한 패키지가 공격 표면이 된다. 기본 이미지를 주기적으로 다시 빌드하지 않으면 패치가 쌓인다.
- **자원 제한과 런타임의 상호작용.** 최신 JDK는 컨테이너 메모리 제한을 알고, 기본 최대 힙을 제한의 25%로 둔다. 힙 외 메모리(스레드 스택, 메타스페이스, 다이렉트 버퍼)까지 합쳐 제한을 넘으면 OOM으로 죽는다.
- **파일 시스템은 휘발된다.** 컨테이너 안에 쓴 파일은 컨테이너가 사라지면 없어진다. 상태는 볼륨이나 외부 저장소에 둔다.
- **로컬 개발 경험.** macOS·Windows에서는 가상 머신 위에서 돌아 파일 공유와 성능이 리눅스와 다르다.

## 대안과 경계

| 대안 | 고를 때 |
|---|---|
| 서버에 직접 설치 | 서비스가 하나이고 서버를 코드로 관리한다(Ansible 등). |
| Buildpacks, Jib | Dockerfile 없이 언어별 모범 사례로 이미지를 만든다. Jib은 Java 프로젝트에서 Docker 데몬 없이 층을 나눠 빌드한다. |
| 관리형 PaaS | 이미지 대신 소스나 산출물을 올리면 플랫폼이 실행한다. |
| Podman 등 | 데몬 없는 실행, rootless 기본값이 필요하다. |

## 깊이 있는 활용

- **의존성 층을 분리한다.** Java라면 의존성 JAR과 애플리케이션 클래스를 다른 층에 둔다(Spring Boot의 layered JAR, Jib). 코드만 바뀌면 작은 층만 다시 올라간다.
- **다단계 빌드로 실행 이미지를 줄인다.** 빌드 단계는 JDK와 빌드 도구, 실행 단계는 JRE나 distroless 이미지에 산출물만 둔다.
- **캐시 마운트를 쓴다.** `RUN --mount=type=cache`로 Gradle·Maven·npm 캐시를 빌드 사이에 재사용한다. CI에서는 GitHub Actions 캐시 백엔드나 레지스트리 캐시로 빌드 캐시를 공유한다.
- **비밀은 비밀 마운트로.** `RUN --mount=type=secret`으로 빌드 중에만 비밀을 노출한다.
- **태그 전략과 다이제스트 고정을 함께 쓴다.** 기본 이미지는 다이제스트로 고정하고, 자동화 도구(Dependabot, Renovate)가 고정값을 갱신하는 PR을 만들게 한다. 재현성과 보안 패치를 함께 얻는다.
- **PID 1을 제대로.** 진입점은 exec 형식(`["java", "-jar", "app.jar"]`)으로 쓰고, 스크립트가 필요하면 마지막에 `exec`로 넘긴다. 종료 신호를 받아 우아하게 멈춘다.
- **JVM은 비율로 힙을 잡는다.** `-XX:MaxRAMPercentage`를 제한에 맞춰 올리고(예: 50~75%), 힙 외 메모리 여유를 남긴다. 컨테이너 메모리 사용량과 GC 로그를 함께 본다.
- **root가 아닌 사용자로 실행한다.** `USER`로 비특권 사용자를 지정한다.

## 임시방책의 신호

- `FROM openjdk:latest`처럼 가변 태그를 쓴다.
- 빌드마다 모든 의존성을 새로 받아 빌드가 몇 분씩 걸린다.
- `ENV DB_PASSWORD=...`나 `ARG TOKEN`으로 비밀을 넣는다.
- 컨테이너가 OOM으로 죽자 메모리 제한을 계속 올린다. 힙 설정은 보지 않는다.
- 종료 때 요청이 끊기는데 원인이 PID 1 신호 처리인 줄 모른다.
- 컨테이너 안에 접속해 설정을 고친다.

## 실패 재현

- **재현성.** 같은 Dockerfile을 시간을 두고 다시 빌드해 이미지 다이제스트와 설치 패키지 버전이 달라지는지 본다. 다이제스트 고정 후 반복한다.
- **비밀 잔존.** 비밀을 `ARG`로 넘긴 이미지에서 `docker history`나 층 파일로 비밀이 보이는지 확인한다.
- **신호.** 셸 형식 진입점과 exec 형식 진입점의 컨테이너에 `docker stop`을 보내 종료 시간(기본 유예 뒤 SIGKILL)과 처리 중 요청의 끊김을 비교한다.
- **메모리.** JVM 컨테이너에 메모리 제한을 걸고 부하를 줘 OOM으로 죽는 지점을 찾는다. 힙 비율을 바꿔 반복한다.

## 측정과 검증

- **빌드 시간과 캐시 적중.** 코드만 바꿨을 때의 빌드 시간, 의존성을 바꿨을 때의 빌드 시간을 기록한다.
- **이미지 크기와 층 수.** 실행 이미지 크기, 층별 크기를 본다.
- **취약점.** 이미지 스캐너(Docker Scout, Trivy 등)의 치명·높음 취약점 수를 추세로 본다.
- **자원.** 컨테이너 메모리 사용량과 제한의 비율, OOM 종료 횟수, CPU 제한에 따른 스로틀링을 본다.
- **종료 품질.** 배포 중 끊긴 요청 수를 잰다.

## 재검토 조건

- 서비스가 하나로 줄고 PaaS가 이미지 관리 없이 충분하다.
- 빌드 시간이 개발 흐름을 막는다. 층 구조와 캐시 백엔드를 다시 설계한다.
