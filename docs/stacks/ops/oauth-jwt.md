# OAuth 2.0과 JWT

확인: 2026-09-27, OAuth 2.1 초안(oauth-wg/oauth-v2-1, main), Spring Security 7.1.1 문서, RFC 8725(검색 요약) 기준. OAuth 2.1 초안이 인용하는 RFC 9700(OAuth 2.0 보안 모범 사례)의 내용은 초안의 변경 목록으로 확인했다.

## 요약

OAuth는 "누가 어떤 범위로 이 자원에 접근해도 되는가"를 토큰으로 위임하는 인가 프레임워크이고, JWT는 그 토큰을 서명된 자기 기술 형식으로 담는 방법 중 하나다.
인증(누구인가)과 인가(무엇을 해도 되는가)를 나누고, 인가 서버가 발급한 토큰을 자원 서버가 검증한다.
대부분의 사고는 흐름을 잘못 고르거나(구식 grant), 토큰 검증을 빠뜨리거나(audience, 알고리즘), 토큰을 잘못된 곳에 두는 데서 난다.

## 문제 신호

- 서비스가 여럿이고 각자 로그인과 세션을 따로 구현한다.
- 모바일 앱, SPA, 외부 파트너가 우리 API를 호출한다.
- 사내 인증 시스템(SSO)과 연결해야 한다.
- 서비스 간 호출에 공유 비밀 키를 쓴다.

## 기준선의 한계

기준선은 서버 세션(세션 ID 쿠키)과 서비스별 사용자 테이블이다.

- 단일 웹 애플리케이션이면 세션이 가장 단순하고 안전하다. 즉시 무효화도 쉽다.
- 서비스가 늘면 세션 저장소를 공유하거나, 서비스마다 로그인을 따로 만들어야 한다.
- 제3자 앱에 사용자 비밀번호를 주지 않고 권한 일부만 위임할 방법이 없다.

## 원리

- **역할 분리.** 인가 서버가 토큰을 발급하고, 자원 서버가 토큰을 검증해 요청을 허용한다. 클라이언트는 토큰을 받아 쓰기만 한다.
- **Authorization Code + PKCE.** 사용자가 인가 서버에서 로그인하고, 클라이언트는 받은 코드를 토큰으로 바꾼다. PKCE는 코드를 가로챈 공격자가 토큰으로 바꾸지 못하게 한다. OAuth 2.1 초안은 PKCE를 기본으로 요구하고 `plain` 방식을 없앴다.
- **없어지는 흐름.** OAuth 2.1 초안은 RFC 9700에 따라 Implicit grant와 Resource Owner Password Credentials grant를 뺐고, 리다이렉트 URI의 정확한 문자열 일치를 요구하고, URL 쿼리 문자열의 bearer 토큰 사용을 뺐다.
- **리프레시 토큰 보호.** 공개 클라이언트(SPA, 모바일)의 리프레시 토큰은 발신자에 묶거나(DPoP, mTLS) 한 번만 쓰게(회전) 해야 한다. 회전에서는 쓰인 옛 토큰이 다시 오면 탈취를 감지한다.
- **JWT 검증.** 서명, 알고리즘, 발급자(`iss`), 대상(`aud`), 만료(`exp`), 시작(`nbf`)을 검증한다. RFC 8725는 라이브러리가 허용 알고리즘 목록을 받아야 하고, `alg: none`이나 RS256을 HS256으로 바꿔 공개 키를 HMAC 비밀로 쓰게 하는 공격을 경고한다. 명시적 타입(`typ`)과 대상 검증도 권한다.
- **Spring Security 기본값.** 자원 서버는 발급자 URI만 설정하면 `iss`, `exp`, `nbf`를 검증하고, 시계 오차 60초를 허용한다. `aud`는 `audiences` 속성이나 검증기를 따로 설정해야 검증한다.

## 가치

OAuth와 JWT의 가치는 **자격 증명과 권한을 분리해, 여러 서비스와 클라이언트가 한 인가 서버를 믿게 하는 것**이다.

- 사용자 비밀번호는 인가 서버만 본다. 클라이언트와 자원 서버는 범위가 제한된 토큰만 다룬다.
- JWT는 자원 서버가 인가 서버를 매번 부르지 않고 서명만으로 검증하게 한다. 서비스가 늘어도 검증 비용이 늘지 않는다.
- 범위(scope)와 대상(audience)으로 토큰 하나가 할 수 있는 일을 좁힌다.

## 트레이드오프와 리스크

- **JWT는 즉시 무효화가 어렵다.** 서명만 보고 검증하므로, 만료 전에 탈취된 토큰은 쓸 수 있다. 짧은 만료와 리프레시 토큰, 필요하면 토큰 조회(introspection)나 차단 목록이 필요하다.
- **검증 누락이 곧 취약점이다.** `aud`를 검증하지 않으면 다른 서비스용 토큰이 우리 서비스에서 통한다. 알고리즘을 토큰 헤더에 맡기면 알고리즘 혼동 공격이 가능하다.
- **토큰 보관 위치.** 브라우저 `localStorage`의 토큰은 XSS 한 번에 탈취된다. 쿠키는 CSRF 대책이 필요하다. SPA에서는 백엔드가 토큰을 들고 브라우저에는 세션 쿠키만 주는 방식(BFF)이 흔히 권장된다. (미검증: 권장 문서는 이 조사에서 원문 확인하지 않았다.)
- **토큰이 커진다.** JWT에 권한과 사용자 정보를 많이 넣으면 모든 요청 헤더가 커지고, 권한 변경이 토큰 만료까지 반영되지 않는다.
- **인가 서버가 핵심 의존성이 된다.** 인가 서버와 서명 키 배포(JWKS)가 멈추면 새 로그인과 토큰 갱신이 멈춘다. 키 회전 절차가 필요하다.
- **직접 구현의 위험.** 인가 서버를 직접 만들면 표준의 보안 요구를 모두 우리가 지켜야 한다.

## 대안과 경계

| 대안 | 고를 때 |
|---|---|
| 서버 세션 | 단일 웹 애플리케이션이다. 즉시 로그아웃과 권한 변경 반영이 중요하다. |
| 불투명 토큰 + introspection | 즉시 무효화가 중요하고, 자원 서버가 인가 서버를 부르는 비용을 감수한다. |
| 관리형 인증 서비스, Keycloak 등 | 인가 서버를 직접 만들지 않는다. 대부분의 경우 이쪽이다. |
| mTLS, 서비스 메시 신원 | 서비스 간 호출의 신원 확인이 주 목적이다. 사용자 위임이 없다. |
| Client Credentials grant | 사용자 없이 서비스가 자기 권한으로 호출한다. |

## 깊이 있는 활용

- **흐름은 하나로 모은다.** 사용자가 있는 모든 클라이언트는 Authorization Code + PKCE, 서비스 간 호출은 Client Credentials. Implicit와 Password grant는 쓰지 않는다.
- **자원 서버는 대상을 반드시 검증한다.** Spring Security라면 `audiences`를 설정한다. 인가 서버는 토큰을 한 자원 서버(또는 좁은 목록)에 한정해 발급한다.
- **알고리즘을 고정한다.** 검증 쪽에서 허용 알고리즘을 명시하고 키 종류와 맞춘다. 헤더의 `alg`를 믿지 않는다.
- **짧은 액세스 토큰, 보호된 리프레시 토큰.** 액세스 토큰은 몇 분, 리프레시 토큰은 회전이나 발신자 결합으로 보호한다. 재사용 감지 시 해당 토큰 계열 전체를 폐기한다.
- **권한은 토큰에 최소한만.** 토큰에는 주체와 거친 범위만 넣고, 세밀한 권한(이 문서를 볼 수 있는가)은 자원 서버가 데이터와 함께 판단한다. RAG의 문서 권한 필터도 여기서 온다([LLM 평가](../rag/llm-evaluation.md)의 권한 위반 유형).
- **키 회전을 연습한다.** JWKS에 새 키를 먼저 공개하고, 서명 키를 바꾸고, 옛 키를 토큰 최대 수명 이후에 뺀다. `kid`로 키를 고른다.
- **시계 오차를 감안한다.** 서버 시계가 어긋나면 막 발급한 토큰이 "아직 유효하지 않음"이 된다. 허용 오차(Spring 기본 60초)를 알고, 서버 시각 동기화를 감시한다.

## 임시방책의 신호

- 모바일 앱이 사용자 ID와 비밀번호를 받아 토큰 엔드포인트에 직접 보낸다(Password grant).
- JWT를 디코드만 하고 서명은 검증하지 않는다. 또는 `aud`를 검증하지 않는다.
- 액세스 토큰 만료를 며칠로 길게 두고, 로그아웃은 클라이언트에서 토큰을 지우는 것으로 끝낸다. 탈취된 토큰은 며칠간 유효하다.
- 권한이 바뀌었는데 토큰에 박힌 옛 권한으로 계속 동작한다.
- 서비스 간 호출에 모든 서비스가 같은 정적 API 키를 쓴다.
- 토큰을 URL 쿼리에 넣어 로그에 남는다.

## 실패 재현

- **대상 혼동.** 서비스 A용으로 발급된 토큰으로 서비스 B를 호출해, `aud` 검증이 없으면 통과하는 것을 테스트로 고정한다.
- **알고리즘 혼동.** 테스트에서 `alg: none` 토큰과 RS→HS로 바꾼 토큰을 만들어 거부되는지 확인한다.
- **만료와 시계.** 만료 직후 토큰, 시계 오차 경계의 토큰으로 요청해 기대대로 거부·허용되는지 본다.
- **리프레시 토큰 재사용.** 회전된 옛 리프레시 토큰을 다시 써서 탈취 감지와 계열 폐기가 되는지 본다.
- **키 회전.** 키를 바꾸는 동안 기존 토큰과 새 토큰이 모두 검증되는지, 옛 키 제거 후 옛 토큰이 거부되는지 본다.

## 측정과 검증

- **보안 검증은 음성 사례 테스트로.** 위 실패 사례를 자동 테스트로 두고 CI에서 돌린다. 통과해야 할 것과 거부해야 할 것을 모두 둔다.
- **인증 흐름 지표.** 로그인 성공률, 토큰 갱신 실패율, 인가 서버 지연과 가용성을 본다.
- **토큰 수명.** 발급 토큰의 수명 분포와 리프레시 재사용 감지 건수를 본다.
- **외부 점검.** OWASP ASVS의 인증·세션 항목으로 주기적으로 점검한다. (미검증: 항목 번호는 확인하지 않았다.)

## 재검토 조건

- 서비스가 하나로 줄었다. 서버 세션이 더 단순하다.
- 즉시 무효화 요구가 강해졌다. 불투명 토큰이나 짧은 만료 + 차단 목록을 검토한다.
- OAuth 2.1이 RFC로 확정됐다. 변경점을 다시 확인한다.

## 출처

- IETF OAuth WG, [The OAuth 2.1 Authorization Framework](https://github.com/oauth-wg/oauth-v2-1/blob/main/draft-ietf-oauth-v2-1.md) 초안: PKCE 기본 요구와 `plain` 제거, Implicit·Password grant 제외, 리다이렉트 URI 정확 일치, 쿼리 문자열 토큰 금지, 공개 클라이언트 리프레시 토큰의 발신자 결합이나 회전. 각 항목은 RFC 9700의 해당 절을 근거로 든다.
- Spring Security 7.1.1, [OAuth 2.0 Resource Server JWT](https://github.com/spring-projects/spring-security/blob/7.1.1/docs/modules/ROOT/pages/servlet/oauth2/resource-server/jwt.adoc): 기본 검증(`iss`, `exp`, `nbf`), 시계 오차 60초, `audiences` 설정.
- [RFC 8725, JSON Web Token Best Current Practices](https://www.rfc-editor.org/rfc/rfc8725.html): 허용 알고리즘 목록, `none`과 RSA/HMAC 혼동 공격, 대상 검증, 명시적 타입. 검색 요약으로 확인했다.
