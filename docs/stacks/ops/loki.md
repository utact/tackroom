# Loki와 로그 수집

확인: 2026-09-28, Grafana Loki 문서(grafana/loki, main)와 OpenTelemetry 문서(main) 기준.

## 요약

Loki는 로그 본문을 색인하지 않고, 로그 흐름(stream)을 구분하는 라벨만 색인하는 로그 수집 시스템이다.
본문은 압축해 객체 저장소에 두고, 조회 때 라벨로 흐름을 고른 뒤 본문을 훑는다.
전문 색인을 하는 Elasticsearch 방식보다 저장과 운영이 싸다. 대신 **라벨 설계가 성능을 결정하고**, 넓은 범위의 본문 검색은 느리다.

## 문제 신호

- 인스턴스가 여럿이라 장애 때 서버마다 접속해 로그 파일을 grep한다.
- 컨테이너가 재시작되면 로그가 사라진다.
- 한 요청의 로그를 여러 서비스에 걸쳐 모아 봐야 한다.
- 로그 저장 비용이 커져 보관 기간을 줄이고 있다.

## 기준선의 한계

기준선은 애플리케이션이 구조화 로그(JSON)를 표준 출력이나 파일로 남기는 것이다.

- 한 서버에서는 `grep`과 `jq`로 충분하다. 서버가 늘면 모아서 볼 곳이 없다.
- 컨테이너 로그는 노드에 잠시 남았다가 회전되거나 사라진다.
- 로그와 트레이스, 메트릭을 잇는 방법이 없다.

## 원리

- **라벨만 색인한다.** 같은 라벨 조합의 로그가 한 흐름이 된다. 색인은 작고, 본문은 청크로 압축해 S3 같은 객체 저장소에 둔다.
- **흐름 수가 비용이다.** 라벨 값 조합이 많으면 흐름이 많아지고, 작은 청크가 많이 생겨 색인이 커지고 조회가 느려진다.
- **라벨 권고.** 문서의 권고는 다음과 같다.
  - 지역, 클러스터, 앱, 환경처럼 값이 고정되고 적은 정적 라벨을 쓴다.
  - 동적 라벨은 값이 수십 개 이하로 제한될 때만 쓴다.
  - trace ID, 주문 ID 같은 값은 라벨로 만들지 않는다.
  - 큰 테넌트도 활성 흐름 10만 개, 하루 100만 개 미만을 권한다.
- **본문 필터가 생각보다 빠르다.** 문서는 `level` 라벨 대신 `|= "level=error"` 필터가 많은 경우 비슷하게 빠르다고 적는다. 라벨로 흐름을 쪼개면 청크가 늘어서다.
- **구조화 메타데이터.** pod 이름, 사용자 ID처럼 카디널리티가 높지만 자주 거르는 값은 색인하지 않는 구조화 메타데이터로 붙인다. OpenTelemetry 형식 수집에 쓰인다.
- **LogQL.** 라벨 선택자로 흐름을 고르고 줄 필터와 파서를 잇는다. 로그에서 메트릭을 만들어 알림도 건다.

## 가치

Loki의 가치는 **로그를 싸게 오래 모으고, 메트릭·트레이스와 같은 라벨로 잇는 것**이다.

- 색인이 작고 저장소가 객체 저장소라 같은 비용으로 더 오래 보관한다.
- Prometheus와 같은 라벨 체계를 쓰면 대시보드의 메트릭에서 같은 라벨의 로그로 바로 넘어간다.
- 트레이스 ID를 로그에 남기면 트레이스에서 로그로, 로그에서 트레이스로 오간다.

## 트레이드오프와 리스크

- **넓은 전문 검색이 느리다.** 라벨로 좁히지 못하는 "지난 30일 전체에서 이 문자열"은 본문을 모두 훑는다.
- **카디널리티 사고.** 요청 ID나 사용자 ID를 라벨로 만들면 흐름이 폭발해 수집과 조회가 무너진다. 수집 에이전트가 자동으로 붙이는 라벨도 조심해야 한다.
- **수집 제한.** 수집 속도 제한, 줄 길이 제한, 너무 오래된 로그 거부 같은 기본 제한에 걸리면 로그가 버려진다.
- **로그 유실.** 에이전트 버퍼가 차거나 노드가 죽으면 전송 전 로그가 사라진다. 로그는 감사 기록이 아니다.
- **운영 부담.** 작은 규모는 단일 바이너리로 되지만, 규모가 크면 여러 구성 요소와 캐시를 운영해야 한다.

## 대안과 경계

| 대안 | 고를 때 |
|---|---|
| Elasticsearch·OpenSearch 기반 ELK | 본문 전문 검색, 복잡한 집계, 보안 분석이 주 용도다. 저장과 색인 비용을 감수한다([Elasticsearch](../search/elasticsearch.md)). |
| 관리형 로그 서비스 | 직접 운영하지 않는다. 수집량 요금을 감수한다. |
| 메트릭 | 개수와 비율을 보는 것이 목적이다. 로그에서 세지 말고 메트릭으로 낸다([Prometheus와 Grafana](prometheus-grafana.md)). |
| 감사 로그 테이블 | 유실되면 안 되는 기록(결제, 권한 변경)이다. DB에 트랜잭션으로 남긴다. |

## 깊이 있는 활용

- **로그에 trace ID를 넣는다.** OpenTelemetry SDK를 쓰면 기존 로그에 활성 트레이스와 스팬 ID가 자동으로 붙는다([OpenTelemetry](opentelemetry.md)). 요청 하나의 로그를 서비스에 걸쳐 모은다.
- **라벨은 조회 습관으로 정한다.** `app`, `env`, `namespace`로 시작해 늘 거르는 값만 라벨로 올리고, 나머지는 본문이나 구조화 메타데이터에 둔다. 값이 폭발한 라벨은 `logcli series --analyze-labels`로 찾는다.
- **조회는 좁히고 단순하게.** 시간 범위를 먼저 줄이고, 가장 구체적인 라벨을 고르고, 정규식보다 `|=`, `!=` 필터를 쓴다.
- **개수는 메트릭으로.** "분당 오류 수"를 매번 로그로 세지 말고, 애플리케이션 메트릭이나 기록 규칙으로 만든다.
- **로그 수준과 표본.** 성공 요청의 상세 로그는 표본으로 줄이고, 오류는 모두 남긴다. 개인정보는 수집 전에 가린다.

## 임시방책의 신호

- 장애 때 서버마다 SSH로 들어가 로그 파일을 본다.
- 요청 ID를 라벨로 만들어 특정 요청의 로그를 빠르게 찾으려 한다.
- 로그 문자열을 파싱해 매출이나 가입 수를 센다.
- 로그가 너무 많아지자 보관 기간만 줄이고, 무엇을 남길지는 정하지 않는다.
- 결제 기록을 로그에만 남긴다.

## 실패 재현

- **카디널리티 폭발.** 스테이징에서 요청 ID를 라벨로 넣어 부하를 걸고, 활성 흐름 수, 수집 거부, 조회 지연을 본다. 라벨을 빼고 반복한다.
- **수집 거부.** 수집 속도 제한을 넘는 로그를 보내 `rate_limited` 거부가 나는지 확인하고, 거부된 로그가 어디서 드러나는지 본다.
- **유실.** Loki를 잠시 멈춰 에이전트 버퍼가 넘치게 하고, 복구 뒤 빠진 구간을 센다.

## 측정과 검증

- **수집.** 초당 수집량, 거부된 줄 수(이유별), 에이전트 버퍼 사용량.
- **흐름.** 테넌트별 활성 흐름 수와 라벨별 고유 값 수.
- **조회.** 자주 쓰는 조회의 지연과 훑은 바이트 수.
- **비용.** 하루 저장량과 보관 기간. 로그 한 줄의 평균 크기와 수준별 비율을 본다.

## 재검토 조건

- 로그 사용의 대부분이 넓은 전문 검색과 집계다. ELK 계열을 검토한다.
- 로그로 세는 지표가 많다. 메트릭으로 옮긴다.
