# 하네스 엔지니어링

AI가 프로젝트를 수행하는 방식을 개선할 때 참조하는 공통 판단 기준이다.
지침, 도구, 상태, 검사와 실행 제어 중 무엇을 바꿀지 결정하고 효과를 검증하는 데 쓴다.
특정 플러그인이나 설치 범위를 전제로 하지 않는다.
2026-10-01에 개정했다. 호스트별 훅과 권한 동작은 설치된 버전에서 확인한다.

## 먼저 원인을 찾는다

하네스는 모델과 도구 실행을 둘러싼 환경이다.
모델에 제공하는 문맥, 도구 인터페이스, 권한, 상태 복원과 피드백이 행동에 영향을 준다.
지침을 늘리는 것만으로 개선을 판단할 수는 없다.

1. 기대 행동과 실제 실패를 요청·도구 입력·결과로 남긴다. 한 번의 실패를 모든 작업에 적용할 규칙으로 만들지 않는다.
2. 모델이 필요한 정보를 받았는지, 도구가 의도대로 실행됐는지, 결과를 확인할 기회가 있었는지 구분한다.
3. 모델·프롬프트·설정·도구·환경 중 원인에 맞는 가장 작은 변경을 고른다. 기존 설정이나 도구 설명으로 해결되면 새 컴포넌트가 필요하지 않을 수 있다.
4. 같은 초기 상태와 과제로 변경 전후를 비교한다. 실패했던 사례와 정상적으로 처리하던 사례를 함께 본다.

예를 들어 테스트 명령을 몰라 건너뛴 경우에는 실행 안내가 필요하다.
테스트 결과를 읽고도 완료를 잘못 선언했다면 판정과 피드백 경로를 봐야 한다.
외부 실행을 확실히 막아야 한다면 자연어 지침만으로는 충분하지 않다.

## 개입의 역할

아래는 설계를 돕는 분류다. 파일 종류나 제품 이름으로 역할이 고정되지는 않는다.

| 역할 | 맡는 일 | 선택할 때 | 강제 범위 |
|---|---|---|---|
| Guide | 판단 기준과 작업 절차를 제공한다. | 정보·절차가 빠져 있다. 지침과 Skill이 해당한다. | 행동을 강제하지 않는다. 읽혀도 무시될 수 있다. |
| Sensor | 결과를 관찰하고 피드백한다. | 잘못된 결과를 발견하지 못한다. 테스트와 진단 도구가 해당한다. | 관측한 결과를 알린다. 다음 행동은 별도 제어가 필요하다. |
| Gate | 보호할 전이 전에 진행을 거부한다. | 위반을 차단해야 한다. 권한 검사와 필수 CI가 해당한다. | 검사를 반드시 거치는 경로만 차단한다. 오류 시 통과·우회 경로를 확인한다. |
| Transformer | 규칙에 따라 결과를 직접 바꾼다. | 포맷처럼 수정 방법이 명확하다. | 수정 권한이 있는 산출물에 작용한다. 의미 보존과 diff를 확인한다. |

같은 테스트도 실행 후 알려 주면 Sensor이고, 통과해야 병합할 수 있으면 Gate다.
판정 방식은 역할과 별도로 정한다. 같은 Gate도 코드·모델·사람 판정을 사용할 수 있다.
종료 코드·스키마·테스트처럼 결정 가능한 조건은 코드로 검사한다.
의미와 문체 같은 열린 기준은 모델 판정을 사람 표본과 비교하고, 불일치 유형을 남긴다.
사람 판정도 기준이 모호하면 흔들리므로 판단 근거와 의견 차이를 기록한다.

### 판정 뒤의 경로

역할은 무엇을 하는지 설명하고, 판정 결과는 다음에 누가 무엇을 할지 결정한다.
Sensor가 오류를 알려도 에이전트가 반드시 고치는 것은 아니며, Gate가 차단해도 자동으로 수정 루프가 생기지는 않는다.

| 판정 결과 | 다음 행동 |
|---|---|
| 통과 | 근거를 기록하고 원래 작업을 이어간다. |
| 에이전트가 고칠 수 있는 실패 | 실패 위치·기대 결과를 에이전트에 돌려주고 수정과 재검사를 한 번의 작업 흐름으로 잇는다. 반복 횟수와 시간을 제한한다. |
| 사람의 판단이 필요한 실패 | 사용자 선택, 권한 승인, 요구 변경처럼 에이전트가 결정할 수 없는 내용을 구체적으로 제시하고 해당 작업을 멈춘다. 이미 확인된 사실과 시도한 수정도 함께 전달한다. |
| 검사 자체가 실패하거나 한도에 도달 | 통과로 둔갑시키지 않는다. 보호할 전이의 위험에 따라 중단하거나 제한된 결과를 보고한다. 사람의 결정이 필요한 경우에만 넘긴다. |

에이전트 루프로 되돌릴지 사람에게 넘길지는 지적의 종류와 권한으로 정한다.
같은 검사 실패를 반복할 때마다 사용자에게 묻지 않으며, 사람에게 넘긴 뒤에는 응답 없이 승인된 것으로 간주하지 않는다.

## 위치와 실행 경계

판정에 필요한 정보가 생긴 뒤, 보호할 행동이 일어나기 전에 개입한다.
실행이 끝난 뒤의 검사는 이미 발생한 부작용을 취소하지 못한다.

| 필요한 시점 | 연결할 수 있는 곳 | 확인할 사항 |
|---|---|---|
| 계획·구현 전 | 프로젝트 지침, Skill, 도구 설명 | 필요한 맥락에서 읽히는가. 다른 작업에도 불필요하게 적용되는가. |
| 도구 실행 전 | 호스트 권한, 실행 전 훅 | 차단할 동작과 인자를 실제로 검사하는가. 우회 경로가 있는가. |
| 실행 후 | 테스트, 린터, 실행 후 훅 | 위치·근거·다음 행동이 피드백에 포함되는가. |
| 완료 선언 전 | 완료 검사, 종료 훅 | 검사를 실패로 판정했는가. 반복 수정이 끝나지 않는가. |
| 병합·배포 전 | 필수 CI, 브랜치 보호, 배포 정책 | 로컬 검사를 건너뛰어도 경계가 유지되는가. |

Claude Code에서는 `PreToolUse`, `PostToolUse`, `Stop` 등이 연결 지점이다.
`PostToolUse`는 실행 후이며, `Stop`은 `stop_hook_active` 등으로 반복 차단을 고려해야 한다.
다른 호스트에서는 동등한 실행 지점과 실제 거부 동작을 확인한다.
로컬 Git 훅은 `--no-verify` 등으로 우회될 수 있다.
검사 오류 때 통과할지 막을지는 보호할 대상과 복구 경로에 맞춰 명시한다.

### 구현 전에 정할 실행 계약

| 항목 | 기록할 내용 |
|---|---|
| 입력과 범위 | 검사할 파일·도구·인자, 세션 시작점, 제외 대상 |
| 성공·실패·오류 | 규칙 위반과 검사기 고장·시간 초과를 별도 상태로 처리할 방법 |
| 피드백 | 실패 위치, 관측값과 기대값, 에이전트 수정·재검사 경로 또는 사람에게 넘길 구체적인 결정 |
| 반복과 복구 | 같은 지적의 반복 차단, 부분 수정, 프로세스 재시작·취소 시 상태 |
| 우회와 권한 | 검사 없이 가능한 실행 경로, 외부 데이터가 지시를 바꿀 수 있는 경로 |
| 유지 조건 | 목표 실패율·오탐·비용, 다시 측정할 시점과 제거 조건 |

예를 들어 배포 전 검사기가 시간 초과됐으면 검사 통과와 구분한다.
배포를 막도록 설계한 경우 원인을 표시하고 재시도 경로를 제공한다.
자동 포매터가 중간에 실패했으면 일부 수정된 파일을 확인한 뒤 재실행하며, 실행 전 상태로 복구됐다고 가정하지 않는다.

## 문맥과 상태

지침에는 반복해서 필요한 사실과 판단 기준을 두고, 상세 자료는 필요할 때 읽게 한다.
모든 자료를 항상 제공하면 비용과 주의 분산이 늘 수 있다.
반대로 발견할 수 없는 자료는 존재해도 도움이 되지 않는다.
발동 설명, 참조 경로와 실제 읽힌 내용을 구분해 확인한다.

대화에 있는 정보, 프로젝트 기록, 실행 중 임시 상태를 구분한다.
다음 세션에 필요한 결정은 프로젝트 문서나 호스트의 지원 기능으로 보존한다.
상태 저장이 필요하면 키의 범위, 동시 실행, 만료와 복원 실패를 설계한다.
전용 기억 시스템은 기존 기록으로 해결되지 않는 필요가 있을 때 도입한다.
플러그인의 설치 범위가 프로젝트 데이터의 공유 범위를 뜻하지는 않는다.

## 평가와 유지

- **목표에 맞게 잰다.** 기능 정확성, 사용자의 학습, 작업 완료, 비용과 지연 중 개선하려는 것을 정한다. 도구 사용 횟수 자체를 성공으로 보지 않는다.
- **동작과 판정을 분리한다.** 코드로 검사할 수 있는 결과는 독립된 검사로 본다. 설명을 모델로 채점하면 조건을 가리고 사람 표본과의 불일치를 확인한다.
- **정상 사례도 포함한다.** 지적해야 할 사례와 조용히 통과해야 할 사례를 함께 둔다. 오탐률 상한과 필요한 탐지율을 구분한다.
- **비교 조건을 맞춘다.** 모델·초기 상태·도구·예산을 맞추고 변경 유무를 반복 비교한다. 같은 프로젝트의 여러 요청은 독립 표본처럼 세지 않는다.
- **발동과 내용을 구분한다.** 명시 호출로 내용이 유효한지 확인하고, 자연스러운 요청에서도 필요한 시점에 사용되는지 평가한다.
- **반복 비용을 본다.** 같은 경고, 불필요한 확인, 이미 결정한 선택의 반복과 수정 루프를 기록한다. 종료·시간·비용 조건을 둔다.
- **변경 후 다시 판단한다.** 모델과 도구가 바뀌면 기존 장치의 효과를 다시 본다. 제거·축소 여부는 목표에 대한 이득과 유지 비용으로 결정한다.

단일 성공 사례나 문서 형식 검사는 행동 개선의 증거로 충분하지 않다.
평가용 사례를 보고 수정했다면 그 사례는 개발용으로 옮기고 별도 검증 사례를 보충한다.
새로운 실패를 만날 때마다 보편 규칙을 추가하기보다, 기존 설명과 실행 경로의 결함부터 확인한다.

### 측정 기록

| 지표 | 분모와 기록할 내용 |
|---|---|
| 작업 성공률 | 독립된 완료 기준을 만족한 과제 수 / 전체 과제 수. 중단·시간 초과도 전체에 포함한다. |
| 탐지율·오탐률 | 위반 사례 중 발견 비율과 정상 사례 중 잘못 지적한 비율을 각각 잰다. 경고 개수만으로 계산하지 않는다. |
| 성공당 비용 | 실패·재시도·하네스·채점 비용을 포함한 총비용 / 성공 과제 수. 성공이 0이면 산출 불가로 보고한다. |
| 지연과 개입 | 시작부터 검증 완료까지의 시간, 사람 수정·승인 횟수, 같은 지적의 반복 횟수 |

과제·초기 상태·모델·설정·하네스 버전·도구·예산·판정 기준을 실행 결과와 함께 남긴다.
예를 들어 테스트 실패 무시를 줄이는 장치라면 실패한 테스트를 제시하는 과제와 정상 통과 과제를 함께 실행한다.
실패 은폐 감소와 정상 작업의 불필요한 차단을 모두 기록하고, 조건별 차이와 표본 수·반복 수를 보고한다.
불확실성은 과제 단위의 의존성을 반영해 계산한다. 동일 과제의 반복 횟수를 독립 과제 수로 세지 않는다.

## 참고와 확인 범위

- [Claude Code Hooks reference](https://code.claude.com/docs/en/hooks): 2026-09-29 본문 확인. 이벤트 위치와 반환 동작은 구현할 호스트 버전에서 확인한다.
- [Claude Code Skills](https://code.claude.com/docs/en/skills): 2026-09-29 본문 확인. 발동 설명, 필요할 때 본문을 읽는 구조와 참조 파일을 설명한다.
- [Evaluating AGENTS.md](https://arxiv.org/abs/2602.11988): 저장소 지침의 효과를 비교한 연구다. 특정 코딩 평가의 결과를 모든 목적의 지침에 일반화하지 않는다.
- [LLM Evaluators Recognize and Favor Their Own Generations](https://arxiv.org/abs/2404.13076): 모델 채점의 자기 선호 편향에 관한 연구다. 독립 모델 사용만으로 판정 편향이 사라지는 것은 아니다.

위 역할 분류와 절차는 설계 지침이다. 모든 조합의 효과가 실증됐다는 의미는 아니다.
