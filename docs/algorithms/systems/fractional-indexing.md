# Fractional indexing과 순서 키

확인: 2026-10-04.

## 요약

각 항목에 정렬 가능한 위치 키를 저장하고, 두 이웃의 키 사이에 새 키를 만들어 삽입·이동한다. 보드 카드·재생 목록·문서 블록처럼 항목 순서를 자주 바꾸는 기능에서 주변 항목의 순번을 다시 쓰는 작업을 줄인다. 키 생성만으로 공동 편집의 충돌이 해결되지는 않는다.

## 문제 신호

항목 하나를 이동할 때 많은 행의 순번을 갱신하거나, 오프라인·동시 편집 때문에 배열의 숫자 인덱스가 서로 다른 항목을 가리킨다. 순서와 항목의 정체성을 따로 저장해야 하는 상황이다.

## 기준선의 한계

작은 목록은 항목 ID 배열 전체를 저장해도 충분하다. 연속 정수 순번은 중간 삽입에 재번호가 필요하며, 간격을 둔 정수도 같은 구간에 삽입을 반복하면 빈 값이 소진된다. 전체 배열 교체는 동시 변경을 병합하는 규칙이 추가로 필요하다.

## 원리

항목 ID와 위치 키를 분리하고, 같은 목록 안에서 위치 키로 정렬한다. 숫자 예시에서는 1과 2 사이에 1.5를 넣고 다음에는 1과 1.5 사이에 1.25를 넣는다. 이동은 옮기는 항목의 키를 새 이웃 사이 값으로 바꾸는 연산이다. 이 방식은 배열 전체의 위치 번호를 이동시키는 연산과 다르다.

실제 저장에는 고정 정밀도 실수 대신 길이를 늘릴 수 있는 표현을 사용한다. Rocicorp 구현은 가변 길이 정수 부분과 소수 부분을 문자열로 부호화한다. 기본 설정에서 `a1 < a1V < a2`가 성립하며, `generateKeyBetween("a1", "a2")`는 `a1V`를 만든다. 중간 문자를 넣을 여유가 없으면 접미사를 확장한다. 생성기와 저장소는 같은 문자 순서·대소문자 구분을 사용해야 한다.

## 가치

통상적인 삽입·이동은 대상 항목의 키만 갱신하므로 순번 재작성 범위를 줄인다. 순서 표현, 데이터베이스 정렬, 동시 변경 병합을 분리해 설계할 수 있다. Figma가 공개한 2017년 설계는 레이어 순서 변경에 이 원리를 사용한다.

## 트레이드오프와 리스크

좁은 구간에 삽입을 반복하면 키가 길어져 저장·인덱스·비교 비용이 늘어난다. 두 작성자가 같은 이웃을 보고 같은 결정적 키를 만들면 충돌한다. `(위치 키, 항목 ID)`로 최종 정렬 순서를 통일해도 같은 위치 키 사이에 새 키를 만드는 문제는 남는다. 동일 항목의 동시 이동, 삭제와 이동의 충돌도 별도 병합 규칙이 필요하다.

## 대안과 경계

작은 목록은 ID 배열, 단일 작성자는 간격 정수와 필요 시 재번호가 더 단순할 수 있다. 중앙 서버는 충돌한 삽입의 키를 다시 발급할 수 있다. 분산 환경의 무작위 접미사는 충돌 확률을 줄이지만 충돌 불가능성을 보장하지 않는다. 문자·문단의 연속성이 중요한 공동 편집에서는 동시에 삽입한 묶음이 서로 끼어드는 문제가 있어 시퀀스 CRDT나 트리 기반 위치 표현을 비교한다. [CRDT 병합](crdt-calm.md)은 수렴 조건을 다루는 보완 자료다.

## 깊이 있는 활용

여러 항목을 한 구간에 넣을 때는 하나씩 같은 경계를 좁히기보다 묶음 키 생성으로 길이를 줄인다. 목록 ID를 포함한 정렬 범위, 같은 키의 처리, 구버전 키의 호환성을 정의한다. 키를 다시 짧게 부호화하는 재번호 작업은 기존 키를 기준으로 보낸 지연된 이동과 충돌할 수 있으므로 목록 버전·중앙 조정·재시도 중 사용할 규칙을 먼저 정한다. 이는 키 생성 함수 밖의 저장 설계다.

## 임시방책의 신호

위치 키를 항목 ID로 쓰거나, 평균을 계산하는 실수 컬럼이면 무한히 삽입할 수 있다고 가정한다. 화면에서는 문자 코드 순서로, 데이터베이스에서는 대소문자를 무시하는 순서로 정렬한다. 키 생성 라이브러리를 도입한 사실만으로 모든 공동 편집 충돌이 해결됐다고 설명한다.

## 실패 재현

직접 계산: 2026-10-04 Windows Python 3.12.12에서 `lo=1.0`, `hi=2.0`으로 시작해 `mid=(lo+hi)/2`를 계산하고 `hi=mid`로 바꿨다. 53번째 계산에서 `hi=1.0000000000000002`와 `lo=1.0`의 중간값이 `1.0`으로 반올림됐다. 이때 엄격한 `lo < mid < hi`가 깨졌다. 고정 정밀도 실수의 한계이며 문자열 키 구현의 성능 측정은 아니다.

제안 실험: 두 작성자가 같은 구간에 동시에 삽입하고, 항목 ID를 보조 정렬값으로 쓴 뒤 같은 위치 키를 가진 항목 사이에 다시 삽입한다. 동시 항목 묶음의 섞임, 데이터베이스 정렬 규칙 차이, 재번호 전 키를 가진 지연된 이동도 재현한다.

## 측정과 검증

생성 키의 엄격한 사이 관계, 키의 유일성 정책, 화면·저장소의 정렬 일치, 최종 순서 수렴을 각각 검사한다. 반복 삽입의 키 길이 분포, 변경한 행 수, 인덱스 크기와 이동 지연을 측정한다. 실제로 확인한 실행 결과는 위 실수 계산이며, 라이브러리·데이터베이스·공동 편집 실험은 제안이다.

## 재검토 조건

키 길이 제한, 동시 편집량, 오프라인 기간이나 항목 묶음의 연속성 요구가 바뀌면 표현과 병합 규칙을 다시 선택한다. 라이브러리 버전·문자 집합을 바꾸면 기존 키와의 정렬 호환성을 확인한다. 재번호 빈도가 높아지면 간격 배분과 다른 순서 자료구조를 비교한다.
