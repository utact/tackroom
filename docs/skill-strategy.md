# 기술 판단 스킬 전략

2026-09-28에 정한 설계다.
스킬을 만들기 전에 구조, 개입 방식, 평가를 먼저 정한다.
하네스 일반 원칙은 [하네스 엔지니어링](harness-engineering.md)을 따른다.

## 풀려는 문제

맥락 없이 기능을 만들면 AI는 증상만 넘기는 임시방책을 고른다.
두 방향이 있다.

- **요구를 재지 않고 기준선에 머문다.** 채팅을 만들며 `setInterval` 폴링을 쓰고, WebSocket이나 SSE는 검토하지 않는다.
- **원인을 재지 않고 기술을 붙인다.** API가 느리다는 말에 원인을 찾지 않고 Redis를 붙인다.

둘 다 진단을 건너뛴 것이다.
스킬은 특정 기술을 권하지 않고, 문제를 재고 대안을 비교하는 단계를 되살린다.
기준선이 맞으면 기준선을 고르는 것도 성공이다.

## 판단의 전제

- **현재 규모는 근거가 아니다.** "사용자가 적으니 폴링으로 충분하다"는 판단을 미룬 것이다. 계산은 목표 규모로 하고, 목표가 없으면 가정을 적는다.
- **학습도 목적이다.** 그래서 "작으니까 대충"도, 학습을 핑계로 맞지 않는 기술을 들이는 것도 버린다. 배울 것은 "이 문제에 왜 이 기술인가"이다.
- **기준선은 문제의 성질로 정당화한다.** 폴링이 맞는 채팅도 있다.
  - 상담원이 분 단위로 답하는 문의 채팅
  - 요청 시간이 제한된 서버리스처럼 긴 연결을 유지할 수 없는 환경
  - 푸시 연결이 막힌 네트워크의 대체 경로
- **증상에서는 원인부터 잰다.** 느린 원인이 인덱스라면 답은 캐시가 아니라 인덱스다([Redis 캐시](stacks/search/redis-cache.md)의 기준선).
- **기준선을 골라도 경계를 적는다.** 어느 수치에서 이 선택이 깨지는지 재검토 조건에 숫자로 둔다.

## 재료와 스킬의 관계

- [기술 스택 조사](stacks/README.md)의 카드가 원본이다. 주장, 출처, 확인 날짜는 카드에만 둔다.
- 스킬은 카드에서 판단에 쓰는 부분만 줄여 만든다. 문제 신호, 기준선 계산, 대안과 경계, 임시방책의 신호, 측정 방법이다.
- 스킬의 모든 줄은 카드를 가리킨다. 테스트가 연결이 끊긴 줄을 찾는다.

## 구조

진입 스킬 하나와 영역별 참조 파일로 나눈다.

```
plugin/techjudge/
  skills/tech-judgment/
    SKILL.md            # 발동 조건, 판단 절차, 결정 기록 양식
    areas/comm.md       # 영역별 참조. 필요한 영역만 읽는다.
    areas/storage.md
    ...
  hooks/                # 코드에서 드러나는 임시방책을 알리는 Sensor
evals/techjudge/        # 평가 과제와 채점기
```

- **진입 스킬은 짧게 둔다.** 설명에는 기술 선택이 생기는 작업(기능 설계, 실시간 갱신, 파일 처리, 재시도, 대기열, 캐시)만 발동 조건으로 쓴다.
- **영역 파일은 필요할 때만 읽는다.** 11개를 모두 올리면 컨텍스트를 쓰고, 지침이 많을수록 성능이 떨어진 보고도 있다.
- **스킬을 영역마다 쪼개지 않는다.** 채팅처럼 여러 영역에 걸친 문제에서 하나만 발동하기 쉽다.

## 판단 절차

1. **증상이면 원인부터 잰다.** 원인이 기존 도구 안에서 고쳐지면 거기서 끝난다.
2. **문제 신호를 목표 규모의 숫자로 적는다.** 반응 시간, 동시 접속 수, 파일 크기, 유실 허용 같은 성질이다.
3. **기준선으로 계산한다.** 예를 들어 폴링은 요청 수가 접속 수 ÷ 간격이고, 평균 지연이 간격의 절반이다.
4. **문제의 성질이 기준선에 맞으면 기준선을 고른다.**
5. **대안 둘 이상을 비교한다.** 고른 기술, 버린 기술, 버린 이유를 적는다.
6. **잃는 것을 적는다.** 이 상황에 해당하는 트레이드오프와 대응이다.
7. **검증을 정한다.** 실패 재현 하나와 측정 지표 하나 이상이다.
8. **결정 기록을 남긴다.**

결정 기록은 `신호`, `기준선 계산`, `선택`, `버린 대안`, `잃는 것`, `검증`, `재검토 조건`의 일곱 줄이다.
채점기가 항목 유무를 코드로 확인할 수 있다.

## 개입 방식

| 역할 | 맡는 것 | 이유 |
|---|---|---|
| Guide(스킬) | 판단 절차 전체 | 기술 선택은 조건으로 판정하기 어렵다. 요즘 모델은 절차만 주면 잘 따르는 편이다. |
| Sensor(`PostToolUse`) | 코드에 남는 임시방책 | 코드로 찾을 수 있는 신호만 알리고, 막지 않는다. |
| Gate | 두지 않는다 | 기술 선택이 틀렸다고 코드로 확정할 수 없다. |
| Eval | Guide와 Sensor의 효과 | 효과가 없으면 뺀다. |

Sensor 후보는 다음과 같다.

- 메시지·알림 경로를 부르는 `setInterval`과 `fetch`, 커서 없는 "최근 N개" 조회
- 사용자 파일명으로 만든 저장 경로, 업로드 바이트를 메모리에 모두 올리는 코드
- 타임아웃 없는 클라이언트, 백오프 없는 재시도 루프
- 요청 처리 안의 `Thread.sleep`이나 긴 동기 작업

Sensor는 kowrite처럼 규칙마다 양성·음성 사례를 두고, 오탐률과 재현율에 바닥값을 둔다.

## 평가

Guide는 강제력이 없으므로 평가가 유일한 근거다.
평가는 스킬과 분리해 `evals/`에 둔다.
과제 하나는 초기 저장소 상태, 요청 원문, 채점 기준으로 이루어진다.

### 회귀 사례

- 실제로 관찰한 실패만 요청 원문 그대로 넣는다. 재구성한 요청은 추측이라 넣지 않는다.
- 원문은 실제 작업에서 다시 보인 실패, 또는 차원 사례를 스킬 없이 돌린 실행에서 얻는다.
- 채팅 폴링은 아직 원문이 없어 차원 사례로 둔다. 스킬 없이 돌려 폴링이 나오면 첫 회귀 사례로 옮긴다.

### 차원 사례

| 차원 | 값 |
|---|---|
| 영역 | 조사 목록의 11개 영역 |
| 정답 방향 | 기준선이 맞다 / 기준선을 넘어야 한다 |
| 기준선이 맞는 근거 | 지연 요구 / 실행 환경 / 네트워크 제약 / 원인이 기존 도구 안에 있다 |
| 요청의 명시성 | 기술을 지정했다 / 문제만 말했다 |
| 운영 여건 | 운영 인력이 있다 / 없다 |

- 모든 영역에 두 정답 방향을 둔다. "기준선이 맞다" 사례가 없으면 과한 설계를 잡지 못한다.
- 규모는 정답을 바꾸지 않으므로 차원에 두지 않는다. 대신 요청에 "사용자가 적다"를 섞어 이 말에 끌리는지 본다.
- 겉이 같고 정답이 갈리는 짝 사례를 둔다.
  - 채팅: 그룹 채팅(푸시), 상담 문의 채팅(폴링), 서버리스 채팅(환경 제약을 따진다)
  - 느린 API: 인덱스 부재(인덱스), 반복되는 비싼 집계(캐시 검토)
- 사용자가 기술을 지정했으면 따르는 것이 정답이다. 명백한 위험만 한 줄로 알린다.
- 차원 값마다 사례가 있는지 메타 테스트로 검사한다.

### 채점

- **코드 채점을 먼저 쓴다.** 임시방책 패턴, 선택한 기술의 흔적(`EventSource`, 커서 파라미터 등), 결정 기록 항목을 본다.
- **모델 채점은 판단의 질에만 쓴다.** 계산과 근거가 상황에 맞는지 루브릭으로 본다. 결론이 맞아도 근거가 규모뿐이면 실패다.
- 채점 모델은 결과를 만든 모델과 다르게 두고, 표본을 사람이 채점해 일치율을 기록한다.
- Sensor가 조용했다는 사실은 채점에 쓰지 않는다.

### 지표

- **통과율 차이.** 같은 과제를 스킬 있음과 없음으로 여러 번 돌려 차이와 신뢰 구간을 낸다([측정 통계](stacks/verify/statistics.md)).
- **과한 설계율.** "기준선이 맞다" 과제에서 새 기술을 들인 비율이다. 스킬이 이 수치를 올리면 실패다.
- **근거 오류율.** 규모만을 근거로 삼거나, 원인을 재지 않고 기술을 고른 비율이다.
- **일관성.** k번 모두 통과한 비율(pass^k)이다.
- **비용.** 통과한 결과 하나당 토큰과 시간이다.
- 통과율에는 바닥값을 두고, 오르면 바닥을 올린다.

## 유지와 제거

- 모델이 바뀌면 다시 잰다. 스킬 없이도 통과율이 같은 영역은 영역 파일을 뺀다.
- 카드의 확인 날짜가 오래되면 원본을 다시 확인하고 스킬을 다시 만든다.
- 새 실패는 회귀 사례로 먼저 넣고, 실패를 확인한 뒤 카드와 스킬을 고친다.

## 다음 단계

1. 통신 영역 차원 사례로 평가 틀을 만든다. 스킬 없이 돌려 기준 통과율을 재고, 나온 실패를 회귀 사례로 옮긴다.
2. 진입 스킬과 통신 영역 파일을 만들어 같은 과제로 비교한다.
3. 효과가 확인되면 나머지 영역과 Sensor를 붙인다.
