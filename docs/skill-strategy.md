# 기술 판단 스킬 전략

2026-09-28에 정한 설계다. 스킬을 만들기 전에 구조, 개입 방식, 평가를 먼저 정한다.
하네스 일반 원칙은 [하네스 엔지니어링](harness-engineering.md)을 따른다.

## 풀려는 문제

맥락 없이 기능을 만들면 AI는 눈앞의 증상만 넘기는 임시방책을 고른다.
채팅을 만들 때 `setInterval`로 목록을 다시 받는 폴링이 대표적이다. WebSocket, SSE, 순번 기반 이어받기는 검토조차 하지 않는다.
원인은 모델이 기술을 몰라서라기보다, **문제 신호를 보고 기준선의 한계를 계산하고 대안을 비교하는 단계를 건너뛰기 때문**이라고 본다.
스킬은 이 단계를 되살리는 것을 목표로 한다. 새 기술을 많이 쓰게 하는 것이 목표가 아니다. 기준선이 맞는 상황에서는 기준선을 고르는 것도 성공이다.

반대 방향의 실패도 같은 뿌리다. "API가 느리다 → Redis를 붙인다"는 원인을 재지 않고 기술을 고른 것이고, "채팅 → 폴링"은 요구를 재지 않고 기준선에 머문 것이다.
둘 다 진단을 건너뛰었다. 스킬이 막으려는 것은 특정 기술의 선택이 아니라 이 건너뜀이다.

## 판단의 전제

- **현재 규모는 근거가 아니다.** "사용자가 적으니 폴링으로 충분하다", "트래픽이 적으니 타임아웃은 나중에"는 판단이 아니라 판단을 미룬 것이다. 계산은 요구가 정한 목표 규모로 한다. 목표 규모가 없으면 가정을 세워 적는다.
- **학습도 목적이다.** 이 저장소의 프로젝트는 기술을 원리부터 이해하고 측정해 보는 데에도 의의가 있다. 그래서 "작으니까 대충"은 버린다. 반대로 학습을 핑계로 문제에 맞지 않는 기술을 들이는 것도 버린다. 학습의 대상은 기술 자체가 아니라 "이 문제에 왜 이 기술인가"이다.
- **기준선은 문제의 성질로 정당화한다.** 폴링이 맞는 채팅도 있다. 상담원이 분 단위로 답하는 문의 채팅, 긴 연결을 유지할 수 없는 실행 환경(요청 시간이 제한된 서버리스), 푸시 연결이 막힌 네트워크의 대체 경로가 그렇다. 근거는 지연 요구, 실행 환경, 네트워크 같은 성질이어야 하고, 사용자 수가 적다는 사실은 근거가 되지 않는다.
- **증상이 아니라 원인에서 시작한다.** 느림, 유실, 중복 같은 증상은 먼저 재서 원인을 찾는다. 느린 API라면 쿼리 계획, N+1, 외부 호출 중 어디서 시간이 드는지 보고, 원인이 인덱스라면 캐시가 아니라 인덱스가 답이다([Redis 캐시](stacks/search/redis-cache.md)의 기준선).
- **기준선을 골라도 경계를 기록한다.** 어떤 수치에서 이 선택이 깨지는지 계산해 재검토 조건에 숫자로 둔다. 기준선을 고른 결정도 이렇게 배울 거리가 된다.

## 재료와 스킬의 관계

- [기술 스택 조사](stacks/README.md)의 카드가 원본이다. 주장, 출처, 확인 날짜는 카드에만 둔다.
- 스킬은 카드에서 판단에 필요한 부분만 줄여 만든다. 문제 신호, 기준선의 계산, 대안과 경계, 임시방책의 신호, 측정 방법이 들어간다. 원리와 깊이 있는 활용은 필요할 때 카드를 읽게 한다.
- 스킬의 모든 줄은 카드 하나 이상을 가리킨다. 카드가 바뀌면 스킬을 다시 만들고, 테스트가 연결이 끊긴 줄을 찾는다.

## 구조

진입 스킬 하나와 영역별 참조 파일로 나눈다.

```
plugin/techjudge/
  skills/tech-judgment/
    SKILL.md            # 언제 쓰는지, 판단 절차, 결정 기록 양식
    areas/comm.md       # 영역별 참조. 필요한 영역만 읽는다.
    areas/storage.md
    ...
  hooks/                # 코드에서 드러나는 임시방책을 알리는 Sensor
evals/techjudge/        # 평가 과제와 채점기
```

- **진입 스킬은 짧게 둔다.** 설명(`description`)에는 발동 조건만 쓴다. 기능 설계, 실시간 갱신, 파일 처리, 재시도, 대기열, 캐시처럼 기술 선택이 생기는 작업이다. 본문에는 판단 절차와 결정 기록 양식만 둔다.
- **영역 파일은 필요할 때만 읽는다.** 영역이 11개라 모두 올리면 컨텍스트를 쓴다. 지침을 늘리면 성능이 떨어진 보고도 있다. 절차의 첫 단계에서 해당 영역을 고르고 그 파일만 읽게 한다.
- **스킬을 여러 개로 쪼개지 않는다.** 영역마다 스킬을 두면 발동 판단이 영역 수만큼 늘고, 영역이 겹치는 문제(채팅은 통신, 저장, 비동기에 걸친다)에서 하나만 발동한다.

## 판단 절차

스킬 본문이 요구하는 순서다.

1. **증상이면 원인부터 잰다.** 성능·장애 증상에서 출발했다면 측정으로 원인을 찾는다. 원인이 기존 도구 안에서 고쳐지면 거기서 끝난다.
2. **문제 신호를 적는다.** 요구에서 관찰된 성질(초 단위 반응, 동시 접속 수, 파일 크기, 유실 허용)을 목표 규모의 숫자로 적는다. 모르면 가정을 적는다.
3. **기준선으로 계산한다.** 영역 파일의 기준선 공식으로 비용과 한계를 계산한다. 예를 들어 폴링은 요청 수가 접속 수 ÷ 간격이고 평균 지연이 간격의 절반이다.
4. **문제의 성질이 기준선에 맞으면 기준선을 고른다.** 여기서 끝나는 것도 정답이다. 단, 현재 규모가 작다는 것은 이유가 되지 않는다.
5. **대안 둘 이상을 경계 표로 비교한다.** 고른 기술과 버린 기술, 버린 이유를 적는다.
6. **잃는 것을 적는다.** 트레이드오프와 리스크 중 이 상황에 해당하는 것과 대응을 적는다.
7. **검증을 정한다.** 실패 재현 하나와 측정 지표 하나 이상을 정한다. 도구(k6, Toxiproxy, Testcontainers)와 통계 기준을 쓴다.
8. **결정 기록을 남긴다.** 아래 양식으로 짧게 남긴다. 사용자가 원하지 않으면 응답 안에만 둔다.

결정 기록 양식은 `신호`, `기준선 계산`, `선택`, `버린 대안`, `잃는 것`, `검증`, `재검토 조건`의 일곱 줄이다.
기준선을 골랐다면 `재검토 조건`에 선택이 깨지는 수치를 쓴다.
카드 양식을 줄인 것이라 채점기가 항목 유무를 코드로 확인할 수 있다.

## 개입 방식

모든 판단을 강제할 수는 없다. 역할별로 할 수 있는 것만 맡긴다.

| 역할 | 맡는 것 | 이유 |
|---|---|---|
| Guide(스킬) | 판단 절차 전체, 대안 비교, 잃는 것 | 기술 선택은 조건으로 판정하기 어렵다. 요즘 모델은 절차만 주면 스스로 잘 따르는 편이다. |
| Sensor(`PostToolUse`) | 코드에 남는 임시방책의 모양 | 카드의 "임시방책의 신호" 중 코드로 찾을 수 있는 것만 알린다. 막지 않는다. |
| Gate | 두지 않는다 | 기술 선택이 틀렸다고 코드로 확정할 수 없다. 오탐으로 막으면 작업 자체를 망친다. |
| Eval | Guide와 Sensor의 효과 | 강제할 수 없는 Guide는 평가로 효과를 확인하고, 효과가 없으면 뺀다. |

Sensor 후보는 다음과 같다. 모두 "이 신호가 보인다, 판단 절차를 거쳤는가"를 알리는 수준이다.

- 채팅·메시지·알림 경로를 부르는 `setInterval`과 `fetch`의 조합, 커서 없는 "최근 N개" 조회.
- 사용자 파일명으로 만든 저장 경로, 업로드 바이트를 메모리에 모두 올리는 코드.
- 타임아웃 없는 HTTP·DB 클라이언트 생성, 백오프 없는 재시도 루프.
- 요청 처리 안의 `Thread.sleep`이나 긴 동기 작업.

Sensor는 kowrite와 같은 방식으로 검증한다. 탐지 규칙마다 양성·음성 사례를 두고, 오탐률과 재현율에 바닥값을 둔다.

## 평가

Guide는 강제력이 없으므로 평가가 유일한 근거다. 평가는 스킬과 분리해 `evals/`에 둔다.

### 과제

과제 하나는 초기 저장소 상태, 사용자 요청 원문, 채점 기준으로 이루어진다.

- **회귀 사례.** 실제로 관찰한 실패를 요청 원문 그대로 넣는다. 결과를 고치려고 요청을 다듬지 않는다.
- **차원 사례.** 규칙이 충분히 덮는지 확인하려고 차원의 곱으로 만든다.

회귀 사례에는 원문이 있는 것만 넣는다. 기억으로 재구성한 요청은 관찰이 아니라 추측이므로 회귀 사례가 될 수 없다.
원문은 두 경로로 얻는다.

- 실제 작업에서 실패가 다시 보이면 요청문, 초기 상태, 결과를 그대로 저장한다.
- 차원 사례를 스킬 없이 돌린 결과에서 실패가 나오면, 그 실행의 요청과 결과가 곧 원문이다.

채팅 폴링은 아직 원문이 없다. 그래서 회귀 사례가 아니라 차원 사례(통신, 기준선을 넘어야 함, 문제만 말함)로 넣는다.
스킬 없이 돌려 폴링이 나오면 그 실행을 첫 회귀 사례로 옮긴다.

### 차원

| 차원 | 값 |
|---|---|
| 영역 | 조사 목록의 11개 영역 |
| 정답 방향 | 기준선이 맞다 / 기준선을 넘어야 한다 |
| 요청의 명시성 | 기술을 지정했다 / 문제만 말했다 |
| 기준선이 맞는 근거 | 지연 요구 / 실행 환경 / 네트워크 제약 / 원인이 기존 도구 안에 있다 |
| 운영 여건 | 운영 인력이 있다 / 없다 |

- 모든 영역에 두 정답 방향이 있어야 한다. "기준선이 맞다" 사례가 없으면 과한 설계를 잡지 못한다. 예를 들어 분 단위로 갱신하는 관리자 대시보드는 폴링이 정답이다.
- 규모는 차원에 두지 않는다. "사용자가 적다"는 기준선을 고를 근거가 아니므로 정답 방향을 바꾸지 않는다. 대신 요청에 "사용자가 적다"를 넣은 사례를 두어, 이 말에 끌려 판단을 건너뛰는지 본다.
- 짝 사례를 둔다. 표면이 같고 정답이 갈리는 과제다.
  - 채팅: 그룹 채팅(푸시가 맞다), 상담 문의 채팅(폴링이 맞다), 서버리스에서의 채팅(환경 제약을 따져야 한다).
  - 느린 API: 인덱스가 없어서 느리다(인덱스가 맞다), 비싼 집계가 반복된다(캐시를 검토한다).
- 사용자가 기술을 지정한 경우에는 지정을 따르는 것이 정답이다. 명백한 위험이 있을 때만 한 줄로 알린다.
- 이 조건은 kowrite 테스트처럼 메타 테스트로 확인한다. 차원 값마다 사례가 하나 이상 있는지 검사한다.

### 채점

- **코드 채점을 먼저 쓴다.** 결과 저장소에서 임시방책 패턴의 유무, 선택한 기술의 흔적(`EventSource`, WebSocket 핸들러, 커서 파라미터), 결정 기록 일곱 줄의 유무를 본다.
- **모델 채점은 판단의 질에만 쓴다.** 기준선 계산이 맞는지, 버린 대안의 이유가 상황에 맞는지를 루브릭으로 채점한다. 결론이 맞아도 근거가 "규모가 작다"뿐이면 실패로 채점한다. 채점 모델은 결과를 만든 모델과 다르게 두고, 표본을 사람이 채점해 일치율을 기록한다.
- 스킬의 Sensor가 조용했다는 사실은 채점에 쓰지 않는다. 채점은 하네스와 분리한다.

### 지표

- **스킬 있음과 없음을 같은 과제로 비교한다.** 과제마다 여러 번 실행하고, 통과율 차이와 신뢰 구간을 낸다([측정 통계](stacks/verify/statistics.md)).
- **과한 설계율.** "기준선이 맞다" 과제에서 새 기술을 들인 비율이다. 스킬이 이 수치를 올리면 실패로 본다.
- **근거 오류율.** 결론과 상관없이 현재 규모나 증상만을 근거로 삼은 비율이다. 원인 측정 없이 기술을 고른 경우도 여기에 센다.
- **일관성.** 같은 과제를 k번 돌려 모두 통과한 비율(pass^k)을 함께 본다. 한 번 통과는 우연일 수 있다.
- **비용.** 통과한 결과 하나당 토큰과 시간이다. 스킬과 영역 파일을 읽는 비용을 포함한다.
- 통과율에는 kowrite처럼 바닥값을 두고, 오르면 바닥을 올린다.

## 유지와 제거

- 모델이 바뀌면 스킬 없음 조건을 다시 잰다. 스킬 없이도 통과율이 같은 영역은 영역 파일을 뺀다.
- 카드의 확인 날짜가 오래되면 원본을 다시 확인하고 스킬을 다시 만든다.
- 새로 관찰한 실패는 먼저 회귀 사례로 넣고, 그다음 카드와 스킬을 고친다. 사례가 실패하는 것을 확인한 뒤 고친다.

## 다음 단계

1. 채팅을 포함한 통신 영역 차원 사례로 평가 틀을 먼저 만든다. 스킬 없이 돌려 기준 통과율을 재고, 나온 실패를 회귀 사례로 옮긴다.
2. 진입 스킬과 통신 영역 파일을 만들고 같은 과제로 비교한다.
3. 효과가 확인되면 나머지 영역 파일과 Sensor를 차례로 붙인다.
