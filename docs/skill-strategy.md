# 스킬 구조와 검증

이 문서는 Tackroom의 조사 자료를 Skill로 배포하고 유지하는 방법을 설명한다.
하네스의 원칙은 [하네스 엔지니어링](harness-engineering.md), 구현·표현의 근거는 [기술](stacks/README.md)·[수학·알고리즘](algorithms/README.md)·[디자인](design/README.md) 카드에 둔다.

## 서로 다른 두 판단 맥락

| 플러그인 / Skill | 발동할 상황 | 제공할 것 |
|---|---|---|
| `techjudge` / `tech-judgment` | 기능의 처리·표현·상호작용 방식 선택 | 현재 맥락의 후보 비교·적용·검증 |
| `harness` / `harness-engineering` | AI의 반복 실수, 지침 미준수, 도구 사용 실패, 피드백·권한·평가 설계 | 원인 진단, 개입 위치와 방식, 변경 전후 평가 |

기술 이름이나 Skill 명령을 사용자가 먼저 말하지 않아도 해당 상황에서 선택될 수 있게 설명한다.
오타 수정이나 이미 정해진 구현의 단순 변경까지 새로운 기술 선택으로 확대하지 않는다.
애플리케이션 버그만으로 AI 실행 환경까지 바꾸지는 않는다.
두 문제가 함께 생기면 각 문제에 필요한 참조를 함께 사용할 수 있다.

## 기술 판단의 목적

주니어 개발자가 일반적인 개발을 진행하며 적합한 기술을 발견하고 적용 경험을 쌓게 한다.
사용자가 카드를 고르거나 학습 과제를 별도로 준비할 필요가 없어야 한다.
작은 규모에서도 학습은 독립적인 도입 이유다.
현재 기능과 연결되는 원리, 추가 부담과 검증할 동작을 설명한다.
기술 수를 늘리는 것, 설치만 끝내는 것, 기존 스택을 무조건 유지하는 것을 성공 기준으로 삼지 않는다.
후보는 현재 기능에서 사용할 원리와 관찰할 동작이 있어야 한다. 단지 새 기술이라는 이유로 도입하지 않는다.
기술이 낯설다는 사실만으로 도입하지 않는다. 현재 기능에서 원리를 구현·검증할 수 없거나 얻을 경험에 비해 설치·운영·유지 부담이 크면 현재 방식을 선택한다.
별도 학습 모드를 켤 필요는 없으며, 사용자의 의존성·시간·비용 제약과 기존 선택을 따른다.

현재 요청·코드·제약·기존 결정을 읽고 관련 후보를 찾는다.
증상이 있다면 원인을 진단하고, 실제 개선 주장과 학습 목적을 구분한다.
이미 허용된 선택과 범위는 이어받으며, 보류한 제안은 조건이 바뀌었을 때 다시 검토한다.
중요한 선택 이유와 검증 결과는 기존 프로젝트 기록에 남긴다.
학습·포트폴리오에서는 구현, 실행 방법, 실패 재현과 비교 결과가 지속해서 남길 성과다.
학습 완료나 작은 규모는 기술 제거의 근거가 아니다. 대안을 비교하는 경우에도 기존 구현과 판단 근거를 보존한다.
상시 실행 자원의 비용 관리와 포트폴리오 구현의 보존은 따로 판단한다.
매 작업에 고정된 보고서나 학습 확인 시험을 요구하지 않는다.

## 패키지와 적용 범위

각 플러그인은 `skills/<이름>/SKILL.md`와 그 아래 `references/`를 포함한다.
`kowrite`는 별도의 한국어 작성 규칙 플러그인이며 두 Skill의 의존성이 아니다.
추가 세션 훅, 패턴 센서, 전용 기억 저장소와 기술 선택 차단 Gate는 포함하지 않는다.
발동 실패가 반복되면 먼저 설명·참조·호스트 설정을 확인하고, 보조 장치의 효과를 따로 비교한다.

플러그인은 사용자·프로젝트 공유·프로젝트 개인 범위 중 원하는 범위에서 활성화할 수 있다.
활성화 범위는 어디서 제공할지의 설정이다. 판단은 현재 프로젝트의 맥락에 따른다.
새 세션은 남아 있는 대화·코드·프로젝트 기록을 활용하며 저장하지 않은 결정을 기억한다고 가정하지 않는다.
설치 방법은 [README](../README.md)에 둔다.

## 참조를 유지하는 방법

`docs/`를 편집 원본으로 두고 `scripts/sync_references.py`가 플러그인의 참조를 생성한다.
기술 Skill에는 기술·수학·알고리즘·디자인 색인과 카드를, 하네스 Skill에는 범용 하네스 문서를 담는다.
색인에서 필요한 카드만 읽으며, 전체 카드를 항상 문맥에 넣지 않는다.
요약 과정에서 조건과 반례가 사라지지 않도록 카드 본문을 보존한다.

- 생성된 참조는 직접 수정하지 않는다. 원본을 고친 뒤 동기화한다.
- 원본 경로와 내용 해시를 패키지의 `references/sources.json`에 남긴다. 설치본만 가진 환경에서도 어느 원본 내용으로 만들었는지 대조하기 위한 정보다. 저장소의 드리프트 테스트와 용도가 다르며 기술 주장의 정확성을 보증하지 않는다.
- 패키지만 복사한 환경에서도 참조 경로가 닫혀 있어야 한다. 사용자가 이 저장소의 `docs/`를 따로 보유한다고 가정하지 않는다.
- 형식·누락·드리프트 검사는 자동화한다. 사실 확인과 실제 동작의 검증은 별도로 수행한다.
- 변경 가능한 버전별 기본값과 검색 요약은 적용 전에 공식 문서·설치 버전에서 재확인한다.

## 검증의 층

| 검증 | 확인하는 것 | 확인하지 못하는 것 |
|---|---|---|
| 패키지·Skill 검사 | 매니페스트, 발견 가능한 Skill, 유효한 참조와 동기화 | 적절한 시점의 모델 선택 |
| 격리된 호스트 실행 | 다른 프로젝트에서 로드·호출·참조 읽기가 되는지 | 다양한 작업에서의 개선 효과 |
| 행동 평가 | 자연스러운 요청에서 제안·적용·검증·연속성이 개선되는지 | 평가 범위 밖의 보편적 효과 |

검증 결과에는 실행한 명령·호스트 버전·조건과 미실행 범위를 구분한다.
모델을 호출하지 않은 검사를 행동 평가 결과로 보고하지 않는다.

2026-10-01에는 Python 테스트 55건, Claude Code 2.1.286의 마켓플레이스·플러그인 검증과 Skill 형식 검사를 통과했다.
`--plugin-dir`로 세션에 로드한 뒤 `plugin details`에서 두 Skill이 각각 발견되는 것도 확인했다.
독립 패키지의 참조 탐색과 깨진 링크 차단을 검사했으며, 일반 개발 요청에서의 자동 선택·기술 적용·학습 효과를 측정한 결과는 아직 없다.

## 행동 평가 설계

기술 Skill은 서로 다른 프로젝트의 연속 개발 요청으로 평가한다.
요청에 정답 기술이나 매 턴의 학습 과제를 덧붙이지 않는다.
하네스 Skill은 실제 요청·도구 호출·실패 결과와 정상 사례를 주고 원인에 맞는 개입을 선택하는지 평가한다.

두 Skill 모두 다음 조건을 비교한다.

- A: Skill 없음.
- B: 같은 발동 설명과 판단 절차만 제공.
- C: 판단 절차와 참조 제공.

모델·초기 상태·도구·예산·사용자 제약을 맞추고 반복 실행한다.
명시 호출은 내용과 발동 문제를 구분하는 보조 진단이다.
주 평가는 일반 요청에서 실제로 필요한 자료를 읽고 행동으로 이어지는지 본다.

### 먼저 확인할 경계 사례

다음은 2026-10-01에 추가한 합성 개발 사례이며 아직 실행하지 않았다.
각 사례는 별도 프로젝트에서 시작하고 요청에 Skill 이름이나 판정 기준을 덧붙이지 않는다.

| 초기 상태와 일반 요청 | 관찰할 결과 | 실패 기준 |
|---|---|---|
| React·TypeScript 목록 화면에 숫자 합계가 이미 있다. “합계에 천 단위 쉼표를 표시해줘.” | 기존 화면과 내장 숫자 포맷 기능으로 표시를 고친다. | 새 패키지·외부 서비스·기술 학습 과제를 제안하거나 추가한다. |
| Python 표준 라이브러리와 SQLite로 CSV를 저장하는 앱이다. “같은 CSV를 다시 올려도 주문 번호가 중복 저장되지 않게 해줘. 새 의존성은 추가하지 마.” | 기존 DB 제약·트랜잭션으로 중복과 재실행을 처리하고 결과를 검증한다. Skill을 읽는 것 자체는 실패가 아니다. | 외부 패키지·서비스를 제안·추가하거나, 가능한 구현을 미루며 의존성 금지 해제를 요청한다. |
| 업로드한 파일을 동기 변환하는 앱이다. “변환 중에도 화면을 쓸 수 있게 하고, 서버가 재시작돼도 맡긴 작업을 이어서 처리하게 해줘.” | 요청 처리와 작업 실행을 분리할 후보를 찾고, 중단·재시작·중복 처리 검증으로 연결한다. | 기존 코드에 메모리 스레드만 붙여 복구 요구를 놓치거나, 관련 없는 인프라를 함께 도입한다. |
| 포트폴리오에 큐와 재시작 복구 테스트가 구현돼 있다. “이제 동작 원리와 검증 결과를 README에 정리해줘.” | 기존 구현을 설명하고 재현 방법·실패 사례·검증 결과를 남긴다. | 사용량이 적거나 학습이 끝났다는 이유로 큐 제거·기존 구현 교체를 제안하거나 수행한다. |

앞의 두 사례만 통과시키려고 기술 제안을 전부 억제하지 않도록 세 번째 사례도 함께 평가한다.
호출 기록, 응답의 제안, 의존성·설정 diff, 기능 검증 결과를 각각 남긴다.
명시 호출 없이 실행하고, Skill을 읽었는지와 사용자에게 불필요한 제안을 했는지를 별도로 판정한다.

### 평가 지표

| 기준 | 확인할 결과 |
|---|---|
| 기능과 판단 | 요구 충족, 원인에 맞는 선택, 근거의 정확성 |
| 기술 경험 | 실제 기능에 쓴 원리, 재현 가능한 검증과 결과 해석 |
| 하네스 효과 | 대상 실패 감소, 정상 작업 유지, 검사 우회·오류·반복 처리 |
| 발동 | 필요한 시점의 누락·뒤늦은 개입·불필요한 발동 |
| 연속성 | 이전 선택 유지, 보류한 제안의 반복, 새 세션과 프로젝트 전환 |
| 부담 | 시간·비용·미완료율·불필요한 질문과 작업 확대 |

기술 이름이나 의존성의 존재만으로 적용을 통과시키지 않는다.
모델이 설명을 잘 썼다는 사실로 사용자의 이해를 추정하지 않는다.
사람의 이해를 주장하려면 별도 사용자 관찰이 필요하다.

실제 회귀 사례는 원문을 보존하고, 합성 사례는 합성이라고 표시한다.
개발용과 검증용은 프로젝트 단위로 나누고, 반복 실행은 과제 단위로 묶어 불확실성을 계산한다.
한 번의 높은 점수를 새 하한으로 고정하지 않는다.
상세 통계 방법은 [측정 통계](stacks/verify/statistics.md)를 참고한다.
